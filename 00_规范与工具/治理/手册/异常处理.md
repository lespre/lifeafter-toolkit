# 异常处理清单

原则：**异常即数据。** 先识别类型，再按分支处理，不盲目重试。
来源：行业调研（QuickBMS / CUE4Parse / AssetRipper / Ark-Unpacker / arknights-data-pipeline）+ 本项目实战。

---

## 一、错误分类（E1~E7）

| 编号 | 类型 | 典型症状 | 关键判断 |
|---|---|---|---|
| **E1** | 加密/格式识别错 | 头部乱码、解出垃圾 | 魔数不符（`xxd -l 16`） |
| **E2** | 容器版本/变体不支持 | 版本串不符、字段错位 | 头版本字段 vs 已知表 |
| **E3** | 依赖缺失 | ImportError、DLL 找不到 | 环境检查 |
| **E4** | 解码失败 | 纹理解不出、音频 crc 表缺失 | 逐条失败记账 |
| **E5** | 条目/路径缺失 | 找不到条目、命中 0 | **先自证伪**（见 §三） |
| **E6** | 载荷损坏/截断 | 解析中途失败、长度不符 | 长度 vs 声明长度 |
| **E7** | 未知 | 都不像 | 先取证，**禁反复重试同一命令** |

## 二、本项目已确认的坑（含解法）

### 坑 1：名字哈希 0 命中 ≠ 资源不存在
**症状**：按名字查条目，返回 0 命中，容易误判「本地没有」。
**根因**：哈希算法对**斜杠方向**敏感；且候选名变体会撞哈希。
**解法**：
```
· 路径规范化只能有一个函数；先 "/" → "\" 再算
· 查找走有序候选列表：规范化名 → 变体 → **未加工的原始输入**（最后一个候选必须是原始串）
· 命中后必须校验魔数 + bbox，防假阳性
```
**出处**：CUE4Parse `AbstractFileProvider.TryGetGameFile` 的候选回退链。

### 坑 2：多块容器的载荷偏移必须按「该行所属块」算
**症状**：按总偏移取，得到错位数据。
**根因**：块表没进索引，每条都要重推块边界。
**解法**：`firstBlock = offset / blockSize`、`offsetInBlock = offset % blockSize`、
`lastBlock = (offset + len - 1) / blockSize`，逐块解压后 `BlockCopy` 切片。
**根治**：块表进索引（每块 offset / 压缩长 / 解压长 / 方法索引）。
**出处**：CUE4Parse `IoStoreReader`（TOC 的 `CompressionBlocks[]` / `PartitionSize`）。
**现状**：✅ 已解决 —— `lifeafter_files.sqlite3` 保存逐块 payload delta。

### 坑 3：zstd 解压失败是**静默**的
**症状**：某条「没载荷」，不报错。
**根因**：解压方法索引未校验，失败被当成「无数据」。
**解法**：
```
· 压缩方法索引化：0 = 未压缩 (stored)，其余查表；**未知索引直接报错**
· 解压后强校验：长度 == 声明长度、帧 eof 检查
· 失败必须进失败清单，不得静默跳过
```
**出处**：CUE4Parse `CompressionMethodIndex`；AssetStudioMod `--block-comp` 强制覆盖。

### 坑 4：`--find` 假阳性（变体名撞哈希）
**症状**：`h_m_3715a_lod03.gim` 命中一个地图网格（bbox 完全不符）。
**根因**：`variants=True` 生成候选名变体时撞上别的条目哈希。
**解法**：**关掉变体 + 强制校验魔数（编译网格 `3480c8bb`）+ 校验 bbox**。

### 坑 5：bbox 尺寸匹配认网格 —— **已证伪，勿再试**
```
v3~v12 共 10 个版本全败。顺序配对（数量对不上）、IoU（正控 0.6499 vs 负控 0.6365）、
空间相关性（武器正控 0.1677 有效，时装失效）——全部无区分力。
```
**唯一可靠方法 = 名字 → 行号**。

### 坑 6：源坐标语义（背包挂错位置的根因）
```
源 Y 小 = 头，Y 大 = 脚
源 Z **负 = 胸前**（不是背后）⇒ 要贴到背后必须 Z 镜像 + 反转三角绕序
背包声明坐标是**绑骨前模型空间**，不能微调，需重新定位
```

### 坑 7：解析成功 ≠ 内容正确
**症状**：导出成功但结果错（贴图全黑、模型错并、Spine 效果异常）。
**解法**：
```
结构类检查**全量**断言（数量 / 头部 / 哈希 / schema）
内容类检查**抽样人眼**（打开贴图、渲染白模、听音频）
「脚本没报错」不算通过
```
**出处**：Ark-Unpacker issue #27；arknights-data-pipeline 人工修复 SOP。

### 坑 8：第三方库的隐藏假设会变成你的 bug
**实例**：`fsb5` 内置 164 条**为《炉石传说》生成的静态 crc32 表**，遇非标准 Vorbis 必然失败。
**解法**：记录已试方案 + 兜底产物清单 + 推荐外部工具，不无限重试。

### 坑 9：完整性自检
```
三角数 / 顶点数 < 1.5  ⇒ 解析残缺（正常封闭网格 ≈ 2:1）
例：行29184 v=28494/f=36448 ✓    行29191 v=9182/f=8613 ✗
```

## 三、防自欺纪律

任何「100% 命中」先自证伪。参照 Neversoft 的置信度门槛：
> **只有当某类映射的命中次数比碰撞次数高至少 50 倍，才保存该映射。**

```
✗ 禁 any() 多列混判命中
✗ 禁过滤后索引 / 跨列组合凑命中率
✗ 禁由「没找到」反推「不存在」
✓ 单式单列必须报 N/N
```

**「没有名字 = 资源不存在」是错的。** QuickBMS 作者 aluigi 在手册里写：
> 拆包真正必需的只有 `offset`。没有 filename 和 size 都不是问题，只要知道 offset。

行业应对「只有哈希没有名字」的四条路：
```
① 字典 + 哈希反查        ← 本项目已走死（30 万次组合 + 168,513 条字典 → 5,041 条全 0 命中）
② 位置/序号认领          ← 可用
③ 从结构化源头枚举候选名  ← 可用（AssetRipper PR #973：先全局建 CRC 缓存再查，O(N²)→O(N)）
④ 确定性占位名，永不静默丢条目  ← 可用：path_<id> / __Unknown\FD77A2A5 / %08x%08x
```

## 四、上报格式（写死，避免「我这儿报错了」式沟通）

```
【问题类型】E1~E7
【现场信息】命令 / 完整报错原文 / 出错文件路径 + 大小 + 前 16 字节 hex / 相关日志
【已尝试】1. 方案A → 结果   2. 方案B → 结果
【影响范围】哪些步骤 / 资源受影响
【建议回退点】指向工作流第几步
```

## 五、统一停止条件（什么时候必须停下来）

```
· 修复范围扩大到成本明显增加
· 候选结果与源身份 / 哈希不一致
· 关键调用超时或 5xx，且无法确认对端是否已处理
· 产物状态无法确认
· 原问题消失，但关联依赖或边界抽查失败
· 需要删除历史资产 / 覆盖已有交付 / 绕过校验
⇒ 暂停并保留现场，先查证据，再决定重试、回滚还是另开任务。
```

---

## 六、fail-closed 交付纪律

探测失败 / 数量回退 / 哈希不符时，**宁可不发布，也不覆盖上一代可用产物**。
保留候选与草案，先查远端状态再重试，不盲目重复创建。
