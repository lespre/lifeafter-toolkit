# 大型网游拆包项目架构调研与改造方案

日期：2026-10-22　范围：UE / Unity / FFXIV / 网易 NeoX / 通用 CLI 工具

---

## 一、调研对象

| 生态 | 代表项目 | 类型 | 规模 |
|---|---|---|---|
| UE4/UE5 | **CUE4Parse + FModel** | 解析库 + GUI | 最大，覆盖整套 UObject |
| Unity（米哈游） | **AnimeStudio**（AssetStudio 后继） | GUI + CLI | 支持原神/星铁/绝区零 |
| FFXIV | **SaintCoinach** | 库 + 极薄 CLI | 官方级数据完整度 |
| 网易 NeoX | unnpk / NeteaseUnpackTools / neox-tools / NeoXtractor | 单容器小工具 | 只覆盖 npk |
| 通用 CLI | repak / u4pak / QuickBMS | 命令行 | 单格式 |

## 二、六个共性模式（都有实证）

### 1. Provider / VFS 抽象 —— 先统一"文件从哪来"

CUE4Parse 的 `IFileProvider` → `IVfsFileProvider` → `DefaultFileProvider / ApkFileProvider / StreamedFileProvider`，统一了"本地目录 / APK 内 / 远程流"三种来源；上层只认 `provider[path]`。

> 关键点：**来源和内容解耦**。同一个逻辑路径，不管在 pak、apk 还是散文件，调用方代码不变。

AnimeStudio 没有 Provider，但有等价的**"游戏选择器"**（50+ 条目，含各测试版本），本质是"来源配置"。

### 2. 索引先行 —— 先建 map，再取资源

- AnimeStudio：**Asset Map**（全量资产 → 所在 block）+ **CAB Map**（依赖关系）
- CUE4Parse：挂载时建 `FileProviderDictionary`，带 `readOrder`
- FFXIV：`SqPack` 索引 + `exl/exh/exd` 三级
- repak：`hash-list` 出清单

共同点：**索引是可落盘、可复用、可跨版本 diff 的产物**。AnimeStudio 明确写了"不需要每次重建，游戏更新才重建"，且"两张 map 可并排加载看版本差异"。

> 我们已有 `pe_index.sqlite3`（174 包 / 180 万行），但它同时承担"索引"和"查询入口"，没有 diff 能力。

### 3. 版本感知 —— 一个常量决定解析方式

- CUE4Parse：`VersionContainer(EGame.GAME_UE4_LATEST)`，每个 enum 对应一套偏移/序列化
- SaintCoinach：`realm.IsCurrentVersion` + `SaintCoinach.History.zip`（历史映射）
- AnimeStudio：按游戏版本选解密（`Live` vs 早期 build）
- NeoX 工具：`neox-tools` 直接写"只支持某版本"

> 我们的等价物是"服型 + 快照版本"，但现在散在代码里（`kj1` / `kjxq` / `pe_20261020`）。

### 4. 每游戏差异做成"覆盖层"，不是分支

- CUE4Parse：`CUE4Parse/GameTypes/<Game>/` 放 `FAion2PropertyReader`、`PartialEncryptionPakFileReader` 这类**局部覆盖**
- AnimeStudio：50+ 游戏条目各带一套解密
- NeoXtractor：Config Manager 存 XOR key + 名字表

> 模式：**默认实现 + 少数覆盖**。不是 `if game == "A" ... elif game == "B"`。

### 5. CLI 是库之上的一层薄壳

- SaintCoinach.Cmd：`raw` / `image` / `ui` / `exd` / `sql` / `bgm` / `maps`，每个命令一行实现
- AnimeStudio.CLI：`--game --types --names --containers --group_assets --map_op --silent`
- repak：`info/list/unpack/pack/get/hash-list`

> 没有谁把业务逻辑写在 CLI 里。CLI 只做"参数 → 库调用"。

### 6. 导出三件套：类型 / 过滤 / 分组

- AssetStudio：`-t tex2d,sprite,audio` + `--filter-by-name` + `-g type|container|fileName`
- AnimeStudio：`--types --names --containers --group_assets`
- SaintCoinach：`ui 1 999999`（按范围）、`allexd`（按语言）

## 三、结论（修正我上一条的说法）

**结论 1：五层结构真实存在，但只属于"要覆盖整套引擎对象体系"的项目。**
CUE4Parse 分层是因为 UE 有几千种 UObject；FFXIV 分层是因为它有 excel 关系数据库 + 多语言。
网易系工具不做分层，因为它们只到"把 npk 拆成文件"。

**结论 2："每游戏配置档案"是跨生态的硬需求，不是可选项。**
NeoXtractor 的 Config Manager、AnimeStudio 的 50+ 游戏选择器、CUE4Parse 的 GameTypes、SaintCoinach 的 History.zip —— **四个生态、四种做法、同一个需求**：同一份代码要跑不同游戏/版本。

**结论 3：索引必须升格为一等公民。**
AnimeStudio 把 Asset Map 当独立交付物（可保存、可加载、可 diff）；我们把它当下游缓存。这是当前最大的架构差距。

## 四、我们与四种模式的落位

| 模式 | CUE4Parse | AnimeStudio | SaintCoinach | NeoX 系 | 我们 | 差距 |
|---|---|---|---|---|---|---|
| Provider 抽象 | ✅ IFileProvider | ⚠️ 游戏选择器 | ✅ Packs | ✗ | ⚠️ pe_fetch/pc_fetch 各自为政 | **中** |
| 索引先行 | ✅ VFS 字典 | ✅ Asset/CAB Map | ✅ SqPack | ✗ | ✅ pe_index | 缺 diff |
| 版本感知 | ✅ VersionContainer | ✅ 版本条目 | ✅ History.zip | ⚠️ 硬编码 | ⚠️ 散落常量 | **高** |
| 覆盖层 | ✅ GameTypes | ✅ 每游戏解密 | ✅ 每版本映射 | ✅ 配置 | ✗ 无 | **高** |
| 薄 CLI | ✅ | ✅ | ✅ | ✅ | ✅ la.py 14 命令 | 达标 |
| 类型/过滤/分组 | ✅ | ✅ | ✅ | ✗ | ⚠️ 仅 `--filter` | 中 |
| 版本 diff | — | ✅ 双 map 并排 | ⚠️ 更新报告 | ✗ | ✗ | **高** |
| 板块/发布层 | ✗ | ✗ | ✗ | ✗ | ✅ board/wiki | **领先** |

**一句话**：容器和表解码我们领先；**配置档案、版本感知、索引 diff 三项落后**。

## 五、改造方案（三阶段，按投入产出排序）

### 阶段 0：配置档案（1 天，收益最高）

新增 `profiles.yml`：

```yaml
default: pe_test_20261020

profiles:
  pe_test_20261020:
    label: 测试服 · 经典+简单生存
    root: E:/mrzh
    tree: 01_索引与产物/41_还原树/pe/配置
    index: 01_索引与产物/10_索引/pe_index.sqlite3
    containers: [gpk, npk, fpk]
    keys: {npk_xor: auto, gpk: none}
    servers: [classic, simple]
  pc_test_20261020:
    label: 测试服 · PC 侧
    root: E:/mrzh
    index: 01_索引与产物/10_索引/pc_index.sqlite3
    containers: [gpk]
```

CLI 加 `--profile`（默认取 `default`），`la.py profile list|show|use`。

**验收**：`la.py --profile pc_test_20261020 find ...` 与不带参数结果一致；新增 profile 不改代码。

### 阶段 1：索引升格（2 天）

```
1  pe_index 增加 manifest 表：快照 id / 包 sha / 行数 / 生成时间
2  新增 la.py index diff <A> <B>：包级 + 行级差异（对标 repak hash-list）
3  find/list/info 输出统一带 snapshot 字段
```

**验收**：热更前后各跑一次 `index diff`，能列出「新增 37 包 / 变更 12 包 / 删除 0 包」。

### 阶段 2：覆盖层（3 天）

```
1  toolkit_core/registry.py：
     READERS = {"NXPK": NpkReader, "HPGF": GpkReader, "FPK1": FpkReader}
     HANDLERS = {"texture": ..., "audio": ..., "table": ..., "spine": ...}
2  容器 Reader 协议：can_handle(magic) / entries() / read(row) -> bytes
3  服型差异走 profile.overrides，不写 if
```

**验收**：新增一种容器只需注册一个类，`la.py find/list` 自动可用。

### 阶段 3：类型/过滤/分组对齐（2 天）

```
la.py export <容器> --types texture,audio --filter "*skin*" --group type -o out/
```

对标 AnimeStudio 的 `--types --names --group_assets`。

## 六、不做什么

| 不做 | 理由 |
|---|---|
| 完整五层（UObject 级） | 我们不需要解析引擎对象图，只到资源和表 |
| 通用 Provider 支持远程流 | 单机项目，无收益 |
| 打包（pack）能力 | 只读分析，写回无意义 |
| 自研 GUI | 站点已经是消费层 |

---

## 七、优先级总结

```
P0  配置档案 profiles.yml + --profile       ← 立刻做，1 天
P1  索引 manifest + index diff              ← 热更场景刚需
P2  容器/编解码注册表                        ← 遇新格式才不卡
P3  export --types/--group 对齐             ← 体验提升
```

按投入产出，**P0 的 1 天能解决"换个服/换台机器就定位失败"这个真实痛点**，优先做。
