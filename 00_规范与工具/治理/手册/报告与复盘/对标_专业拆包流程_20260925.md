# 对标：专业拆包项目流程 vs 我们（2026-09-25）

## 一、业界主流工具链的流程骨架

| 工具 | 流程 | 可借鉴的核心 |
|---|---|---|
| **FModel**（UE 事实标准） | ① 解析 Pak 索引 → **建立资源路径映射表** ② 反序列化资源 ③ **解依赖** ④ 导出 | **先建路径映射表，再动资产**；导出前解依赖 |
| **AssetStudio**（Unity 事实标准） | 加载容器 → 建 asset 列表 → 按类型/容器筛选 → 导出（含依赖） | **按容器（byContainer）提取**，不是全量解 |
| **QuickBMS** | **BMS 声明式脚本**描述容器格式 → `list` / `extract` / `re-pack` | **格式描述与执行引擎分离**；一个脚本一个格式 |
| **huermi/game-asset-extraction**（中文实战库） | **29 工具 / 3 条标准化工作流 / 异常处理**，覆盖 解包→解密→解码→分类→角色聚合；目标是「**新 AI 无需人工解释即可按文档独立执行**」 | **流程文档化到可被陌生人/AI 直接执行** |
| **assetpipe** | 把资源当源码：**provenance + 依赖图 + 校验 + credits** | **依赖图与自动校验** |
| **UE/Unity TOC 机制** | 索引表 = 偏移映射 + magic 校验；content-addressable（文件名=内容哈希） | 索引即契约 |

### 归纳：专业流程的 6 个稳定动作
```
① 格式识别（magic → parser）            ④ 类型识别与分类（magic/扩展名/依赖）
② 索引解析（TOC：名字→偏移映射）         ⑤ 依赖解析（资源引用图：模型→贴图→材质→骨架）
③ 按需提取（byName / byContainer）       ⑥ 导出标准格式 + 校验
```

## 二、逐项对标

| 环节 | 专业做法 | 我们的现状 | 差距 |
|---|---|---|---|
| **① 格式识别** | magic 驱动、多格式注册表 | ✅ 已有（`c159410d`/`3480c8bb`/`NXPK`/`SKPW`），但**散在脚本里** | 需集中成格式注册表 |
| **② 索引解析** | TOC 表 + 名字映射，**先建索引** | 🟡 有 `gpk_index.tsv`、`mesh_index.json`、名称还原对照库（1.4M 条），但**分散、各脚本各自建** | **统一到 `00_index/`，一次建好复用** |
| **③ 按需提取** | `byName` / `byContainer` | 🔴 **长期整包解**（platform 变 167 万文件）；`--find` 能按名查但慢 | **禁止整包解；一律 byName/byContainer** |
| **④ 分类** | 按 magic/扩展名自动分类 | 🟡 部分 | 成体系 |
| **⑤ 依赖解析** | 资源引用图 | 🔴 **完全没有**（今天才发现 `c159 → Lods → 编译网格 → 贴图` 是条链，全手工串） | **建依赖图，这是最大缺口** |
| **⑥ 导出+校验** | 标准格式 + 自动校验 | 🟡 有完整性自检（f/v 比）、bbox 校验、GLB 结构自检 | 需纳入统一管线 |

### 我们独有、比通用工具强的地方（要保住）
1. **名字哈希算法**（murmur3 双 seed + 反斜杠分隔）—— 多数工具只能靠已知名字表，我们能**由路径反查条目**
2. **bbox 认领法** —— 编译网格**不带名字**时的唯一出路（通用工具遇到这种只能放弃）
3. **多容器热更支持** —— 36 个 gres 包 + 按块算载荷偏移（这块今天才彻底打通）

## 三、我们缺的三样（按重要性）

### ★★★ 1. 依赖图（最大缺口）
现在「模型 → 贴图 → 材质 → 骨架」的引用关系全靠人肉串，今天光找头饰/背包就绕了十几轮。
**专业做法**：解析时顺手抽出引用边，落成一张表（`from → to → 关系类型`），后续「要什么就沿图取什么」。
**对应实现**：解析 `c159` 帧时把 `Lods` / `GisFiles` / `MtlIdx` / 槽位表全部入图。

### ★★ 2. 声明式格式描述（替代硬编码脚本）
QuickBMS 的做法是「一个格式一个脚本」，执行引擎不变。
我们现在是**每个新问题写一批 `qj_*.py`**，换个对象就得重写（今天累积几十个）。
**对应实现**：把容器/帧格式抽成 yaml/json 描述，引擎按描述跑。

### ★★ 3. 「新 AI 无需解释即可执行」的文档
huermi 那个库的卖点就是这个。我们靠技能（`lifeafter-*`）+ 我的记忆，**换个人/换个会话就要重新摸**。
**对应实现**：`03拆包产物/00_index/README.md` 写清：这个包里有什么、怎么查、怎么提、字段含义、坑在哪。

## 四、建议落地的目录与流程

```
E:\la拆包项目\
  01拆包器本体/            工具（对 mrzh 只读）
  02文档索引/              文档
  03拆包产物/
      00_index/            ★ 索引先行（一次建好，全局复用）
                           fname_index.json    名字→fid
                           gpk_index.tsv       容器→行→偏移（按块）
                           mesh_index.json     编译网格 bbox（已有 94k 条）
                           refs_graph.json     ★新增：资源依赖图
                           README.md           ★新增：给陌生人/AI 的执行说明
      10_snapshots/        热更快照，命名 <源>-<日期>-<包哈希前8>
      20_extracted/        按需解包产物（byName / byContainer）
      30_analysis/         分析产物，按专题分目录
      40_deliverables/     只放定版交付
  04临时存放/              临时，定期清
```

### 三条铁律（今天血换来的）
1. **先索引，再解包** —— 永不整包解（167 万文件就是这么来的）
2. **认领只走「名字→fid→行号→bbox 校验」** —— 禁止按形状/尺寸猜
3. **实验产物不入交付面，定版即删**

## 五、一句话总结

**流程动作我们基本都有，但都是「每遇到一个问题临时写一个脚本」。专业项目的差距不在技术，而在：
把一次性脚本沉淀成「索引 + 依赖图 + 声明式格式描述 + 可被外人执行的文档」。**

我们反而在两个点上比通用工具强（名字哈希反查、无名字编译网格的 bbox 认领）——
**这两点该写进 `00_index/README.md`，变成项目的招牌能力。**
