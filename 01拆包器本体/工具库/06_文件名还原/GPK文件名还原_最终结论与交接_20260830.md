# GPK 文件名还原 — 最终结论与交接（2026-08-30）

> 结论先行：**GPK 条目里的 c1/c2 不是路径名哈希，而是「内容指纹」（自研 64 位内容哈希，用于打包去重）。**
> 因此「逆一个路径哈希算法、用路径反推条目名」这条路在原理上不成立，任何 Murmur/CRC/FNV 变种都不必再试。
> GPK 条目本身**不携带任何文件名/路径信息（完全匿名）**，文件名只能靠**外部映射**恢复。下文给出 3 条唯一可行路线。

---

## 一、GPK 容器与条目精确布局（已完全确定）

- 文件头 AES-128-**ECB** 解密，KEY = `606308D8A32C782013D26C2F226F686D`（与 fpk/npk 通用）。
- 解密后：
  - `[4:8]` = `FPGH` 魔数；`[8:12]`=版本2；`[20:24]`=条目数 B（u32 LE）。
  - 条目表从偏移 **64** 开始，每条 **32 字节**，共 B 条，布局 `<IIIIII`：

| 字段 | 偏移 | 含义 |
|---|---|---|
| o   | 0  | 数据在文件中的绝对偏移；数据体从 **o+36** 开始（36B 单条目头） |
| cmp | 4  | 压缩后字节数 |
| dec | 8  | 解压后字节数 |
| **c1** | 12 | 内容指纹高/字1（u32） |
| **c2** | 16 | 内容指纹低/字2（u32） |
| fl  | 20 | 压缩标志：0=原始 / 2=lz4 block / 12=zstd |

- 解包实现见 `01_核心解包器/lifeafter_unpacker_full.py::parse_gpk_entries / extract_gpk`，已稳定。

## 二、八步证据链（脚本见同目录 `gpk_内容指纹验证_20260830/`）

| 步 | 实验 | 结果 | 推论 |
|---|---|---|---|
| 1 | dump c1/c2 分布 | 覆盖全 32 位、无 0 值；weapon 51664 条仅 28474 唯一对，45% 重复 | 像哈希，且大量重复=去重 |
| 2 | 125 个已知 model_path × 271.7 万次哈希碰撞 | 双 32 位 pair **0 命中**，单值 6 次全为随机噪声 | 排除标准路径哈希 |
| 3 | c1/c2 vs 数据 CRC32(压/解)/Adler/MD5 前缀，400 样本 | 全部 0 命中 | 不是标准整段校验和 |
| 4 | 条目内嵌依赖路径扫描 | 前 3000 条含 1153 条**原汁原味 NeoX 路径**（反斜杠，如 `weapon\26_chunjie\textures\xxx.tga`） | 拿到真实路径语料 |
| 5 | 1153 真实路径 × 双 Murmur(7777/6666 及种子对) | pair **0 命中** | NPK 同款双 Murmur 对 GPK 无效 |
| 6 | 补测 UTF-16LE 宽字符 + Murmur3 x64_128 + FNV64，含去扩展名/basename/小写 | pair **0 命中** | 排除宽字符与 64/128 位变种 |
| 7 | 跨 4 个 gpk 求 (c1,c2) 交集 | weapon∩effect02=1，其余全 0，四包公共=0 | 非「全局路径哈希」（否则公共 shader/材质会大量重复） |
| 8 | 包内相同 (c1,c2) 组比对解压内容 MD5（前 60 组） | **60/60 逐字节完全相同，0 组不同** | **c1/c2 = 内容指纹（去重 key）** |

> 第 7 步与第 8 步不矛盾：c1c2 是内容指纹；不同类型包（武器/特效/UI）本就没有逐字节相同的块，故跨包交集≈0；同一资源被包内多处引用时去重，故包内同指纹=同内容。

## 三、已永久证伪清单（请勿重复投入）

以下对「路径字符串」求哈希再撞 c1/c2 的组合**全部 0 命中**，不要再试：
- 算法：Murmur3 x86_32（种子 0/1/0x77777777/0x66666666/0xFFFFFFFF/0x9e3779b9/0xdeadbeef/0x12345678 及任意两两配对）、Murmur3 x64_128（多 seed、多种切分）、CRC32、FNV1/FNV1a(32/64)、djb2；
- 编码：UTF-8 / UTF-16-LE / GBK；
- 路径形式：原样、正/反斜杠互换、全小写、去扩展名、换扩展名(.gim/.mesh/.dds/.tga/.fx…)、basename、加前缀(res/ / ./ weapons/)；
- 内容侧：CRC32(压缩体/解压体)、Adler32、MD5 低 32 位。

c1/c2 是**自研内容哈希**（可能滚动/分块，非整段标准哈希），但因为它不编码路径，**还原其算法对「取文件名」没有帮助**，不建议为取名而逆它。

## 四、唯一可行的三条文件名还原路线

### 路线 A（推荐，主攻）：外部资源清单/目录表
游戏运行时必有「逻辑路径 → (哪个 gpk, 第几条)」的目录，它不在 gpk 内，候选位置：
1. **`E:\mrzh\res\ui.npk`（3.3GB，NPK 格式，条目带双 Murmur file_id）**——最可能藏全局资源目录，优先在其中找「大批量 (pkg_id, entry_index, file_id) 三元组」结构的条目。
2. `script.npk / script.py3.npk / script.py314.lc.npk` 内的 .nxs 资源清单（reslist/manifest/resource_map 类）。
3. `Documents\pkgmapping.json`（当前 mapping 为空，default_pkgname=res）、`preload*.json`（只给了类型→包号范围，不够细）。
4. exe 内嵌打包 manifest（需逆向，硬骨头）。
- 关键配置线索：`Documents\cloud.json` 有 **`"enable_namehash_check": true`**——引擎确有 namehash 校验机制，其查找表即本路线目标，建议在 exe 里搜 namehash/ResourceManager 相关字符串定位表结构。

### 路线 B（现在就能做，部分有效）：内容指纹/MD5 撞库
- c1c2 相同=内容相同，且 `extract_gpk` 已能拿到每个条目的解压字节。
- 用「已知来源」文件（**正式服 `E:\lifeafter`、APK 解包、本地缓存/下载目录**）解出后算内容 MD5，与体验服 gpk 条目解压内容 MD5 比对，命中即命名。
- 雏形已存在：主解包器 `build_gpk_md5_index()`；WPK 阶段曾用此法 77/93 成功。优点是确定性、可批量；缺点是只能命名「别处也存在」的资源，全新独有资源撞不上。

### 路线 C（辅助）：依赖图传播命名
- `.gim/.mat/.mesh` 等条目内部含依赖路径（步 4 已挖出 1153 条，正则见 `gpk_find_embedded_path.py`）。
- 从路线 B 获得少量「种子命名」条目后，沿「条目 → 其内部引用的同包路径」做图遍历，把名字传播到关联的 mesh/dds/材质。需配合路线 A/B 提供种子。

## 五、给接手模型的最短复现实验（先验证再动手）

1. 跑 `gpk_内容指纹验证_20260830/gpk_duplicate_content.py`：亲眼确认「同 c1c2 ⇒ 内容 MD5 相同」。
2. 跑 `gpk_crosspkg.py`：确认跨包 (c1,c2) 交集≈0。
3. 跑 `gpk_collide_embedded.py`：确认真实路径双 Murmur 0 命中。
4. 三者一致后，直接走**路线 A**（在 ui.npk / script NPK 里找资源目录表），不要再花时间猜路径哈希算法。

## 六、与 NPK 文件名还原的区别（别混用）

- **NPK**（ui.npk/script*.npk）：条目 48B，**首字段就是 64 位 file_id = 双 Murmur3(路径, seed 0x77777777 高 / 0x66666666 低)**，可用 `06_文件名还原/filename_restore.py` + 路径字典还原（已可行）。
- **GPK**：条目 32B、**无 file_id、无路径**，c1/c2 是内容指纹——两套机制完全不同，不能把 NPK 的 path_id 套到 GPK。
