# `fashion_data.friendliness` 是什么 —— 调研说明（v3，终版：语义未能确证）

> v1 误判（把"魅力 20 的背包给 1960"当反例）→ v2 查清"按部位固定"→ **v3 推翻"同居好感度"的解读**。
> 数据源：`01_索引与产物/41_还原树/pe/配置/com/cdata/`（PE 还原树，2026-11-01 快照）。

---

## 一句话结论

**能确证的**：`fashion_data.friendliness` 是时装自带的一个 **100 分制隐藏分值**，绝大多数款式是
**按部位的固定值**（背包 1960 / 衣服 1280 / 头饰 680 / 整套 680·1280·1580·1960），**与魅力值无关**。

**不能确证的**：它在游戏里到底影响什么 —— **配置表里查不到任何一条把它和玩法连起来的线**。

---

## 1. 已确证的事实

| 项 | 值 |
|---|---|
| 字段 | `fashion_data.friendliness`（整数） |
| 规模 | 11,169 行里 1,355 行有值 → 886 款 → 板上 1,047 张卡 |
| 值域 | 18 个离散值 240~1960，全是 20 的倍数 |
| 缺省 | 该款不带此值（不是 0） |
| 全库出现范围 | 只有 5 张表：`fashion_data` / `fashion_data_for_export` / `player_appear_data` / `player_appear_v2_bag_data` / `cohabit_level_data` |

**按部位的固定值**：

| 部位 | friendliness |
|---|---|
| 背包 | **1960**（110 张卡无一例外） |
| 衣服 | **1280**（3 行例外） |
| 头饰 | **680**（9 行例外） |
| 整套 | 680 / 1280 / 1580 / 1960 |
| 无 part_type（199 款老时装） | 240~1280 分散 |

**与魅力值无关**（分层后映射完全干净）：魅力 20 / 70 / 100 / 200 / 300 / 400 / 600 / 800 / 1000 / 1500 / 2000 / 3000
的背包**全是 1960**；魅力 35~1400 的衣服**全是 1280**；魅力 0~600 的头饰**全是 680**。

⚠️ 方法论教训：直接算互信息会得到"魅力值解释 68% 熵"的结论 —— 那是**假相关**，
因为部位同时决定两者。**必须先按部位分层再看映射**。

## 2. 为什么觉得它像"好感度"（以及为什么这个想法没被证实）

支持"像好感度"的证据：

1. `cohabit_level_data`（同居等级，5 行）用 `friendliness` 字段名承载同居五档：
   相遇 0（0 天）/ 相知 700（7 天）/ 相伴 1500（15 天）/ 同行 3000（30 天）/ 同心 6000（60 天）
   —— **阈值 ÷ 天数 = 100，五档精确相等**。
2. 时装的三档固定值恰好贴着这套刻度：头饰 680 **差 20** 到「相知 700」；
   头饰+衣服 = 1960 达「相伴」；再加背包 = 3920 达「同行」。
3. 700 / 1500 / 3000 这三个数在游戏里是**通用评分刻度**（大量表的 `score` 字段用同值：
   `combat_power_title_conf_data` / `artifact_entry_level_data` / `new_year_pass_card_buy_data_1` …）。

但**反证更关键**：

1. **同居表群 30 张里没有任何时装关联字段**。`cohabit_*` 全表字段并集里，
   与物品相关的只有 `cost_item_id` / `item_count` / `item_title` 这类道具字段，
   **没有 fashion / appear / equip / skin 任何一个**。也就是说：**配置表里没有一条线把时装接到同居系统上**。
2. **同居好感度是另一套机制**，由互动驱动而不是装扮：
   `cohabit_recommend_conf_data`（`be_loved_female/male`、`be_hated_female/male`、`like_limit`、
   `double_love_str`）、`cohabit_offline_data.love_food_daily_limit`（每日送爱心食物上限）、
   `cohabit_agency_conf_data.add_like_txt`（点赞文案）…
3. **同名字段在别处语义完全不同**：`zss_zombie_friend_data.friendliness` 上限只有 300（速率 0.01），
   是"僵尸好友"系统的分数。说明 "friend" 在这套代码里只是命名字习惯，不代表同一套体系。
4. `add_friendliness_data`（10 档 `critical_prob` 0.2~0.8 / `critical_ratio` 1.5 /
   `add_range` = 品级区间 [2,4]…[8,10]）是**品级→暴击**表，与本字段无关（名字撞车而已）。

⇒ 数值刻度相同 + 没有连接线 ⇒ **更可能是"同一套 100 分制评分体系下的另一个分项"，而不是好感度本身**。

## 3. 还剩三种可能（数据里分不出来）

| 假说 | 支持 | 不支持 |
|---|---|---|
| A. 时装携带的**好感/亲密分值**，参与同居或伴侣互动 | 刻度与同居五档吻合；字段名就叫 friendliness | 没有任何表连接时装与同居；玩家完全感知不到 |
| B. **装扮评分/收藏度**一类的隐藏权重（策划内部排序或解锁权重） | 按部位固定、与魅力值脱钩、100 分制 | 找不到消费方（无表引用该值） |
| C. 早期版本的遗留字段（老款有值、新款只填部位默认值） | 199 款老款值分散杂乱，新款几乎只按部位填 | 新款仍在持续写入该字段（说明还在用） |

> 注：C 的"新款仍在写"是反证 —— 若真是死字段，新数据不会继续填。所以**它一定还在被某个系统读**，
> 只是这个系统不在配置表里（很可能在客户端逻辑或服务端）。

---

## 4. 怎么定案（只能靠游戏内/实测）

配置表到此为止，再挖也是猜测。可行的三条路：

1. **看 UI**：时装详情页 / 衣柜 / 搭配界面里有没有出现这个数（或它的换算值）。
2. **问人**：别问"时装加好感度吗"（玩家视角答"没有"），改问具体的：
   - "背上背包装备后，同居等级会不会涨得更快？"
   - "时装在搭配/收藏评分里算分吗？不同部位的时装分数一样吗？"
3. **对比实测**：拿两件只差一个变量的
   - 同部位：普通头饰（680）vs **赤焰风华典藏-头饰**（1960）
   - 同部位不同款：**瑞秋的背包**（背包，1960）vs **福兔春禧-头饰**（720）
   看两者在游戏里所有相关界面上的差异。

## 附：解码正确性验证（排除"解错了 / 名字引错了"）

**① 字段名不是外部映射表，是表文件自带的 schema**
bindict 行格式：`[marker][uleb schema_ref][uleb bitmap_ref][value stream]`；
schema 在同一个 blob 里定义：`n(字段数) / bits(位图位数) / n×(slot, type_byte, 名字)`，
名字从该表的字符串池（`fashion_data_chs.py`）按 slot 取。
→ 字段名错位会让**整行所有字段**一起乱，不可能只错一个。

**② 同一行的其它字段全部语义自洽**（fashion_data key=166000 极地朋克，schema_ref 1772）：

| 字段 | 值 | 判定 |
|---|---|---|
| name | 极地朋克 | ✓ |
| desc | 一件永久款头饰。 | ✓ 中文描述 |
| new_fashion_id_str | hat_3002_1_0 | ✓ 帽子 |
| model_id / level / charm_value | 3002 / 4 / 40 | ✓ |
| icons / appear_ids / theme_codes | jump:99623 / jump:99630 / jump:45158 | ✓ 引用型 |
| show_no_have / fashion_preview / hide_in_bag / obtain_notify / max_stack_num | 1 / True / True / 1 / 2147483647 | ✓ |
| **friendliness** | **400** | 该款是 199 款无 part_type 老时装之一，取值本就散（240~1280） |

**③ 跨三张独立解码的表，零值冲突**
`fashion_data` ↔ `player_appear_data` ↔ `fashion_data_for_export`：
**849 / 1,355 行三表完全一致**；其余 506 行全是 166xxx 段老款，
差异形式是「外观表上没这字段」，**没有一行出现值不同**。

**④ schema 里字段名的字典序正确**
`schema 1772: … forbid_primary_high_model | foreign_name | friendliness(t1) | gift_package_id | …`
`t1` = ULEB 整数标量；`foreign_name < friendliness < gift_package_id`（f-o-r < f-r-i < g-i-f），
名字池索引没错位。

**⑤ 值本身不可能是解码噪声**
背包 110 张卡**全部** 1960、衣服全部 1280、头饰全部 680（仅 21 行例外，且都是特殊系列）、
老款散在 240~1280 且全是 20 的倍数 —— 这是「策划按部位批量填」的形态，解码噪声不会这么整齐。

⇒ **结论：字段名与数值都是真的**。剩下的"诡异"来自策划的命名与用法，
不是我们的解码问题。
