## 2. 护手归属与改绑

- 护手 = **prim1（Sub1, pbr_crystal）**；宝石 = **prim2（Sub2, pbr_crystal）**（依据 c159 材质序 + 旧 viewer.json per_submesh 交叉印证）。
- **只接参数不够**：D1（cp 有 + `t_basecolor=029_a` 青蓝）护手仍是蓝色钢。
  原因：viewer 公式 `A=mix(q_T, q_T*u_crystal_color, mm)`、`B=mix(u_base_color, q_T*u_crystal_color, dd)`，
  `q_T = 029_a`（青蓝）把 `T*u_crystal_color` 污染成冷色，红色/银色都上不来。
- **受控对照 D1 → D2**（同 manifest 只动一处：把 prim1/2 的 `t_basecolor` 移出渲染输入，
  使 viewer 走 `hasBaseTex=false → q_T=vec3(1.0)`）：

| 变体 | 设置 | blue_frac | red_frac | silver_frac | 观感 |
|---|---|---|---|---|---|
| D0b | 无 cp + diag env | 0.69% | 0.04% | 2.03% | 护手饱和蓝 |
| D1 | cp + T=029_a | 0.67% | 0.04% | 2.03% | 护手蓝钢，无红宝石 |
| **D2** | **cp + q_T 无色** | **0.00%** | 0.06% | **2.70%** | **银白护手 + 中央红宝石 + 柄尾红宝石** ✓ 与参考图一致 |

- **交付采用 D2 口径**：`withheld_slots.t_basecolor` 完整保留源 `logical_path` + `binding_basis` +
  `restore_rule`（一键回退到 D1）。**没有删除任何源证据，也没有顶替任何贴图。**

## 4. 阻塞（viewer 侧，未自行修）

`assets/weapon_skin_viewer.js:1182`
```js
m.customProgramCacheKey=function(){ return 'crystalSrc_'+primIdx+'_'+((typeof prevKey==='function')?prevKey():''); };
```
`prevKey()` **未绑定 this**。当该材质没有自有 `customProgramCacheKey`（= `iblCube` 为 null，即 **prim2 缺
`fashion_qiangpi.cube`**）时，`prevKey` 落到 three 的原型方法
`Material.prototype.customProgramCacheKey(){ return this.onBeforeCompile.toString() }`
（`assets/vendor/three/three.core.min.js`），`this===undefined` →
`TypeError: Cannot read properties of undefined (reading 'onBeforeCompile')`
→ `renderer.render()` 抛出 → **整帧中止：画面全黑、`snapshot()` 无图**。

- 实测堆栈：`at customProgramCacheKey (three.core.min.js) ← weapon_skin_viewer.js:1182 ← weapon_skin_viewer.js:1222 ← getParameters`。
- L1222 的 `pk()` 是**同型**缺陷（当前被 L1182 先装了自有函数所掩盖）。
- 建议改法：`prevKey.call(m)` / `pk.call(m)`。
- 因果对照：同一 manifest，仅把 prim2 `t_custom_ibl` **临时**指向 prim1 同一 cube（诊断用、已回退）→ 渲染恢复正常；
  保持 `missing` → 全黑。故 `fashion_qiangpi.cube` 未定位是当前 1110177 完全不可渲染的直接触发条件。
- `fashion_qiangpi` 在项目全部索引/产物中检索无命中，故按纪律记 `missing`，**不顶替**。
