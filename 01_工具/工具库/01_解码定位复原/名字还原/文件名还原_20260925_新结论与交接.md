## 1. 三族容器 · 三套机制（必须分开记，别混用）

| 族 | 容器 | 条目结构 | 名字能否还原 | 方法 |
|---|---|---|---|---|
| **NPK** | `res/**/*.npk`（ui.npk 3.3G 等） | 头 32B(AES-ECB) + 条目 **48B** | ✅ **能** | 首字段 = **64 位 file_id = 双 Murmur3(路径)**：`(murmur3(path,0x77777777)<<32) \| murmur3(path,0x66666666)`，ASCII、**路径用反斜杠**。配路径字典即还原 |
| **GPK** | `res/*.gpk`、`Documents/gres/*.gpk` | 头 32B(AES-ECB，KEY `606308D8A32C782013D26C2F226F686D`) + 条目 **32B** | ❌ **不能** | c1/c2 = **内容指纹**（非路径哈希）。八步证据链已永久证伪 |
| **WPk/1DPW** | `Documents/res/*.idx` + `*.wpk` | idx 头 `SKPW75`，条目 16B hash | ❌ **不能直接** | idx 的 16B = **payload MD5**（本轮 60/60 实测）。名字必须靠外部 path↔MD5 对照库 |

**★ 本轮更正**：此前（含 8/30 文档）只说「GPK 无文件名」，**没区分 WPk/1DPW 族**。现在补齐：
**WPk 的 idx 存的是内容 MD5 —— 这是可用信息（可撞库），不是死路。**

### AES 头钥（三族通用）
```
KEY = 60 63 08 D8 A3 2C 78 20 13 D2 6C 2F 22 6F 68 6D   (AES-128-ECB, IV 全 0, NoPadding)
NPK: 头 32B 解密后 [8:12]==b'NXPK', [12:16]=ver(3), [16:20]=table_off, [20:24]=total
     条目 48B: u64 file_id | u32 off | i32 csz | i32 dsz | u32 cCRC | u32 dCRC | i32 flag | 16B reserved
GPK: 头解密后 [4:8]==b'FPGH', [8:12]=ver2, [20:24]=条目数；条目表自偏移 64 起、每条 32B
     <IIIIII> = o, cmp, dec, c1, c2, fl     数据体自 o+36 起
     fl: 0=原始 / 2=lz4 block / 12=zstd
```

## 4. 时装/外观 3D 还原（本轮新打通，与文件名无关的一条独立链）

**★ 权威绑定源 = 「模型装配帧」**（`.c159` 帧，特征是同时含 `Lods` + `GisFiles`）：

```
Name         = b_m_3715
Lods:        character\players2021\b_m_3715\b_m_3715_lod01.gim   ← b_ = 衣服主体
             character\players2021\b_m_3715\h_m_3715_lod01.gim   ← h_ = 头饰
GisFiles:    character\players\m002011\m002011.gis               ← 骨架
BoundingInfo: (cx,cy,cz),(halfx,halfy,halfz),radius              ← 世界坐标，可用来绑网格
```

**部件区分规则**：目录 `b_[mf]_NNNN` 只是挂靠，**部件类型看文件名前缀**（`b_`衣服 / `h_`头饰 / `bag_`背包）。
**排除**：含 `shadow`、结尾 `_1`、含 `_1001` 的是阴影件/附加变体。

**绑定网格**：装配帧 `BoundingInfo` 的 `2×half` = 尺寸 → 与编译网格 `sorted(span)` 按比例归一后比 → 相对误差 **≤0.0012** 即可信。
**合并部件**：按装配帧声明的 **center** 平移每个部件再拼（**不能直接拼顶点** —— 各部件坐标系不同，头饰会掉到地上）。
**渲染页必设**：`side = DoubleSide`（绕序不定）、`rotation.x = Math.PI`（源网格 Y 轴朝下）、
**单 canvas + 单 renderer + 多模型摆位**（每格一个 renderer 会取景错乱）。

**网格解析器的骨块坑**：`mesh_parse2.parse_mesh2()` 对带骨骼的 `.mesh` 直接抛 `bone_block_layout_unrecognized`。
**通用兜底（非特判）**：跳过骨块、**全文件扫 sub 表**（三重校验 `term==1 && tv==Σvc && tf==Σfc`，不会误判）。
实测 `0059.gpk` 里 **1449/1449 全解得出**。

## 5. 已永久证伪 / 别重做（本轮又撞了一遍的）

- ❌ **拿 murmur3 撞 GPK/WPK 的 16B hash** —— 语义不同（GPK 是内容指纹、WPK 是内容 MD5）。本项目已试 **297,920 组**（seed/目录/命名/扩展名/编码/大小写/分隔符全排列）→ 0
- ❌ **FHPK（`Documents/file_hash_pack.bin`，110 MB）当名字表** —— 里面几乎没有明文路径（前 20 MB 仅 7 条），且其「名字哈希」是 **32 位内容摘要**，与 H16 零交集
- ❌ **盲生成路径变体滚雪球** —— 4,000 万候选只换来 icon 包 +9.5 个点，且 `huanyeshenyu` 仍 0
- ❌ **解压已解出条目再抽引用** —— NPK 里解出的几乎全是 PNG/DDS，二进制内无路径引用（读 800+ MB 只新增 23 条）
- ❌ **`grep -ac` 数二进制** —— 数的是「行」不是「出现次数」，永远假 0；必须 `grep -oa`
- ❌ **shell heredoc 写 Python** —— 反斜杠/引号转义必炸；**一律写 .py 文件再执行**
