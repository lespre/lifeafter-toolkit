### 修复 1：名字表起点被二进制头字段污染

```
材质文件名字表首串 AnimParam 前紧跟一个 u32 LE 头字段（高 3 字节为 0，
低字节在 0x0c~0x41 游走）。低字节 ≥ 0x20（可打印）时会被 [\x20-\x7e]{2,}
并进同一个串 ⇒ 得到 `"AnimParam` `#AnimParam` `!AnimParam` `4AnimParam` `:AnimParam`，
老代码 lstrip('0123456789') 剥不掉 ⇒ 抛「未找到 AnimParam 起点」。

实测：230 个有 AnimParam 的 .c159 里 19 个（8.3%）因此失败。
修法：_norm_run() 剥掉首个 [A-Za-z_] 之前的一切；剥空则保持原样。
```

### 修复 2：`.c159` 是通用容器，不止装材质

```
抽样 1200 个：材质 481（40.1%），其余首标识符是
  AllFiles（场景资源清单）/ NeoX（几何包围盒）/ Lod0..（LOD 表）/
  FileName / GisFiles / CutBones / AnimationEvent（GIS 模型与动画轨）
老代码对它们一律抛「未找到 AnimParam 起点」⇒ 调用方误判解析器坏了。
现由 classify_c159() 先判类型，非材质抛 NotMaterialError(kind)。
★ NotMaterialError 继承 ValueError ⇒ except ValueError 的既有调用方行为不变。
```

### 重构：消重（落实单一来源）

```
c159_slot_parser.read_names_robust() 原先自己重抄一份名字表逻辑绕开 c159_pair 的硬伤；
现改为直接委托 c159_pair.read_names（唯一来源），只补一个 prefix_chars 字段。
```

## 三、我的独立复核（用 9-26 备份当对照）

### ① 回归与修复计数（1,500 抽样）

```
两版都成功            549

```

### ② ★★ 发现它没写清的第三个 bug：comp 列表重复两遍

用 3,263 个文件逐字段比对，`names` **全部**不同。定位到：

```
样本 0000\00006553.c159
  老 comp 184 项   vs   新 comp 92 项      ← 正好一半
  ★ 老的前 92 项 == 新的 92 项            → True
  ★ 老的第 92..184 项 == 前 92 项         → True   ⇒ 后半段是前半段的逐字复制
  老 max_index 183  →  新 max_index 91
  老 full 长度 184  →  新 full 长度 92
```

**⇒ 老代码把名字表【整段扫了两遍】。**
数据里的铁证（老 comp 前 92 项）：
```
... 'Version', '@@', 'b_m_3655001_lod02_opaque', '@@', 'b_m_3655001_lod02_alphatest',
    '@@', 'shader\pbr_default.fx::TShader', 'Effect', 'False' ×4, 'TWO_SIDE_ENABLE'...,
    'character\...atlas_n.tga', '...atlas_d.tga', '...atlas_m.tga'   ← 第一遍到此结束
    ★ 然后一模一样地再来一遍
```
⇒ `@@` 是分割标记，说明名字表结构是 `[组件名…] @@ [材质名…] @@ [shader…] …`，
老的把整段扫了两遍。

### ③ 裁决

```
✅ 新 comp（92）= 正确；老 comp（184）= 重复
✅ 新 max_index（91）才指向正确位置；老的 183 指向列表末尾
   ⇒ 老代码的槽位引用解析可能一直是错的（索引偏一倍）
⇒ 结论：该修复实际修了 3 个 bug（前缀污染 / comp 重复 / 非材质误报），回归 0。
   应保留。
```

**★ 关于它 docstring 写「索引逐位不变」**：那是指「剥前缀不改变条目本身」，
不是说整个列表长度不变 —— 老的重复是另一个既有 bug，新代码顺带修掉了。
**该措辞容易误读，已在本文档澄清。**
