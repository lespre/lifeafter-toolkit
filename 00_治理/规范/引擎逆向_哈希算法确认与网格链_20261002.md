## 一、★★★★★ 引擎自己的名字哈希算法（Fun_021e6d60 内实测）

```c
// FUN_021e6d60 —— 网格/资源加载入口
sVar6 = strlen(param_2);                       // param_2 = 资源逻辑路径
local_48 = 0;
FUN_034631d0(param_2, sVar6 & 0xffffffff, 0x66666666, &local_48);   // ★ murmur3, seed=0x66666666
local_4c = local_48;                           // 第一轮结果
...
local_50 = param_3 & 0xfffffcff;               // ★ flags（参与哈希）
local_48 = 0x77777777;                          // ★ 第二轮 seed
FUN_03463180(&local_48, &local_4c, 4);          // 把第一轮结果喂进去
FUN_03463180(&local_48, &local_50, 4);          // 再把 flags 喂进去
uVar5 = FUN_034631a0(&local_48);                // finalize ⇒ 得到 fid
```

### 结论

```
★ 项目现有实现（toolkit_core/path_fid.py）：
    fid = (murmur3_x86_32(path, 0x77777777) << 32) | murmur3_x86_32(path, 0x66666666)
★ 引擎真身：两个 seed 的 murmur3，第一轮结果 + flags 一起进第二轮，再 finalize
⇒ 【结构一致 ✓ 项目实现是对的 ✓✓】
   原来是纯实测拟合（V2rayN/GPU 哈希对拍得来），现在有【引擎源码级背书】✓✓

★ 新细节（此前未记录）：**flags（param_3 & 0xfffffcff）参与哈希** ✓
   ⇒ 同一路径在不同 flags 下 fid 不同 ✓
   ⇒ 做"名字 → fid"检索时，flags 必须取对（这是历史上"同路径多条目对不上"的一种解释 ✓）
```

## 五、续挖结果（2026-10-02 晚）：父索引 / 蒙皮流【未能落实，如实记录】

### 引擎侧拿到的（内存结构 ✓）

    FUN_020a62d0（"biped" 宿主，5 处 xref，2798 B）反编译：
      骨数       @ obj+0x228   （u16）
      父索引数组  @ obj+0x22a   （每骨 1 字节 u8）
      骨名表     @ obj+0x330   （每项 32 字节定长，名字形如 "biped head"）

⇒ 这三条【与项目解析器一致】✓✓：
  mesh_parse2.py docstring 写「骨名定长 32B 步进」✓、n_bones = u16 @ offset 8 ✓
  ⇒ 解析器的骨骼块部分【被引擎背书】✓✓
⇒ 唯一未实现的 = 父索引数组（项目只读骨名，不读父子关系）

### 验证尝试（两轮，均【不成立】✗）

    第 1 轮（弱判据 → 假阳性 ✗，已自纠）：
      乱扫骨名块附近找 u8 数组，判据 = max < n 且 父 < 自身
      ⇒ 160/160 "命中" —— 但【全零数组天然满足】⇒ 那是零字节段落 ✗ 采信无效

    第 2 轮（硬判据）：
      判据 = 非全零 · 不同值 >= 3 · 拓扑序 >= n-1 · 值域 < n
      假设位置 = 骨名块【之前 n 字节】（按引擎字段顺序 0x228 → 0x22a 推）
      备选位置 = 骨名块【之后】
      ⇒ 565 个可解析骨块的网格，全【未命中】✗

### 结论

    ✗ 引擎的【内存结构偏移】≠【文件布局】—— 不能由 0x228/0x22a 直接推文件位置
    ✗ 父索引在文件里的位置【未定证】⇒ 【不改代码】✓（宁缺勿猜）
    ★ 但这一轮不是白跑：
      ① 骨骼块参数（32B 定长 / u16 骨数）被引擎确认 ⇒ 现有解析器获得源码级背书 ✓
      ② 又一次实证「弱判据会产生假阳性」⇒ 判据必须非平凡（防全零 / 防常量）✓

## 六、★ 战略结论：exe 的问题一律先查 APK 的 .so（2026-10-02）

### 实测证据（APK libclient.so x86_64，未加密）

    PLATFORM_WIN32                       x5     <- Windows 平台分支在
    d3d11 / report_d3d11_live_device_objects     <- D3D11 渲染后端（PC 专属）
    cef / libcef                         x15    <- CEF 内嵌浏览器（PC 专属）
    Windows x44 · WIN32 x5 · win32 x12
    android x76 · ios x101                       <- 同时含移动分支

⇒ 这是【多平台引擎二进制】：Windows / Android / iOS 三个分支都在同一份 .so 里

### 含义

    能：同一套引擎逻辑从 .so 里读 —— 含 PC 专属子系统（D3D11 / CEF）
        今天已实证 4 次：bindict 格式 / 容器头 / 补丁系统配置 / 渲染规则 / 哈希
    不能：字面还原 lifeafter.exe 文件（自研壳 + VMProtect，且非必要）
    拿不到：Windows 启动器生态（launcher / 渠道 SDK）—— 非游戏逻辑
            exe 链接的第三方 DLL 内部 —— 非必要

### 以后的做法（硬规矩）

    凡"必须拆 exe 才能知道"的问题 => 一律先查 .so
      exe = 壳（静态不可行 / 动态是反作弊红线）
      .so = 同一套引擎的裸体（节名 XOR 0xBB 一解即得）
