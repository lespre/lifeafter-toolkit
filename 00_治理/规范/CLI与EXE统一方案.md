## 一、为什么现在就要处理（不是为了 EXE）

勘查发现四个硬伤，**它们本身就是 bug/技术债，EXE 只是让它们更致命**：

| # | 硬伤 | 位置 | 后果 |
|---|---|---|---|
| 1 | **`PROJECT_ROOT` 硬编码绝对路径** | `toolkit_core/paths.py:9` `Path(r"E:/la拆包项目")` | 它是**唯一单点**（`OUTPUT_ROOT`/`INDEX_ROOT` 都基于它）。项目搬家 / 换机 / EXE 分发 → 全废 |
| 2 | **两套根定位逻辑不一致** | `run_all.py` 用 `Path(__file__).parent/"工具库"`；`paths.py` 用硬编码 | 且 **EXE 打包后 `__file__` 指向 `_MEI` 临时目录** ⇒ 两套都不成立 |
| 3 | **EXE 打的是 GUI 版、无控制台** | `明日之后拆包器_新.spec`：`Analysis(['app.py'])` + `console=False` | 敲不了命令；CLI 没有出口 |
| 4 | **命令定义不是单一来源** | `run_all.py` 手写 9 个子命令 + `toolkit_cli.build_parser()` 各一套 | 改一处行为，另一处的消费方**静默坏掉**（A15 已实证） |

**A15 是活的证据**：把 `index status` 改成默认同步 sidecar，`stdout` 就不再输出 JSON —— 依赖它的主页采集器**不报错、只是全部显示「读取失败」**。

## 二、三个真实案例（行业标准做法）

### Siril（专业天文图像处理）
> 「Siril 有三个界面：GTK 图形界面、无人值守的命令行界面、程序控制的 Python 接口。**它们共用同一个命令系统**。」

```
界面：图形 / 命令行 / Python      ← 三套
命令系统                          ← 一套
```

### VisIt（科学可视化）
> 「GUI 与命令行可以在运行时共享同一个 viewer 组件。敲 `visit` 打开 GUI，敲 `visit -cli` 打开命令行。」

```
同一个 exe：visit → GUI    visit -cli → CLI
```

### M9A（游戏自动化工具，与本项目最像）
> 「三个界面变体……**共用同一套底层系统与资源文件**，区别只在展示层和分发打包方式。」

**共同点：命令定义只有一份，界面/入口是壳。**

## 三、目标架构

```
              ┌──────────────────────────────────────┐
              │  build_parser()     ← 命令定义单点     │
              │  （按三线两带分组）                    │
              └───────────────┬──────────────────────┘
                              │
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
   run_all.py             exe_cli 入口           app.py (GUI)
   开发用                 发布用                 图形壳
   python 直跑            PyInstaller 打包       按钮调同一批函数
```

**三个单点：**

### 单点①：命令定义
- `toolkit_cli.build_parser()` 为唯一来源
- `run_all.py` 改为**调用它**，不再手写子命令
- 将来的 exe 入口、GUI 都调它
- 顺手按**三线两带分组**（CLI 与 exe 同时受益）

### 单点②：路径定位（必须可外部指定）
```
优先级：
  1. 命令行 --root <path>
  2. 环境变量 LA_ROOT
  3. 可执行文件同级向上找项目标记（如 00_治理/索引.md）
  4. 源码树推断（__file__ 向上，仅开发期）
  ⇒ 找不到就明确报错，不猜
```
- `paths.py` 不再硬编码
- **EXE 放哪都能定位项目；项目搬家不用改代码**

### 单点③：依赖分层（EXE 体积的命门）
```
核心命令（index / find / extract / verify）
  ⇒ 只用 stdlib ⇒ EXE 小、启动快

重库命令（glb / tex → numpy / PIL）
  ⇒ 惰性导入（la_glb 已是此样板，照它做）

GUI（PySide6）
  ⇒ 可选打包；不带 GUI 的版本体积显著更小
```

## 四、落地步骤

> **★ 顺序铁律（2026-09-26 用户明示）：先确认没有 bug，再做 CLI。**
> CLI 是壳，底下功能不稳，壳做再好也没用。所以第 1 步之前先插一节「前置」。

### 前置 · ① 线 bug 清零（**做完才轮到下面**）

```
理由：① 解码定位复原线是整个项目的基石，CLI 只是它的壳。
      壳再漂亮，底下算错也是白搭。

做法：
  1. 入口普查 —— 把 ① 线每个命令实跑一遍，记 通过/失败/异常
  2. 逐条修 —— 每条给「现象 / 根因 / 改法 / 验证」
  3. 加测试 —— 把修过的坑固化成测试，防回归
  4. 对标核对 —— 参照成熟项目的做法，看有没有漏的环节
  5. 判定 —— 全绿才算清零；有红就继续修，不往下走

已知待清（本轮已发现）：
  · npk 条目 declared_size 语义随 flag 变 ⇒ 94.88% 误报  ← 已修，待全量验证
  · 没有「按编号/表名查条目」的命令（find 只吃路径）
  · 编号 → 内容的对应不随快照走（跨快照引用会串味）
  · 索引 stale 只比清单指纹，不比单文件 sha256
```

### 第 2 步 · run_all.py 收敛到 build_parser()
### 第 3 步 · build_parser() 按三线三带分组
