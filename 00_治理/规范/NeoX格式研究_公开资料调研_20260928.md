## 0. 结论速览（先看这三条）

1. **新版索引表确实变了，而且有人在 2025~2026 年把它写清楚了。**
   直接可用的实现级资料是 **`MarcosVLl2/NeoXtractor`（2024-11 至今，v3.2 = 2026-06-11）**，它的 `core/npk/npk_file.py` 给出了完整头部字段语义：
   `magic / file_count / var1 / encrypt_mode / hash_mode / index_offset`，索引项步长按 **0x1C → 0x20 → 实测推断** 三档判定，索引甚至可以**整体挪到文件尾部**（`var1==1` 时 `seek(-info_size*count, SEEK_END)`）。这解释了为什么老工具（统一按 0x1C / 0x14 读）在《明日之后》上新包直接失败。
2. **增量更新/散文件层有公开证据链，而且和你在客户端看到的 `Documents/res/*.idx + *.wpk` 完全对得上。**
   - 引擎侧：`NXFileSystem::Open` 遍历 FileLoader 取**第一个成功**的 → 散文件(discrete) 优先于 npk（ZhangFengze 2022 逆向 + ZenHAX 2020 游戏日志）。
   - CDN 侧：`h55.update.netease.com/pl/*.plist` 是**完整文件清单（path/size/md5）**（本次实测 147 KB XML，HTTP 200）；每个版本的 CDN 目录下还有 `res.npk.txt` / `res.npk.map` / `res.npk.bin` / `res.skip.txt` 等**配套清单**（本次实测，见 §2.7）。
   - **`.idx + .wpk` 就是 NeoX 3.0 的新容器**：`NeoXtractor` issue #45 标题即 *「Neox 3.0 has discontinued the use of the .npk save file format … They use .wpk and .idx」*（2026-02-13）。格式细节我已从源码逐字段抄出（见 §3.2）。
3. **带完整路径清单的公开数据集：找到了，但不是《明日之后》。**
   `https://h55.gph.netease.com/iosuni_netease_2.90.125221.2268510/res.npk.txt` 是 **73 MB 纯文本**、每行 `<相对路径> <整数×6> 262145 <md5>`（本次实测抓取首 900 字节）。**这是官方自己发布的"名字表"**，可直接构建 路径↔哈希 字典。
   **没有找到**《明日之后》的公开完整路径清单。

## 3. 对你三个问题的直接回答

### 3.1 新版容器索引表布局有何变化？

**结论：头部从"只用 2 个字段"扩成 6 个字段；索引项步长不再固定；索引位置可能整体挪到文件尾部；索引本身可能被加密或携带 NXFN 名称串块。**

**(a) 头部（实抓自 `MarcosVLl2/NeoXtractor/core/npk/npk_file.py::_read_header`，2024-2026）**

| 偏移 | 字段 | 说明 |
|---|---|---|
| 0x00 | magic | `NXPK` = NeoX Package；`EXPK` = 变体（其索引需 `EXPKKeyGenerator` 解密） |
| 0x04 | file_count | u32 条目数 |
| 0x08 | var1 | u32 语义未明；**`var1==1` ⇒ 条目步长 0x20，且索引位于文件尾部** |
| 0x0C | encrypt_mode | u32；取值含 `3`(EggParty 索引加密)、`256`(NXFN 变体) |
| 0x10 | hash_mode | u32；`2` ⇒ NXFN 名称串块；`3` ⇒ 索引整表 ARC4 |
| 0x14 | index_offset | u32 索引表偏移（**老工具只认这一个**） |

> 交叉印证：Dumbrava（2024-11）在 Once Human 上观察到 `0x0D` 位置恒为 `0x01`，并猜是"版本号"。按此布局，`0x0C` 是 `encrypt_mode`、`0x0D` 只是它的第二个字节 ⇒ **`0x01` 更可能是 `hash_mode` 或 `encrypt_mode` 的字节，而不是独立版本号**。（Old QuickBMS/DKDave 脚本完全没读这些字段。）

**(b) 索引项步长（实抓 `_determine_info_size`）**
```python
if self.encrypt_mode == 256 or self.hash_mode == 2:
    return 0x1C       # 28 字节
elif self.var1 == 1:
    return 0x20       # 32 字节
# 否则：用 (文件尾 - index_offset) // file_count 反推
return (index_end - index_start) // self.file_count
```
- 老格式 = **0x1C (28)**（ZhangFengze 2022 / Ekey 2020 / DKDave 2024-01 / 蛋仔派对 2022 三方一致）
- 新增 = **0x20 (32)**（`var1==1`）
- 新版 = **需按包反推**；**NeoXtractor issue #50 上有人实测《明日之后》小包"每条 48 字节（0x30），最后 16 字节固定"**
  → 链接：https://github.com/MarcosVLl2/NeoXtractor/issues/50 `[已打开]`（2026-04-17 建，2026-04-18 更新，**至今 open**）
  → 该 issue 原文：*"The index data seems to be taking up **48 bytes per file, and the last 16 bytes are fixed**. Due to the file encryption, you can't load it directly without decrypting it… Since all data is compressed by zstd, and zstd has a fixed frame header, you can split the data directly"*
  → 仓库作者回复：*"This appears to be an invalid NPK file, either it's a new format that's fully encrypted or it's missing data or it's supposed to be loaded along with other NPK files and so it's missing header information"* ← **"要和别的 NPK 一起加载"= 你的跨包/散文件层问题的旁证**

**(c) 索引块的三种新形态**
- `hash_mode == 2`：索引之后紧跟 **NXFN 块** = 以 `\0` 分隔的字符串序列（`index_offset + file_count*info_size` 处开始），**这就是名字所在**
- `encrypt_mode == 256`：同上，但**再 +16 字节**才到 NXFN
- `hash_mode == 3`：整个索引用 **ARC4** 解密，**密钥硬编码为 `61ea476e-8201-11e5-864b-fcaa147137b7`**（一个 GUID 字符串）
- `encrypt_mode == 3`：EggParty 风格，**按 16 字节块**用 61 项 round-key 表解密（`core/npk/decryption.py::decrypt_eggparty_index`）

**(d) 压缩与加密枚举（实抓 `core/npk/enums.py`）**
- `CompressionType`：`0 NONE / 1 ZLIB / 2 LZ4 / 3 ZSTANDARD`
- `DecryptionType`：`0 NONE / 1 BASIC_XOR（仅前 0x80 字节）/ 2 ADVANCED_XOR / 4 INCREMENTAL_XOR`
- 与 ResHax BMS 时间线对应：**Encryption Mode 3 (2024-05)、Mode 2 (2024-05)、Mode 4 (2024-07)、Compression Mode 3 = zstd (2025-04)**

**(e) 条目内的"再包装层"（issue #46 原文）**
`NONE` / 自定义 LZ4-like / `ROTOR` / `NXS3`，另有 `DTSZ`、`ENON` 头、`COBL` 块（`wpk_file.py` 方法名可见）

### 3.2 多层分包与增量更新机制是怎么设计的？

**(a) 引擎侧的读取优先级（三处独立来源一致）**
1. **2020（ZenHAX，EVE Echoes 运行日志）**：`FileLoader = (opener, loader, root, depth)` 四元组按顺序创建，顺序为
   `os+discrete(@ Documents\res)` → `os+evepatch(@ Documents\0\1)` → `os+discrete(@ res)` → `asset+discrete(@ res)` → `obb+npk(@ res0..res12)` → `obb+discrete(@ res)` → `os+evepatch(@ Documents\0\0)`
2. **2022（ZhangFengze，ARM 端 IDA 分析）**：`NXFileSystem::Open` **遍历 `NXFileLoader`，采用第一个成功读出的结果**；`NXDiscreteFileLoaderCreator`（散文件）**优先**于 `NXNpkLoaderCreator`（npk）——*"优先读取散文件，方便更新与调试，没找到散文件则去资源包读"*
3. **2026（NeoXtractor issue #55）**：IDX 条目可能指向"当前 WPK 集里读不到的数据"，**跨包错配属于已处理状态而非错误**

**(b) 更新下载侧（实测官方 CDN）**
- **入口**：`https://h55.update.netease.com/pl/<渠道>_patch[_gongyan]_release[_force_update]_neox2.plist?r=<N>`
  - 官服：`iosuni_patch_release_force_update_neox2.plist?r=1519`
  - 共研服：`iosuni_patch_neox2_gongyan_release.plist?r=6961`
  - 返回 **`<engine_ver>/<res_ver>/<display_version>` + 全量 `<files><path><size><md5></files>` 列表**（本次实测 147 KB，HTTP 200）
  - → **`res_ver` 即"包体版本"**，用它拼出 CDN 目录：`https://h55.gph.netease.com/iosuni_netease_<res_ver>/<path>`
  - → **客户端"只下载变化部分"的最小实现就是：拉 plist → 与本地 list/version 比对 md5 → 只下差异项。**（这是从 plist 的字段结构直接推出的，**官方未公开文字说明**）
- **散文件明文下发**：plist 里 `res/ar_confs/...`、`res/video/*.mp4|*.srt`、`res/rhythm_game/*.mp4` 等**都是直接的散文件路径**，不是 npk ⇒ 官方确实把"会被频繁更新/单独更新的东西"做成散文件新发。

**(c) `.idx` + `.wpk` 层（新容器，2026 公开）**
**触发点**：`NeoXtractor` issue #45（2026-02-13）：*"Neox 3.0 has discontinued the use of the .npk save file format… Identity V and Onmyoji… use .wpk and .idx. Wpk is a virtual file system, and idx is the system index. There are many wpd file blocks in wpk. The first 136 bytes of the wpd file block are encrypted, and the entire block is compressed."*

**格式（实抓 `core/wpk/constants.py` / `idx_reader.py` / `paths.py` / `slot_file.py`）**

`.idx`：magic **`SKPW`**（= `WPKS` 小端写反）；`0x0C` 处 u32 = 条目数；**头长 `0x20`、记录长 `0x24`(36 字节)**
记录字段：
| 偏移 | 大小 | 含义 |
|---|---|---|
| 0x00 | 16 | **原始哈希（128 位）**，源码里直接 `index.filename = raw_hash.hex()` |
| 0x14 | 1 | `pkg_id` |
| 0x18 | 4 | 载荷偏移 |
| 0x1C | 4 | 载荷长度 |
| 0x20 | 2 | 头部长度（u16）|

`.wpk`：magic **`FKPW`**（= `WPKF`，独立包）；内部块 magic **`1DPW`**（= `WPD1`）；**内嵌块最小头 `0x30` = 48 字节**；*"Embedded entry header size usually stored at **+0x24 (u16)**"* ← **与 issue #50 实测的"48 字节 / 后 16 字节固定"吻合**

**命名规则（实抓 `core/wpk/paths.py`）**：
- `pkg_id ∈ [0, 15]` ⇒ 映射到 **`<stem><pkg_id>.wpk`** 或 **`<stem>_<pkg_id>.wpk`**（正则 `^{stem}_?0*{pkg_id}\.wpk$`，且会扫描目录做全名匹配）
- `pkg_id > 15` ⇒ 判为 **`slot_file`（散槽）**，从目录取；目录名 = **词干去掉末尾数字**（`re.sub(r"\d+$", "", stem)`）
  - 例：`res3.idx` ⇒ 扫 `res/`；条目按 **哈希 hex 文件名** 或 **前缀匹配** 命中
- ⇒ **这直接对应你看到的 `Documents/res/*.idx` + `*.wpk` 结构**：`res*.idx` 是系统索引，`res{0..15}.wpk` 是分包，**其余是 `res/` 目录下的散文件（slot_file）**

**加密（实抓 `core/wpk/decryption.py`）**：
- WPD1 块首部 **AES-ECB** 解密，密钥由 `derive_key(length, t)` 从一个 64 位常量派生出 16 字节（常量形如 `0x7C2E6B6A00000000`、`0x5C74656E00003630` —— 后者的 ASCII 是 `"0l 6.."` 之类，**注意 `0x5C74656E` = `\0\\ten`**）
- 之后是 **偏移相关 XOR**（`xor_offset` 会先把已解出的前段镜像进 XOR 流）和 **线性 XOR**（`xor_linear`，`buf[i] ^= (seed + i) & 0xFF`）
- 与 NetEase DMCA 自述的 *"前 136 字节加密 + 整块压缩"* **方向一致但数字不同**（0x88=136 vs `MIN_EMBEDDED_HEADER_SIZE=0x30=48`），**尚未对齐，需要在我们自己的样本上验**

**(d) 关于 `<家族>.layers.<起始号>.<结束号>.npk` —— 没找到**
本次调研**没有**找到任何公开资料记载 `layers.<start>.<end>` 这种命名规则。
公开资料里出现过的分包命名只有这几类：
- 数字后缀：`res0.npk .. res12.npk`（EVE Echoes）、`res_normal_pack_1.npk .. res_normal_pack_180.npk`（Once Human）、`res.mini.npk`、`chr.mini.npk`
- 语义名 + `.conflict` 后缀：`res/chr.conflict.npk`、`res/scene.conflict.npk`、`res/ui.conflict.npk`、`res/fx.conflict.npk`、`res/effect_cache.conflict.npk`
- 子目录分组：`res\character\players.npk`、`res\scene_bw\bigworld\bg01_content.npk`（《明日之后》）

⇒ **`layers.<a>.<b>` 大概率是《明日之后》自有的分包命名**，要么是较新引入、要么是社区从未公开过。**建议把它当作"我们独有的一手发现"来记录，而不是去找别人的文档。**

## 4. 可参考点 → 我们怎么验证 → 预期结论

> 每条格式：**具体是什么** / **我们怎么验证** / **预期结论**

**R1. `res_ver` + plist 就是增量更新的全貌**
- 是什么：`h55.update.netease.com/pl/*.plist` 返回 `<res_ver>` + 全量 `<files><path><size><md5>`（实测 HTTP 200，147 KB）
- 怎么验证：在《明日之后》客户端目录/配置里找同构的 patch 清单或 version 文件（可能在 `Documents/` 下）；把 PC 端的更新 URL 构造规则与 plist 的 `<path>` 列表比对，看**是否只下载 md5 变化项**
- 预期结论：客户端用"清单比对 md5"做增量；**我们能据此拿到"哪些文件会在热更中被单独替换"的官方名单**，进而区分"稳定包"与"热更散文件"

**R2. `.idx` 就是散文件层的索引，记录 36 字节**
- 是什么：magic `SKPW`、头 0x20、记录 0x24（`[0:16]` 128 位哈希 / `[0x14]` pkg_id / `[0x18:0x1C]` 偏移 / `[0x1C:0x20]` 载荷长 / `[0x20:0x22]` 头长）
- 怎么验证：**先只读文件头 0x20 字节**，确认 `Documents/res/*.idx` 前 4 字节是否为 `SKPW`（`53 4B 50 57`），再核对 0x0C 处的 u32 是否 ≈ 文件大小 / 0x24
- 预期结论：命中 ⇒ **`*.idx` 的 16 字节哈希就是我们的定位键**，且**它比 npk 索引项里的 32 位哈希多 96 位**——这解释了为什么"散文件层能定位到 npk 里定位不到的东西"

**R3. `res.npk.txt` 证明了"名字表是官方外置发布的"**
- 是什么：73 MB 纯文本，`<路径> <整数×6> 262145 <md5>`，按分片一行一条
- 怎么验证：把这套 URL 构造规则套到《明日之后》的 CDN（`h55.gph.netease.com/<渠道>_<res_ver>/`），试探 `res.npk.txt` / `res.npk.map` / `res.npk.bin` / `res.skip.txt` 是否存在（**HEAD 即可，不要下载**）；同时检查本地 `Documents/` 下是否已有同类伴随文件
- 预期结论：**这是把 44.86% 抬上去的最短路径**。若《明日之后》也发布同类文件，名字缺口基本可直接补全；若不发布，则确认"官方只在 IDV/部分手游渠道外置名字表"

**R4. `res.npk.txt` 的哈希字段与 IDX 的 16 字节哈希是否同一函数**
- 是什么：`res.npk.txt` 每行末尾是 32 hex（128 位）；IDX 记录 `[0:16]` 也是 128 位
- 怎么验证：取同一路径在两个文件里的值做比对（**纯文本比对，不涉及本地游戏目录**）；再用 `NeoXtractor/core/npk/npkhash_v1.py` 算出 32 位哈希，看与 128 位值有无前缀/派生关系
- 预期结论：若是同一族 ⇒ **`res.npk.txt` 可直接充当 IDX 的名字表**；若不同 ⇒ 说明存在"索引哈希"与"内容哈希"两套

**R5. 索引项步长必须按包判定，不能全局固定**
- 是什么：`_determine_info_size` 的三分支 + issue #50 实测 0x30
- 怎么验证：对我们 60 个包，**逐个包**统计 `(文件大小 - index_offset) % file_count`，能被 28/32/48 整除的情况分别有多少；同时读 `0x08(var1)`、`0x0C(encrypt_mode)`、`0x10(hash_mode)`
- 预期结论：**预期会出现"一部分包 28、一部分 32、一部分需要反推"**。若整除性不成立，说明这些包的索引被整表加密（对照 `hash_mode==3` / `encrypt_mode==256`）

**R6. 头部第 5/6 字段（`encrypt_mode` / `hash_mode`）我们可能一直在当"保留位"**
- 是什么：`0x0C`/`0x10` 两个 u32；`hash_mode∈{2,3}`、`encrypt_mode∈{3,256}` 有特殊语义
- 怎么验证：**读全部 60 个包的 0x0C/0x10 并做直方图**；把非 0/非 1 的包单独挑出来，看它们的名字覆盖率是否异常
- 预期结论：**如果非零值集中在"名字覆盖率低的包"上，就等于直接定位了缺口的成因**（索引加密 / NXFN 缺失）

**R7. NXFN 串块可能就在索引之后**
- 是什么：`hash_mode==2` 时 NXFN 在 `index_offset + count*size`；`encrypt_mode==256` 时再 +16
- 怎么验证：在我们覆盖率最低的包上，按 `index_offset + file_count*步长` 跳到该位置，读 4 字节看是否 `NXFN`；前后各扫 ±64 字节
- 预期结论：**若命中 ⇒ 这些包的名字一直在文件里，只是我们没按新偏移去读**（这将是一次"48 字节步长 + NXFN 偏移"的组合修正）；若全不命中 ⇒ 这些包确实靠 bindict/哈希树，需要换路线

**R8. 名字不在文本里是设计使然，不是我们方法不对**
- 是什么：ResHax 上 AexaDev 明确说 *"most games just work by cross reference, there is no TOC… the model loader follows a tree structure it starts with a path whose computed hash leads to a buffer with other file references"*；ResHax 905 楼主说 *"npk files don't include file paths"*；`Ekey/LA.NPK.Tool` 覆盖率表里 scene/model 系列结构性为 0
- 怎么验证：把我们的 55.14% 缺口**按包分类**，与 `LA.NPK.Tool` 的 0% 包清单做交集；统计缺口条目是否集中在 scene / scene_bw / model
- 预期结论：**如果交集高度重合 ⇒ 缺口是引擎级设计导致的，应停止"找文本串"，转而做 `<prefix> × <ext变体>` 候选名批量哈希**（照搬 `zed-0xff/nxpk` 的配色方案）；**如果交集很分散 ⇒ 说明我们的问题在索引读取层，回到 R5/R6/R7**

**R9. `npkhash_v1.py` 与 `NpkHash.cs` 可以直接拿来做名字反查**
- 是什么：两套独立的 32 位名字哈希实现（2025 / 2021）
- 怎么验证：用我们已确认的 44.86% 名字 → 哈希，**双向对拍**这两个实现，确认哪个与《明日之后》一致；不一致的话看是否 `hash_mode` 区分（v1 / v2）
- 预期结论：**确定我们该用哪个哈希函数**后，才谈得上按哈希反查名字

**R10. 混合压缩已经存在，遇到"解不开"先怀疑 zstd**
- 是什么：`0 NONE / 1 ZLIB / 2 LZ4 / 3 ZSTD`；ResHax 1066 与 DKDave 脚本分别记录了 zstd 在 2024 出现、2025 才被 QuickBMS 支持；issue #50 用"zstd 定长帧头切分"绕过加密解压
- 怎么验证：统计我们 60 包里的 compression 字段取值分布；对"解出乱码"的条目扫 zstd 魔数 `28 B5 2F FD`
- 预期结论：**若出现非 {0,1,2} 的值 ⇒ 直接确认新版已切到 zstd**，我们的解压链要补 zstd

**R11. 加密模式 4 = INCREMENTAL_XOR，且近两年在加速迭代**
- 是什么：`DecryptionType` 有 `INCREMENTAL_XOR=4`；ResHax BMS 2024-05→2025-04 连续加了 Mode 3 / Mode 2 / Mode 4 / zstd；denpk2 记录 Python 2.7.3→3.11.6、`redirect.nxs` 被移除、opcode 重排
- 怎么验证：统计我们包里的加密模式取值；查是否已有 4
- 预期结论：**能给出我们"卡在哪个版本"的判断**，也说明后续要**定期复查**（引擎迭代速度快于社区文档）

**R12. bindict 是跨引擎共用的（NeoX ↔ Messiah）**
- 是什么：NeoXtractor issue #52：*"NeoX is only tested in Identity V and Seven Days World. Files related to the **Messiah engine** can also be loaded using files. The parser will support them synchronously because **they are the same files**."*
- 怎么验证：把我们的 bindict 解析逻辑与 `core/bindict/{hasher,parser}.py` 做字段级对照
- 预期结论：**若确认同一套 bindict ⇒ 可借 Messiah 引擎的公开研究（`fangfang1984/netease-messiah-tools`、`Aexadev_MESSIAH_extractor`）补齐理解**，这是我们此前完全没考虑过的资源池

**R13. 风险：`.idx/.wpk` 是网易已明确动手的敏感区**
- 是什么：**2025-12-18 NetEase 对 `Ekey/BW.WPK.Tool` 发了 DMCA**（GitHub 451），通知里逐条写明 `*.idx` 依赖、`*.wpk` 解密、`apk\assets\res\*.wpk` 位置、可执行文件名
- 怎么验证：无需技术验证；**只需决策**
