# 拆包链路稳健性修复（robust_bytes）

日期：2026-09-28 ｜ 结果：**pytest 129 passed · CLI 热更测试 377/377 · help 逐字节相同**

---

## 一、为什么做这个

解包链路反复出现同一类 bug：「偶发解不开」「误判成加密」「差几个字节对不齐」。
逐个打补丁治不了根 —— **每个脚本都自己写一遍** zstd 解压、长度读取、路径处理。
这次把这批原语收成唯一实现，并把每个坑钉成断言。

## 二、收录的 6 类坑（都有实测来源）

### 坑① zstandard 参数字数
```
zstandard 0.25 的 decompressobj().decompress() **只收 1 个参数**
传 max_output_size= ⇒ TypeError
后果：实测 11 个 overlay 包【全解失败】（当时的模块一开始就是这么错的）
修：decompress_one() 统一封装，不带该参数
```

### 坑② 帧切分漏帧
```
旧判据：帧前必须有【3 个零】+ zstd 魔数
实测：只有 153/192 个魔数前面是 0（魔数前一字节分布 {0:153, 1:6, 2:3, 63:2, …}）
后果：instance.layers.1.1.1 实际 192 帧，只切出 45 帧
      解出 320,755 B vs 正确 1,365,605 B —— ★ 漏掉 76%
修：所有 zstd 魔数位置都当帧起点；帧尾剥 0 填充
```

### 坑③ 坏帧吞掉部分成功
```
旧实现：某帧失败就 return ⇒ effect 包前 2 帧解得开、第 3 帧坏，结果什么都没留下
修：decompress_zstd_frames() 逐帧解，返回 bad_frames 列表，已解出部分照常返回
```

### 坑④ 变长记录的对齐填充
```
变长记录间常有 0~3 字节填充，[4B 长度] 不在紧邻位置
只读紧邻位置 ⇒ 把天文数字当长度 ⇒ 误判成「加密/损坏」
★ 而且「值在合理区间」不够 —— pad=0 处常撞上看似合理的错值（如 0x7b00 = 31488）
修：find_u32_aligned() 遍历 pad 0..3，并要求 off+pad+4+value 不越出缓冲
    （自检第一版就抓到了这个漏洞）
```

### 坑⑤ 大窗口平均熵误判「加密」
```
★ 本轮最大误判来源：
  明文 marshal 字节码 + 常量池混在一起，16KB 窗口平均熵可达 7.9，与密文无法区分
  我第一次用它判 ⇒ 断言「script 包全加密」
  第二次细看 ⇒ 代表项熵只有 4.0~5.4，中文「小队分数」直接可读
修：looks_encrypted() 改用【小窗口 512B + 取中位数】
    —— 密文每个小窗口都接近满熵；明文总有低熵窗口把中位数拉下来
```

### 坑⑥ 路径/文件名卫生
```
· CRLF 污染：清单文件 \r\n ⇒ basename 把 \r 带进文件名
  ⇒ Windows 上造出看似正常、实际无法按名打开的怪文件
· .sh 里写中文路径会被 mangle ⇒ 下载全失败
· /tmp 在 MSYS 下不通（必须用 $TMPDIR 或项目内路径）
修：safe_stem() / strip_crlf() / iter_lines()（统一 utf-8-sig + 剥 CRLF）
```

```

★ 每条修过的坑都要有对应断言，否则下次还会犯
```
