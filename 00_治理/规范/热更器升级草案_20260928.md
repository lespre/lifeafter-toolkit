### 2.1 数据从哪来（依据，不猜）

| 表 | 它给什么 |
|---|---|
| `huodong_conf_data_chs.py`（含 `oversea/` 变体） | 活动主配置：ID / 时间 / 类型 |

| `gift_data_chs.py` | 礼包 |
| `box_data_chs.py` | 宝箱 |
| `store_v2_data_chs.py` | 商店 |
| `all_huodong_class_data.py` | ★ **活动分类总表（639 个 class）** |

**⇒ 活动 = `huodong_conf_data` 驱动；奖池 = `lottery_*` + `all_huodong_class_data` 交叉。**

### 2.2 奖池解析（最关键的技术点）

现在 `LOTTERY_POOL_RESOLVED_v01.jsonl` 已经解出结构，但它**没回答「本次新增了什么」**。

```
要做的是：
  ① 把 116 MB 产物按【活动 ID】建索引（一次性，之后 O(1) 查）
  ② 用本次热更的 fid diff ∩ 奖池表 → 得出「本次动过的奖池」
  ③ 逐奖池出：奖池名 / 成员清单 / 各档权重 / 保底规则 / 大奖
```

**★ 必须先定的判据**：什么算「新奖池」？
```
候选 A  表里新增的行（fid 新增）        —— 保守，可能漏「改内容的」
候选 B  新增行 ∪ 内容变更（overlay）    —— 完整，但要两路都跑
候选 C  按活动 ID 算「首次出现」        —— 需要跨版本历史，成本高
⇒ 建议 B，和文字表那条判据一致（pkg_N.pi diff ∪ overlay 清单）
```

### 2.3 渲染成什么（交付形态）

**★ 这里要你拍板**，我倾向：

```
方案 甲  一张长图（PNG）—— 活动卡片墙 + 每活动展开的奖池表
         优点：一眼看完，好发人
         缺点：活动多了会很长

方案 乙  一个网页（接进 wiki）—— 可点开单个活动、可筛选、可看 3D
         优点：能交互，能接 3D
         缺点：要开服务（已有 :8765，成本低）

方案 丙  两份都出 —— 长图给「速览」，网页给「细看」
```

### 2.4 活动的 2D 素材从哪来

```
① 活动入口图/横幅：sprite 全量里已有 huodongrukou / huodongyemian / huodongjiangli 等族
② 奖池奖品的图：从奖品 ID → item 表 → icon 路径 → atlas 定位 → 切图
③ 活动专属 spine 动画：ui/spine_new/ 下按活动名分组
```

**★ 判据：一切都从【表里的路径字段】出发**，不扫目录猜（现有 `atlas discover` 是扫目录的，
要补一条「按表里的图路径 → fid → 容器行 → 切图」的正路）。

## 三、目标② 时装 / 武器皮肤：2D 定位 + 3D 渲染

### 3.1 2D 图定位

**两类图，来源不同：**

| 类型 | 在哪 | 定位方式 |
|---|---|---|
| **图标**（小图，列表/背包里看到） | atlas sprite（`ui/item_icon` 等族） | 从表的 `icon_path` 字段 → fid → 容器行 → 切 sprite |
| **立绘**（大图，活动页/详情页） | `gres/0000.gpk` 立绘段（**无名**） | ★ 位置族法（容器+行+尺寸+视觉），名字查不到 |

**★ 已知铁律（踩过两次，写进技能了）**：
```
按名撞库 0 命中 ⇒ 只能推「名字未知」，不能推「资源缺失」。
立绘是【零散插在段里】的（同段 31 行只有 2 张是大立绘）。
```

### 3.2 3D 渲染

**武器皮肤**：`skin3d_pipeline.py` 六步链已跑通
```
皮肤表 → fid → c159 定义帧 → BoundingInfo half → bbox 认领(rel<0.02)

```
⇒ **要做的：从归档区捞回来 + 改成「本次新增」驱动 + 接进交付**

**时装**：比武器复杂（男女两套 × 衣服/头饰/背包多部件）

★ 男女是两套（b_m_ / b_f_）；头饰 model_id 可能与衣服不同
