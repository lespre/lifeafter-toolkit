### ④ `snapshot` 子命令（H-2，接 `patch_snapshot.py`）

```bash
python 01_工具/run_all.py snapshot scan                      # 全量（默认根 E:\mrzh）：见下方实测
python 01_工具/run_all.py snapshot scan --only bin/x64-a50    # 小规模（9 文件 / 2.5 MB / 0.0 s）
python 01_工具/run_all.py snapshot scan --suffix .npk --only Documents
python 01_工具/run_all.py snapshot scan --baseline auto       # 与最近一次【同源根】的基线比
python 01_工具/run_all.py snapshot diff                       # 最近两同源根快照按内容比
python 01_工具/run_all.py snapshot scan --json -              # 纯 JSON 到 stdout（自动静音进度）
```

**实测 1 · 全量真扫（这是「跑一次真实扫描」）**

```
[1/3] 廉价扫（只 stat）…  131 个文件
[2/3] 无基线 ⇒ 全量算哈希：131 个
[3/3] 完成，用时 54.4 秒；不稳定 0 个
[snapshot scan] E:\mrzh → 03_执行\10_索引\patch_snapshots\20260927_220354
  文件 131 个 · 不稳定 0 个 · 用时 54.4s
  落盘：CURRENT_STATE.json · source_lock.json
```
> 131 个容器合计 **70.56 GB**（按后缀：gpk 58 · bin 55 · idx 8 · wpk 8 · npk 2），
> 全部算出 64 位 sha256 ⇒ 实际吞吐 **≈1328 MB/s**。
> **预期耗时结论：本机首次全量 ≈ 1 分钟，不是「几十分钟」**（改动前的估算是按 HDD 口径）。
> 之后每次：见实测 2。

**实测 2 · 二扫（两段式生效）**
```
[2/3] 需重算哈希：0 个（新增 0 · stat 变 0）；其余沿用基线
[3/3] 完成，用时 0.1 秒
  与基线比（按内容）：新增 0 · 消失 0 · 内容变更 0 · 未变 131 ｜ mtime-only 0
  落盘：CURRENT_STATE.json · patch_delta.json · source_lock.json
```
⇒ **全量之后日常扫描 0.1 秒**（只 stat），这正是 H-2 存在的理由。

**实测 3 · 语义（库级 15 项全 ✓，用 scratch 样本，不写 E:\mrzh）**：首扫只收容器后缀 / sha256 全算 /
内容变更被认出 / **仅 mtime 变被单列且不算更新证据** / `stat_changed_but_sha_same` 显式记账 /
新文件算「新增」不算「变更」/ stat 未变的沿用基线哈希不重算 / `CURRENT_STATE` 记 delta 总数 /
写入窗口守卫对静止文件判 `stable` / 与 `source_lock.compare_snapshots` 口径一致。

**实测 4 · 治理边界（硬约束，rc=2）**
```
$ run_all.py snapshot scan --source-root E:/LifeAfter
snapshot scan 拒绝执行：只允许扫 E:\mrzh（体验服）。正式服安装目录 E:\LifeAfter 与其它路径由治理边界禁读…
rc=2      （项目内路径 E:/la拆包项目/03_执行、C:/Users 同样拒绝）
```

**实测 5 · `--json -` 是纯 JSON**：scan 与 diff 均已用 `json.loads()` 验证通过（为此给 `lock()` 加了
`quiet`，否则进度行会混进 stdout）。

**顺带修掉一个自己踩的坑**：`snapshot scan --root` 与全局 `--root`（项目根）**同 dest 冲突**，
会把源根当成项目根去 `set_root()`。已改为 `--source-root`（`--root` 作为别名，dest=source_root），
并在 help 里点明「源根 vs 项目根」。
