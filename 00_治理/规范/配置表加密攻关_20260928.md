## 0. 结论速览

1. **没有加密。** 这批文件是 **NeoX 定制版 `marshal` 序列化出来的 Python `code object`**（不是密文、不是压缩流）。**【实测】**
2. **中文是明文 UTF-8。** `*_chs.py` 里的中文串直接以 UTF-8 存在，可逐字读。**【实测】**
3. 全量导出结果：**334,266 条含中文条目**，全局去重 **224,272 条**；其中活动/时装/抽奖等优先表 **589 张、65,583 条**。**【实测】**
4. 唯一「非标准」的两处：
   - `marshal` 的 **type 字节表被整体换过**（已确认 6 条，见 §5.1）；**【实测】**
   - 底层 **opcode 表被重排**（`RESUME` 落在 0x80 而非 CPython 的 0x97，且末条 `0x12` 在 3.12 里根本不是合法 opcode）。**【实测】**
5. **「UTF-16」这条线是误判，已证伪**（见 §4）：UTF-16LE 解出的 17k 个「汉字」里 **`的` 出现 0 次**、常用字占比 0.7%~10.8%；同一文件按 UTF-8 解出的常用字占比 47%~69%、`的` 出现 13,022 次。典型样本 `desc_info_data_chs.py`。
6. `.nxs` 的中文**不在 `.nxs` 里**——每个 `.nxs` 都有一个同名 `_chs.py` 兄弟文件（如 `monster_area_data_122.nxs` ↔ `monster_area_data_122_chs.py`），中文在该兄弟文件里。**【实测】**
7. `.nxs` 的二进制载荷 **不是加密**，是明文的 IEEE-754 数值表（8 字节块 `9a9999999999a93f`=0.05 重复 60 次、`fa7e6abc7493683f`=0.003 重复 73 次）。**【实测】**
8. **反编译不可行**（两个独立原因，见 §6），但**不需要**——常量里的中文已经全部拿到。

## 1. 文件格式（实测规格）

### 1.1 骨架

以 `double_react_line_group_data_chs.py`（172 B，已 100% 逐字节对齐）为例：

```
0000  73 00 00 00 | 00 00 00 00 | 00 00 00 00 | 01 00 00 00 | 00 00 00 00
      ^^ TYPE_CODE  +---------- 5 x u32 头部 ----------+
0015  fb 0a 00 00 00  80 00 44 00 78 00 44 01 12 00
      ^^ TYPE_STRING(带ref)  len=10   ^^ co_code 10 字节
0024  2e 02                                        <- co_consts = SMALL_TUPLE(2)
0026  7b 14 00 00 00 <20 字节>                      <- consts[0] = bytes 池
003f  78                                           <- consts[1] = NONE
0040  2e 01 d3 0b "string_pool"                     <- co_names = ('string_pool',)
004f  ae 00                                        <- 空 tuple
0051  fb 00 00 00 00                               <- 空 bytes
0056  d3 2d "com\cdata\double_react_line_group_data_chs.py"   <- co_filename
0085  d3 08 "<module>"                             <- co_name
008f  5a 05 00 00 00                               <- co_qualname(ref#5)
0094  01 00 00 00                                  <- co_firstlineno = 1（裸 u32，无 type 字节）
0098  7b 0a 00 00 00 <10 字节>                      <- co_linetable
00a6  5a 03 00 00 00                               <- co_exceptiontable(ref#3)
00ab  <EOF>
```

字段顺序与 CPython 3.11+ **逐字段一致**（`code → consts → names → localsplusnames → localspluskinds → filename → name → qualname → firstlineno → linetable → exceptiontable`），只有 type 字节取值不同。

### 1.2 ★ 字符串池结构（本次的核心突破）

`co_consts[0]` 是一个 `bytes` 对象，内容是一张**扁平字符串池**：

```
[u32 n] [u32 start] [u32 end_0] [u32 end_1] ... [u32 end_{n-1}] [UTF-8 池体]
             ^ 恒为 0        ^ 累积结束偏移（= 前缀和），最后一个 == 池体长度
```

实例（`ab_test_conf_data_chs.py`）：

```
7b 82 00 00 00 | 07 00 00 00 | 00 00 00 00 | 06 00 00 00 0d 00 00 00 17 00 00 00
25 00 00 00 38 00 00 00 4b 00 00 00 5e 00 00 00 | "weight" "is_main" "server_ids" ...
```

- `n = 7`，`end = [6, 13, 23, 37, 56, 75, 94]`，池体长 94 → **自洽**
- 切分后 7/7 段**全部是合法 UTF-8**

**统计自证**（不是猜的）：全量扫描里 `fashion_data_chs.py` 19,594/19,594 段合法、`all_equips_data_chs.py` 11,632/11,632 段合法、`desc_info_data_chs.py` 5,888/5,888 段合法。随机切分不可能做到 100% 合法 UTF-8。

### 1.3 `.nxs` 与 `*_chs.py` 的分工

| 文件 | co_code | co_consts | 中文 |
|---|---|---|---|
| `*_chs.py`（小表） | 10 B（5 条指令） | `(bytes 池, None)` | **在池里，明文 UTF-8** |
| `*.nxs` / `*_data.py` | 230 B（115 条指令） | `(?, None, bytes 大块, …)` 共 6 个 | **不在本文件**，在同名 `_chs.py` |

`.nxs` 的 `co_consts[2]` 是真正的数据表（最大 129 KB），二进制。

`pickle-80 04@2372` 命中只是文件尾部一个巧合字节；`pickle.loads` 全文件/各偏移均失败。

### 3.3 AES / xxtea / rotor —— 排除（4 条独立理由）
1. **长度不对齐**：文件长度 172 / 185 / 214 / 274 …，不是 16 的倍数；
2. **无 IV**：头部 64 字节全为 0 + 类型字节，没有 16 字节随机 IV 区；

4. **小窗口熵 3.4~4.8**，远离密文的 8.0。

### 3.4 关于「NPK AES-128-ECB 密钥」
本次**没有用到、也没有去找**任何 NPK 密钥——因为这些文件根本不需要解密。任务里提到的密钥线索与 `com\cdata\` 下的配置表**无关**。

**判据**：任何真实中文文本（哪怕 200 字）在 3500 常用字表里的占比都在 90% 以上，且 `的` 必然高频出现。UTF-16 解出的「汉字」占比 0.9%~10.8%、`的` 恰好 0 次 —— 这是**随机字节两两配对**落进 CJK 码位（U+4E00–U+9FFF）的统计必然结果，不是文本。

## 5. code object 解析结果

### 5.1 已实测确认的 type 表（6 条）

用「**整个文件必须恰好被消费完**」+ 字段语义做约束，对 `__init__.nxs`(104B)、`ab_test_conf_data_chs.py`(274B)、`double_react_line_group_data_chs.py`(172B)、`monster_script_712_chs.py`(214B) **四个文件同时成立**：

| NeoX 字节 | 语义 | 对照 CPython | 验证方式 |
|---|---|---|---|
| `0x73` | `TYPE_CODE` | `'c'` = 0x63 | 顶层唯一对象，后接 5×u32 + 字段链 |
| `0x7b` | `TYPE_STRING`(bytes, u32 长) | `'s'` = 0x73 | `fb 0a 00 00 00` + 10 字节 = co_code |
| `0x53` | `SHORT_ASCII`(u8 长) | `'z'`/`'Z'` | `d3 2d` + 45 字节 = 文件名（45 = 0x2d ✓） |
| `0x2e` | `SMALL_TUPLE`(u8 元素数) | `')'` = 0x29 | `2e 02` 后正好 2 个对象 |
| `0x78` | `NONE` | `'N'` = 0x4e | consts[1]，0 字节操作数 |
| `0x5a` | `REF`(u32 索引) | `'r'` = 0x72 | 出现的索引值全部 < 已写 ref 数 |
| `0x80` | `FLAG_REF`（与 type 相或） | `0x80` | `0xd3`/`0xfb`/`0xae` 三个带 flag 变体语义自洽 |

**未确认**（诚实标注）：`0x79`（观察到 u8 长度短串，如 `79 13 "FIX Translate Error."`）、`0x00` / `0xbe`（出现在 `_data.py` 的 6 元素 consts 里，未解出语义）。
**方法说明**：曾用「DFS 穷举 type 表 + 要求恰好消费完」的自动求解，在 4 个小文件上能唯一收敛（上表 6 条即由此得出），但在 `ab_test_conf_data.py` 上**出现过假解**（消费完了但语义荒谬，例如 `co_filename` 解析成一个 8 字节整数）。因此本报告**只采信被多文件交叉验证的 6 条**，其余标注未确认，不编造。

### 5.2 Python 版本判定（本机 3.10 / 3.11 / 3.12 三方对拍）

| 版本 | code object 头 | 实测 dump 前缀 |
|---|---|---|
| **3.10** | `e3` + **6×u32(24 B)**，然后 `73 …` | `e3 00…00 | 00 03 00 00 00 **40** 00 00 00 | 73 18 …` |
| **3.11** | `e3` + **5×u32(20 B)**，然后 `f3 …` | `e3 00…00 | 03 00 00 00 00 00 00 00 | **f3** 18 …` |
| **3.12** | `e3` + **5×u32(20 B)**，然后 `f3 …` | `e3 00…00 | 03 00 00 00 00 00 00 00 | **f3** 16 …` |
| **NeoX** | `73` + **5×u32(20 B)**，然后 `fb …` | `73 00…00 | 05 00 00 00 00 00 00 00 | **fb** e6 …` |

结论：
- **排除 ≤ 3.10**（头部是 5×u32，3.10 是 6×u32 且带 `co_flags=0x40`）。**【实测】**
- 字段布局与 **3.11 / 3.12 完全一致**（`co_localsplusnames`/`co_localspluskinds` 两个槽位取代了旧的 `co_varnames`+`co_freevars`+`co_cellvars` 三个槽位，这是 3.11 才有的合并）。**【实测】**
- **倾向 3.11**【推测】：`__init__.nxs` 的 `co_code` 恰好 **3 条指令**（6 字节），与 3.11 的模块形态 `RESUME; LOAD_CONST None; RETURN_VALUE` 吻合；3.12 有 `RETURN_CONST`，同形态只需 2 条。受 opcode 被重排影响，此条只作推测。
- 独立旁证（公开资料）：`hax0r31337/denpk2` 记录 NeoX2 内嵌 Python 从 2.7.3 升到 **3.11.6**，与上述一致。

### 5.3 opcode 表被重排（实测）

| 文件 | co_code | 前 8 条指令 (op,arg) | CPython 3.12 的头部应有 opcode |
|---|---|---|---|
| `__init__.nxs` | 6 B | `80 00 44 00 12 00` | `97 00`(RESUME) |
| `ab_test_conf_data_chs.py` | 10 B | `80 00 44 00 78 00 44 01 12 00` | `97 00`(RESUME) |
| `ab_test_conf_data.py` | 230 B | `80 00 67 00 44 01 6e 00 78 00 4f 00 3f 00 00 00` | `97 00`(RESUME) |
| `monster_data_204.nxs` | 230 B | 同上（**逐字节相同**） | `97 00`(RESUME) |

- CPython 3.12 的 `RESUME = 0x97`，而所有文件首条都是 `0x80` → **opcode 表被换过**；**【实测】**
- `ab_test_conf_data_chs.py` 末条 `0x12` 在 CPython 3.12 的 `dis.opname` 里**根本没有名字**（显示为 `<18>`）→ 再次确认；**【实测】**
- 但**指令是 2 字节定长 + 内联 CACHE**（`co_code` 里 0x00 成串出现，`ab_test_conf_data.py` 里 0x00 占 49/115 条）→ 布局是 3.11+ 风格的。**【实测】**
- `ab_test_conf_data.py` 与 `monster_data_204.nxs` 的 230 字节 `co_code` **完全相同** → 这批表是同一个代码模板批量生成的。**【实测】**

## 6. 反编译可行性 —— 不可行，且不需要

装了 `decompyle3 3.9.3` + `uncompyle6 3.9.3`（+ `xdis 6.1.8`）到项目 venv，做了**对照组实验**：

| 实验 | 结果 |
|---|---|
| 对照组①：真 3.12 pyc → uncompyle6/decompyle3 | ✗ `Unsupported Python version, 3.12.0, for decompilation` |
| 对照组②：真 3.11 pyc → uncompyle6 | ✗ `Unsupported Python version, 3.11, for decompilation` |
| 实验组：`真 magic + NeoX 载荷` 伪 pyc → xdis/uncompyle6 | ✗ `ValueError: bad marshal data (unknown type code)` |
| `marshal.loads(NeoX 文件)` (3.11.8 与 3.12.10 都试) | 返回 `b''` —— **假成功**：`0x73` 在标准 marshal 里是 `TYPE_STRING`，于是把紧跟的 4 字节 `00 00 00 00` 当成长度=0，直接返回空 bytes |
| `marshal.loads(NeoX[21:])` | ✗ `bad marshal data (unknown type code)` |

**双重死路**：
1. 工具层：`uncompyle6`/`decompyle3` 只支持到 3.8，对 3.11/3.12 直接拒绝（这与文件无关，是工具能力上限）；
2. 格式层：type 表被换 → 连 `marshal.load` 都进不去 → 构造不出 code object → 没有任何反编译器能接手。
   即便 type 表全解出来，**opcode 表被重排**（§5.3），`dis`/反编译仍然无法工作。

> `pip install pycdc` 装到的是**同名无关包**（"Please Your Customer Direct Connect"，CRM 工具），已卸载。真正的 `pycdc` 是 C++ 项目（zrax/pycdc），需要 cmake 自行构建，本次**未尝试**。**【未确认】**

> 重要：`marshal.loads` 返回 `b''` 这个坑正是原始 context 里「块数据里 marshal 能读出 1~2 字节的小 bytes 就断了」的真因 —— **不是"读到 1~2 字节就断"，是读到 0 字节然后静默成功**。

## 9. 下一步建议（按性价比排序）

1. **【立刻可用】把导出面扩到全项目。** 本脚本的 `find_pools` 不依赖 `com\cdata` 路径假设，可对整个还原树跑一遍——配置表之外的 `com\lang\*`、`com\ui\*` 里很可能还有大量中文。一行命令即可。
2. **【高价值】补 `.nxs` 的 bindict 解码器。** `.nxs` 的 `co_consts[2]` 是明文数值表（8 字节 IEEE-754 + 整数混排），已有公开线索：`wilson0x4d/once-crunch` 的 `extract-bindicts/decode-bindicts`、`NeoXtractor` 的 `core/bindict/hasher.py`。**中文不缺**（兄弟 `_chs.py` 已给），缺的是**字段名 ↔ 数值的对应关系**（要拿 `_data.py` 里的字段名池去对齐）。
3. **【中价值】补全 type 表。** 用「多文件联合约束 + 拒绝假解」的策略（要求 `co_filename` 等于真实路径、`co_len` 为偶、`co_linetable` 非空），把 `ab_test_conf_data.py` 这类 6-const 文件也约束住，可把 `0x79/0x00/0xbe` 等解出来。**但收益有限**——即使全解完，opcode 被重排仍挡着反编译。
4. **【低价值】opcode 表还原。** 需要拿到同版本 NeoX 的 opcode 表（例如从客户端 `python3x.dll` 的 `_PyOpcode_*` 表里 dump），或用差分（同源码不同版本的 pyc 对比）。**不做也不影响导出中文**。
5. **【纪律提醒】后续不要再用「全文件平均熵」判断这批文件**，用 64 B 窗口中位数；也不要用 `marshal.loads` 单次调用（会静默返回 `b''`）。

## 附：本次修正的既往误判

| 既往说法 | 实测结论 |
|---|---|
| 「`.nxs` 直接扫 UTF-8 中文串 → 0 个，说明加密或非常规压缩」 | 半对：`.nxs` 里确实没有中文，但**原因是中文在配对的 `_chs.py` 里**，不是加密 |
| 「块数据里 marshal 能读出 1~2 字节的小 bytes 就断了」 | **不是断开** —— `0x73` 撞上标准 marshal 的 `TYPE_STRING`，读到长度 0 后**静默成功返回 `b''`** |
| 「明文段与密文段交替出现（分块熵 8.000 / 7.818 …）」 | 高熵段是 `.nxs` 的 **IEEE-754 浮点数值表**（`0000…` / `9a9999999999a93f` / `333333333333f33f` 反复出现），**不是密文** |
| 「中文字符串是 UTF-16LE」 | **证伪**（§4）：常用字占比 0.9%~10.8%、`的`=0 次；UTF-8 解出的是真文本（占比 47%~69%、`的`=13,022 次） |
