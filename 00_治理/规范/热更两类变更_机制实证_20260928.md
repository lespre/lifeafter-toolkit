# ★★ 一次热更有【两类变更】—— 这是「全量定位」的关键机制

日期：2026-09-28 ｜ 状态：**已实证（100% 命中）**

---

## 一、结论先说

```
一次热更的变更分两类，【任何单一数据源都看不全】：

① 新增路径
   · pkg_N.pi diff 抓得到       （本次 23,322 个 fid）
   · 内容落 Documents\gres\0000.gpk（增量包）
   · 实例：ui.* / effect / sound / zhutihuodong_v5

② 内容变更（同路径、内容换）
   · ★ pkg_N.pi diff 【抓不到】 —— fid = murmur3(路径)，路径没变 ⇒ fid 没变
   · 内容落【该族自己的容器】（scene_03 / scene_bw_* …）
   · 实例：res/scene/instance 两个 overlay 包

⇒ 要「全量」，必须：★ overlay 清单（客户端原生）+ pkg_N.pi diff 合起来
   overlay    → 两类都列（权威来源）
   pkg_N.pi   → 只覆盖「新增路径」，补文件级粒度
```

## 三、这解开了两个旧困惑

```
困惑 1：「overlay 覆盖的族 → 新增 fid = 0」是不是 bug？
⇒ 不是。因为 instance 属②类，本就不在「新增」里。

困惑 2：「gres 是重新打包的吗？为什么 88 个块只对上 4 个？」
⇒ 不是重新打包。是【不同 overlay 包落不同容器】：
     ui.* / effect / sound  → 本次增量落 gres\0000.gpk
     scene/instance         → 落 scene 族容器（不是 gres）
   而且我原来的帧切分判据漏了 76% 的帧（见下节）。
```

## 六、加速（本轮新增基建）

```
问题：每次匹配都要重算几十万次 MD5，重复劳动
解法：物化内容指纹索引
    01_工具/工具库/00_共享核心/toolkit_core/content_index.py
      content_hashes(container, row_index, size, md5, mtime)
      · build()       建/补（增量：mtime 没变就跳过）+ 多线程
      · lookup_many() 秒查一批 MD5
      · 尺寸预过滤     只算目标尺寸的行

实测：gres 全量 54,292 行 → ★ 23.2 秒（2,344 行/秒）
      scene 族 866,887 行 → 预过滤到 266,689 行

★ 关于 GPU：对 MD5 无用（torch 无 md5 kernel）。
  只有「解码成图后比像素」这类任务才值得上 GPU。
```
