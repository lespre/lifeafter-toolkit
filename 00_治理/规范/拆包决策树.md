## 一、主决策树

```
你手上拿到什么？
│
├─ A【容器本体】res.npk / res*.gpk / Documents\gres\*.gpk / Documents/script*.npk / *.fpk
│  └─ 目标不是「算它自己的路径」，是「把它登记进索引」
│     ① run_all.py index status   ← 先看闸门（§三 · 异常3）
│     ② run_all.py index build    ← 需要时重建
│     ③ 核对 containers 表：容器名 / rows / status
│     ├─ status != 'ok'  → 只排查这一个容器，【不要重跑全套】
│     └─ 其实我想找「里面的某个东西」  → 转 B / C
│
├─ B【条目坐标】(我有「容器 + 行号」，想知道它是什么) —— 反查
│  └─ sqlite: entries where container=? and row_index=?
│     拿 fid_hex / offset / payload_offset / packed / decoded / flag
│     ├─ 想换回路径文本  → 转 C（登记表）或 D（正向枚举）
│     └─ 只想提取        → run_all.py extract <路径> <输出> --container <C> --row <N>
│
├─ C【一条逻辑路径】(我有路径文本，想找物理位置)  ← 最常用
│  │
│  ├─ C-1 先归类：这条路径属于哪个容器族？
│  │   ├─ 资源族 res.npk / res*.gpk / Documents\gres\*.gpk   → 名字可哈希 ✅ → 转 D
│  │   ├─ 脚本族 Documents/script*.npk                       → 名字不可哈希 ❌ → 转 E
│  │   ├─ FPK 族 *.fpk                                       → 包内条目无路径 ❌ → 转 F
│  │   └─ 旁侧散装 *.idx / *.wpk                             → 转 G
│  │
│  └─ C-2 归类拿不准？（脚本表常长得像资源路径）
│      ├─ 先按资源族试一次：run_all.py find "<路径>"
│      ├─ UNIQUE / AMBIGUOUS  → 它就是资源，走 D ✅（此时 C-1 归错了，以实测为准）
│      └─ MISS (exit 5)       → ★ 不等于「资源不存在」，转 E 查登记表
│
├─ D【资源路径】→ 双 murmur3 → 64 位 fid → sqlite
│   │  路径规范化：" / " → " \ "，latin1 编码，原大小写
│   │  fid = (murmur3(path, 0x77777777) << 32) | murmur3(path, 0x66666666)
│   ├─ 命中 1 条 → 提取
│   ├─ 命中 ≥2 条 → 异常1（多候选）
│   └─ 命中 0 条 → 异常2（0 命中）；确认是脚本族后转 E
│
├─ E【脚本路径】→ 登记表 → entry/file_id → fid → sqlite  ← 【全程不算哈希】
│   │  入口：04_站点/web/data/table_index_entries_<snap8>.jsonl
│   │        table_name == <路径>  →  d['entry'] / d['file_id']
│   │  再用 file_id（不是 entry！）查 sqlite entries.fid_hex
│   ├─ 表里没有这个 table_name → 换另一个快照的 jsonl（见 §二 · E）
│   └─ 有 entry 但 sqlite 查不到 fid  → 换包了：回 §三 · 异常3 核对快照
│
├─ F【FPK】→ fid → fid2info  ← 【包内条目无路径，别去找名字】
│   │  03_执行/10_索引/fpk_fid_index.json → fid2info[fid] = [容器, 行, 偏移, packed, decoded, c1, c2, flag]
│   ├─ 有 fid → 查得到就提取
│   ├─ 没有 fid → 只能反查：cc2fid / c1c2 撞（内容指纹，不是名字哈希）
│   └─ 两条都不通 → 异常2 处理，别猜
│
├─ G【.idx / .wpk 旁侧散装】→ 以 hash16 = 解压内容 MD5 为标识
│   └─ id_locator_index.db → locations where identifier_type='hash16'
│      ├─ 分卷号 255 → 旁侧散装（不在 .wpk 里）
│      └─ 之后接 1DPW→DTSZ→Zstd→DDS 链
│
├─ H【无名条目】编译网格 / 匿名贴图 / 无名字表的容器（如 weapon.gpk）★ 最危险的一支
│  │
│  ├─ H-1 先问：有没有【声明源】能反查？（有声明就不许用 bbox）
│  │   ├─ 装配帧（权威）= Name + BoundingInfo(ctr/dim) + GisFiles + Lods（每部件自己精确的 lod 路径）
│  │   │   → 拿它给的名字，回到 D 用精确路径查
│  │   ├─ .c159 / .sfx / .gim 声明文件 → resolve_declared_paths.py 逐条判 HIT/MISS
│  │   │   → HIT 的条目拿到的就是真路径，回 D
│  │   └─ 声明源存在但某条 MISS → 只说明「按名查不到」，【不等于不存在】
│  │
│  ├─ H-2 没有任何声明源 → 才允许 bbox 认领，且【四条前提必须同时成立】
│  │   ① 关掉候选名变体（不用 --variants / --deep-variants）
│  │   ② 校验魔数（编译网格 34 80 c8 bb）
│  │   ③ 用装配帧声明的 half-extent 比实测网格 bbox（实测精度 rel 0.0005~0.003）
│  │   ④ 只认「装配帧声明 ↔ 实测」的比对，禁按尺寸/顺序/位置猜
│  │   → 四条任一不成立 ⇒ 不许认领，转 H-3
│  │
│  └─ H-3 认领不成立 → 给确定性占位名（path_<id>），登记 unresolved
│       ★ 永不静默丢条目（丢条目 = 数据错误，不是「没找到」）
│
└─ I【声明文件本身】.c159 / .sfx / .gim
    └─ 它常常不是「要找的目标」，而是「路径引用的来源」
       → python <06_皮肤定位链>/resolve_declared_paths.py "*.c159" --json out.json
       （抽 .c159/.sfx/任意文件里的资产路径，逐条判 HIT/MISS + 给目录×扩展名命中矩阵）
```

## 二、分支表（每支：判据 → 命令 → 预期看到什么 → 失败了去哪）

### A · 容器本体

| | |
|---|---|
| 判据 | 文件名以 `.npk` / `.gpk` / `.fpk` 结尾，且它**自己不是条目**（没有外层容器） |
| 命令 | `cd "E:/la拆包项目/01_工具" && python run_all.py index status` |
| 预期 | JSON：`quick_check: "ok"` / `failed_containers: 0` / `stale: false`（exit 0） |
| 失败去哪 | `stale: true` → 异常3；`failed_containers > 0` → 只排查该容器（勿重跑全套） |
| 重建 | `python run_all.py index build`（上次实测 `build_seconds=276.6`；文档口径约 15 分钟，取保守值） |
| 产出去哪 | `03_执行/10_索引/indexes/lifeafter_files.sqlite3` |

**实测容器规模**（sqlite `containers` 表，`status='ok'` 的求和 = 8,160,775 行，与 `meta.row_totals` 一致）：

| kind | 容器数 | 条目行数 |
|---|---|---|
| gpk | 91 | 4,579,792 |
| fpk | 64 | 2,012,297 |
| npk | 158 | 1,568,686 |

### B · 条目坐标 → 反查

| | |
|---|---|
| 判据 | 我有「容器名 + 行号」，想知道它的 fid / 偏移 / 是否可解 |
| 命令 | `SELECT fid_hex, offset, payload_offset, packed, decoded, flag, source FROM entries WHERE container='res.gpk' AND row_index=4501;` |
| 预期 | 一行；`fid_hex` 是 16 位大写十六进制（**跨快照唯一对齐键**），`source` ∈ `gpk-table-8u32` / `npk-table-48b` / `fpk_fid_index` |
| 想换回路径 | → C（登记表 `table_name`）或 D（若可哈希则正向算）或 `asset_path_dictionary.jsonl` |
| 失败去哪 | 查不到行号 → 行号可能来自另一个快照；回 §三 · 异常3 核对快照 |

**实测**：`select ... where container='res.gpk' and row_index=4501` → `D763973EACDC554E`（同 fid 也在 `res.npk` row 14213）。

### C · 逻辑路径 → 先归类，再分流

| | |
|---|---|
| 判据 | 手里是路径文本 |
| 命令 | `python run_all.py find "<路径>"`（`--variants` 展开名变体，`--deep-variants` 再追加 `_lod01/_1/_high` 后缀变体） |
| 预期 | JSON `status` ∈ `UNIQUE` / `AMBIGUOUS` / `MISS`，加 `hits[]` |
| 失败去哪 | `MISS`(exit 5) → **先自证伪**（换斜杠方向、关 variants、核对拼写）；①仍 MISS 且属脚本族 → E ②仍 MISS 且属 FPK → F ③确认路径拼错 → 转 H |

**★ C-2 的判据实测**：同一条命令对两条路径的两种结局

```
python run_all.py find "common\env_map\qiangpi.cube"     → AMBIGUOUS, hit_count=2, exit=0   ← 资源族
python run_all.py find "com\cdata\common_item_data_base.py" → MISS,    hit_count=0, exit=5   ← 脚本族，哈希不成立
```

后者 **exit 5 / MISS 不是「不存在」** —— 它在登记表里有明确登记（见 E）。

### D · 资源路径 → 双 murmur3（首选路线）

| | |
|---|---|
| 判据 | 路径落在 `res.npk` / `res*.gpk` / `Documents\gres\*.gpk` |
| 算法 | `"/" → "\"`，latin1 编码，**保持原大小写**；`fid = (murmur3(path, 0x77777777) << 32) \| murmur3(path, 0x66666666)` |
| 命令 | `python run_all.py find "common\env_map\qiangpi.cube"` |
| 预期 | **1 条 → UNIQUE；≥2 条 → AMBIGUOUS**（同 fid 在多个容器各一份，正常现象） |
| 提取 | `python run_all.py extract "<路径>" "<输出>" --container <C> --row <N>`（多候选**必须**显式指定，否则 exit 6） |
| 失败去哪 | 多候选 → 异常1；0 命中 → 异常2 后转 E |

**实测（qiangpi.cube，同一 fid `D763973EACDC554E` 在两个容器）**

| 容器 | row | offset | payload_offset | packed | decoded | flag | source |
|---|---|---|---|---|---|---|---|
| `res.gpk` | 4501 | 524927644 | **524927680** | 348117 | 524408 | 12 (zstd) | `gpk-table-8u32` |
| `res.npk` | 14213 | 1710400516 | **1710400516** | 446736 | 524408 | 2 (LZ4) | `npk-table-48b` |

> `decoded` 两条都是 524408 ⇒ 同一个资源、两种打包。**gpk 的 `offset ≠ payload_offset`（差 36 B），npk 的相等** —— 提取一律按 `payload_offset`。

### E · 脚本路径 → 登记表（**哈希不成立，唯一入口是登记表**）

| | |
|---|---|
| 判据 | 路径落在 `Documents/script*.npk`（`script.npk` / `script.py3.npk` / `script.py314.lc.npk`） |
| 负结果依据 | 名字哈希对脚本包**不成立**：5184 组变体穷举全不命中（见 `容器与定位.md`） |
| 命令（3 步） | 见下方代码块 |
| 预期 | `table_name` → `entry` + `file_id`；再用 `file_id` 查 sqlite 得到物理容器/行/偏移 |
| 失败去哪 | 表里无该 `table_name` → 换另一个快照的 `table_index_entries_*.jsonl`；有 entry 但 fid 查不到 → 异常3 |

**第 1 步：路径 → entry / file_id**

```python
import json
for line in open(r'E:\la拆包项目\04_站点\web\data\table_index_entries_328b8446.jsonl', encoding='utf-8'):
    d = json.loads(line)
    if d['table_name'] == r'com\cdata\common_item_data_base.py':
        print(d)
```

**实测输出（快照 `328b8446`）**
```
snapshot_id=test-documents-328b8446  client_channel=test
package=Documents/script.py314.lc.npk
entry=19394   file_id=B42760CCA41DBC25
family=common_item_data  role=base  size=1990255  evidence=co_filename
table_body=true  merge_shell=false
```

**第 2 步：file_id → 物理位置**（`file_id` 才是对齐键，`entry` 不是）

```sql
SELECT container, kind, row_index, offset, payload_offset, packed, decoded, flag, source
  FROM entries WHERE fid_hex='B42760CCA41DBC25';
-- 实测: ('Documents\script.py314.lc.npk','npk',19460,149214708,149214708,905648,905648,0,'npk-table-48b')
```

**★ 本支最大的坑：登记表的 `entry` 与物理 `row_index` 是两套编号**

| 快照 / 来源 | entry | file_id | row_index |
|---|---|---|---|
| `test-documents-328b8446`（登记表，27,468 行） | 19394 | B42760CCA41DBC25 | — |
| `test-documents-508bb5bd`（登记表，27,519 行） | 19429 | B42760CCA41DBC25 | — |
| sqlite（物理） | — | B42760CCA41DBC25 | **19460** |

⇒ 同一 FID 在三个快照是三个不同 entry（19394 / 19429 / …）；**任何 entry 必须与 snapshot_id 一起用**。

**交叉核对入口（三者应一致，不一致就是换包了）**
```
① registry/sources.json#table_sources                  logical_path + snapshot_id + FID + entry
② registry/tables.json#snapshot_payload_bindings       entry_index + file_id + declared_size + status
③ registry/payload_maps/<snapshot_id>.json#fid_to_entry fid → entry
   ⚠ payload_map 不是全量路径表：path_to_entry 只在 328b8446 里有，且仅 21,257 条，主表不在其中
```

### F · FPK → fid → fid2info

| | |
|---|---|
| 判据 | 目标在 `*.fpk` 内，或你手上只有一个 fid |
| 硬证据 | `id_locator_index.db` 里 fpk 类 **1,856,043 行全部 `identifier_type` 与 `identifier` = NULL** ⇒ FPK 包内条目**既无路径也无 fid 标识位** |
| 首选查法 | `03_执行/10_索引/fpk_fid_index.json` → `fid2info[fid]` |
| 备选查法 | sqlite `SELECT ... FROM entries WHERE fid_hex='...' AND source='fpk_fid_index'`（索引库已收 2,012,297 行） |
| 预期 | `fid2info` 值 = `[容器, 行, 偏移, packed, decoded, c1, c2, flag]` |
| 失败去哪 | 没有 fid → 用 `cc2fid` / `c1c2` 撞（**内容指纹，不是名字哈希**）；仍不通 → 异常2，别猜 |

**实测**
```
fpk_fid_index.json         253,217,964 B，顶层键 = ['fid2info', 'cc2fid']，fid2info 共 2,069,650 条
'0000528F2893625D' -> ['001.fpk', 0, 106350072, 4798, 5616, 1440785565, 3362934222, 12]
```
⚠ `fpk_fid_index.json` **不含任何 `.gpk`** ⇒ 拿它对 `.gpk` 查出的 0 命中**不能证明不存在**。

### G · .idx / .wpk 旁侧散装

| | |
|---|---|
| 判据 | `.idx` 旁有 `.wpk`（或 `.idx` 内 `pkg = 255`） |
| 标识 | `hash16` = 解压内容 MD5 |
| 命令 | `sqlite3 id_locator_index.db "SELECT * FROM locations WHERE identifier_type='hash16';"`（实测 61,277 行，`kind='idx'`） |
| 预期 | `identifier` 是 16 位十六进制内容 MD5，`pkg` 字段区分分卷 |
| 失败去哪 | `pkg=255` → 旁侧散装，不在 `.wpk` 里；之后接 1DPW→DTSZ→Zstd→DDS 链 |

### H · 无名条目（不许猜的一支）

| | |
|---|---|
| 判据 | 目标所在容器无明文名字表（如 `weapon.gpk` 匿名），或按名查 MISS 但你有证据它就在那里 |
| H-1 命令 | 装配帧 → 取 `Name` / `BoundingInfo(ctr,dim)` / `GisFiles` / `Lods`；声明文件 → `python <06_皮肤定位链>/resolve_declared_paths.py "*.c159" --json out.json`（退出码 0 完成 / 1 参数错 / 2 输入不可读 / 3 写盘失败 / 4 索引不可用） |
| H-1 预期 | 声明里的精确路径逐条判 HIT/MISS；HIT → 回 D |
| H-2 前提 | ① 关变体 ② 校验魔数 `34 80 c8 bb` ③ 装配帧 half-extent vs 实测 bbox（rel 0.0005~0.003） ④ 只认「声明↔实测」比对 |
| H-3 兜底 | 确定性占位名 `path_<id>`，登记 unresolved，**永不静默丢条目** |
| 失败去哪 | 无声明源 → H-2；H-2 四条任一不成立 → H-3 |
| 未验证 | `run_all.py sheet`（装配帧→部件表）**尚未实现**，属 `通用CLI方案.md` §4.1 的设计目标；当前装配帧只能手工/脚本读，别当命令用 |

### I · 声明文件本身

| | |
|---|---|
| 判据 | `.c159` / `.sfx` / `.gim` / `.mat` —— 它们**声明**路径，往往不是要找的终点 |
| 命令 | `python "<06_皮肤定位链>/resolve_declared_paths.py" "*.c159" --no-detail --json out.json` |
| 预期 | HIT/MISS 报告 + 顶层目录×扩展名命中矩阵；`--dump-strings` 只抽路径不解析 |
| 失败去哪 | 全部 MISS → 回 §三 · 异常2；确认是另一族的路径 → 回 C-1 |

## 三、异常分支（三种 + 一种隐性）

### 异常 1 · 多候选（AMBIGUOUS）

```
症状：find 返回 hit_count ≥ 2（同 fid 在多个容器各一份）
工具行为：extract 拒绝自动取第一条 → 打印 AmbiguousMatch → exit 6
命令：python run_all.py extract "<路径>" "<输出>" --container <容器> --row <行号>
预期：exit 0，产物落在输出路径；换 --container/--row 可复现另一份
失败去哪：exit 5（非 AmbiguousMatch 的其他错误）→ 查 IndexNotReady / KeyError / 文件不存在；
          exit 3 → 索引不可用，回 §三 · 异常3
```
> **exit 6 是设计，不是 bug。** 代码在 `toolkit_cli.py:76-77`（`except AmbiguousMatch → return 6`）。禁绕过。

### 异常 2 · 0 命中（MISS / exit 5）

```
症状：find 返回 status=MISS, hit_count=0, exit 5
铁律：★ 禁由「没找到」反推「资源不存在」
处置顺序（自证伪三连）：
  ① 换斜杠方向重试（\ ↔ /）—— 哈希对斜杠方向敏感
  ② 关掉变体重试（去掉 --variants / --deep-variants）
  ③ 核对路径拼写与大小写（哈希保持原大小写）
仍 MISS 则按族转：
  脚本族 → 转 E 查 table_index_entries_<snap8>.jsonl（路径文本必须与表里 table_name 逐字一致）
  FPK    → 转 F（先拿 fid，别找名字）
  其他   → 异常3 核对快照是否换包；确认是本快照的路径且两条路都不通 → H-3 登记 unresolved
```

## 五、「不要做什么」清单

### 已证伪的方法（不许再试）
```
✗ bbox 尺寸匹配认领网格        —— v3~v12 共 10 版全败

```
