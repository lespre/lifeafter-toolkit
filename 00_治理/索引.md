## 二、判定口诀

```
删之前只问两句话：

1. 这是游戏给我的（源包）吗？
   → 是 ⇒ 绝不能删（再热更一次不一定拿得到同一份）

2. 这是我手写的（规范/脚本/页面）吗？
   → 是 ⇒ 不能删（除非已进版本控制）

两个都不是 ⇒ 是产出 ⇒ 能删，用表里的命令重做
```

## 五、健康测试（改完结构必跑）

```
把 04_站点/ 整个删掉（或改名），然后确认：
  01_工具 + 03_执行 是否还能独立工作？

能  ⇒ 结构健康（web 是挂在旁边的壳）
不能 ⇒ 说明拆包逻辑漏进了 web 层，要揪出来
```

依据：AssetRipper 的核心工程里一行 AspNetCore 都没有，桌面壳 `Program.cs` 只有 3 行；
反例 `stable-diffusion-webui` 把 API 和 UI 做成同一个 app，导致「想要 API 就得启整个 UI」。

## 六、写入规则（防止再次变乱）

```
1. 单次 run 的产物只允许写进 03_执行/ 的对应子目录，禁止写回 02_资料/
2. 产出默认拒绝覆盖；覆盖必须是显式开关
3. 日志与失败清单是一等产出，放 03_执行/ 下，带时间戳并轮转（保留 5~10 份）
4. 单层目录文件数超过约 1 万，按名称/hash 前 4 位再分一层
5. 大体积产物（模型/贴图/音频全集）与交付物物理分离，允许指向外部盘
```

出处：FModel 的 `Output/{.data,Backups,Exports,Logs}` 强制分区、AssetRipper 的时间戳子目录与日志轮转、
Unity 文档对 `Library/` 的定义（"disposable, can be regenerated at any time"）。
