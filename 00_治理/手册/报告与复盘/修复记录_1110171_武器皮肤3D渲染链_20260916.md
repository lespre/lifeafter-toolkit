## 二、缺陷 1：空指针导致整链中断（**最严重**）

**症状**：武器渲染为纯黑剪影；`__neox()` 无 `report`；DEBUG_RED 不生效。

**根因**（`weapon_skin_viewer.js` L894）：

```js
if(strictMode && !(albedoOk && (!isWeapon || srcM))){ m=null; state.__strictFailClosed=...; }
//                                                       ↑ 未 continue
...
m.userData.chain={...}   // L938 → TypeError: Cannot read properties of null (reading 'userData')
```

异常自 `applyNeoxManifest` 抛出 → **整条链中止** → 全部 7 个材质保留 GLB 默认黑。
而 L950 的设计意图本是 `m.visible=false`（不绘制）—— **那要求材质对象非空**，所以这是缺陷而非设计。

**证据**（CDP 异常捕获）：
```
TypeError: Cannot read properties of null (reading 'userData')
    at applyNeoxManifest (weapon_skin_viewer.js?v=src50:938:9)
```

**修复**：建占位材质代替 `null`，保留 fail-closed 语义但不再中断整链。

**验证**：
- 修前 `__neox()` → `{"baseColorSRGB":false,"manifest":null}`（无 report）
- 修后 → `{"report":{"applied":7,"applied_prims":[0,1,2,3,4,5,6],"failed":[],"missing":[]}}`

## 三、缺陷 2：manifest weapon 缺 `Tex0`

**根因**：三处代码都要求 weapon 走 `Tex0`
- L795 `colorSlot = isWeapon?'Tex0':'t_basecolor'`
- L849 `REQUIRED = isWeapon ? ['Tex0','ParamMap','NormalMap'] : [...]`
- L862 `albedoSlot = isWeapon ? (g.Tex0||{}) : ...`

但 `neox_material.json` 的 prim0/prim4（weapon）**只有 `t_basecolor`，没有 `Tex0`** → `srcA=null` → fail-closed。
且 `required_by_program_family` 三个族**全部**要求 `Tex0`，manifest 却标 `missing_required: []` —— 自相矛盾。

**修复**：为 prim0 补 `Tex0 = src_tex/012_a.png`、prim4 补 `Tex0 = src_tex/010_a.png`（与本 prim 的 `t_basecolor` 同源文件，依据 viewer 自身「weapon Tex0=001a」口径与 `src_tex/tex0_010.png` 内容副本）。

**验证**：修后 prim0/prim4 `unresolved: []`。

> ⚠️ 未决问题：外审报告 §六.4 实测「Tex0 UV 采样暖金 70.7%」，而 `012_a.png` **金色占比 0.0%**、`012_b_m.png` 为 37.6%。**weapon 的 Tex0 究竟应是 `_a` 还是 `_b_m`，两种证据互相冲突，需用户裁决**（见 §六）。

## 四、缺陷 3：源 IBL 从未被加载（**根因级**）

**根因**（L789-791 + L750-754）：

```js
const mapped = lf ? (lf.indexOf('src_tex/')===0 ? lf : neoxPng(lf)) : null;
function neoxPng(logical){ const m=b.match(/^skin_1003_(\d{3})(?:001)?(a|b_m|n|m|s_m)$/);
                           return m?('src_tex/'+m[1]+'_'+m[2]+'.png'):null; }
```

`t_custom_ibl` 的 `local_file` 是 `src_cube/qiangpi.dds` → 不匹配材质贴图正则 → **恒返回 null**
→ `iblPath=null` → `iblName=null` → `iblCube=null`
→ `envMode` 恒为 `missing_source_ibl`、`envMapIntensity=0`

**这正是外审报告 §六.2「源环境缺失，当前用中性棚光替代」的技术根因** —— 不是资源找不到，而是**解析函数不认 cube 路径**。

**资源实际齐备**：`src_cube/qiangpi.dds`、`car_studio01.dds` 各 524,408 B，六面 ×8 mip 共 96 个 PNG 全部存在且 HTTP 200 可达；lab_src.html L89 的装载路径与 viewer L875 完全一致。

**修复**：cube 槽位直接消费 manifest 的 `local_file`，绕过材质贴图名解析。

**验证**：修后 prim0/prim4 的 `unresolved` 从 `['t_custom_ibl']` 变为 `[]`。

## 六、⚠️ 重要方法论发现：外审报告 §四 的对照测错了对象

`weapon_skin_viewer.js` L1056-1087：

```js
if(!LAB && !callOpts.forceLab){          // 生产模式（无 ?lab=1）
  const SRC={"0":"src_tex/012_a.png", ..., "4":"src_tex/010_a.png", ...};
  obj.material = new MeshBasicMaterial({map:t, toneMapped:false});   // ← 覆盖源链材质
  obj.material.userData.__previewMode='source_texture_preview';
}
```

**生产页（默认 URL）会把 neox 源链材质整体替换为无光照的源贴图预览**，链只在 `?lab=1` 下生效。

而 `neox_final.py` 使用的正是默认 URL（无 `lab=1`）。因此外审报告 §四「当前 strict（逐层校验后）」那一列：

| 指标 | 报告「当前 strict」 | 真实原因 |
|---|---|---|
| 金色 0.0% | 报告解读为「源链输出无金色」 | 实际是 `012_a.png` 未打光预览（该图金色占比 **0.0%**） |
| 蓝紫 67.93% | 同上 | `012_a.png` 均色 [87.8,148.6,254.9]，本身就是蓝紫 |

**结论：报告用「未打光的贴图预览」对比游戏参考图，据此得出「源链数学上不可能出金色」的推论，其前提不成立，需要重做。**
