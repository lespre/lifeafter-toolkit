## 1. 对 v1 三条错误的纠正

### 1.1 「项目内 0 命中」≠「源资源根本不存在」 ❌→✅

v1 写「4 个槽位在项目内**完全没有**源资源」「**客观做不了**」。**这是错的。**

**准确表述**：
> 四个资源在**当前已解出的工作区**和**已验证的 NPK 路径索引**中**尚未定位**；
> 它们仍可能存在于**匿名 GPK、补丁容器或未恢复的目录映射**中。

**反例（本项目自己的历史）**：两个环境 cube（`qiangpi` / `car_studio01`）此前也经历过"全库未找到"，
最后却从 `res.npk` **精确提取**出来了。所以 glob 0 命中**不能**当作"客观不存在"。

**影响**：此项从「不可修复的资源缺失」降级为「**定位任务未完成**」——是一个**可继续推进的工作项**，
而不是终点。这是本次修订中最重要的一条。

### 1.2 参考图口径错，但「我们更亮」同样不成立 ❌→✅

v1 正确发现了「武器区 p95 vs 参考图整帧 p95 不可比」，
但随后推出「**武器区 p95=0.820 已高于参考 0.579，所以我们已经更亮**」——**这个推论同样无效**。

**准确表述**：
> 此前关于偏亮/偏暗的**全部量化结论一律作废**。
> 需要以**同一武器遮罩、同一裁剪、同一颜色空间、同一显示变换**重新测量后，才能重新下结论。

**禁止**：从"不可比"推出任何方向性结论（无论偏亮还是偏暗）。

### 1.3 IBL 旋转与 cube 面朝向**不是死结** ❌→✅

v1 把它写成「两个未知量耦合的死结」。**这也是错的**——它们其实是**两个可以分开的量**：

| 量 | 性质 | 确定方法 |
|---|---|---|
| **DDS/NeoX → WebGL 的固定坐标系转换** | 常量、与材质无关 | **用诊断 cube + 非轴向采样**确定固定基变换 |
| **`u_cube_rotation` 的运行时旋转** | 材质参数 | 在上面的基变换**之上**再叠加 |

**关键认识**：`rot=0` 只表示"在 **NeoX 自己的坐标系**里不额外旋转"，
**不代表 WebGL 里可以直接沿用原方向**。

**方法学禁令**：**不得用"亮度好坏"反推朝向**。
v1 正是这么做的（看到改公式后变暗就想找"补偿角"），这是错误方法。

## 2. `_a` / `_b_m`：**不再是开放问题**

v1 把它列为「待解」并保持了 EMPIRICAL 标注。**这个框架是错的**——它不该靠"A/B 实验哪个好看"或"文件名统一"来判。

**正确判据：按材质槽位 + c159 绑定 + RDEF，而不是按文件名后缀。**

| shader | 后缀 | 角色 |
|---|---|---|
| **crystal** | `_a` | → `t_basecolor` |
| **crystal** | `_b_m` | → `Tex0` |
| **weapon** | `_a` | 可以是该 shader 的 `Tex0` |

**核心认识**：**同一后缀在不同 shader 中可以承担不同角色**，必须以 c159 槽位与 RDEF 绑定为准。

**由此对现状的影响**：
- crystal 的 `_a → t_basecolor` / `_b_m → Tex0` **与规则一致** ✓
- weapon 侧目前绑的是 `_b_m`（标注 `EMPIRICAL`）—— 按本规则，
  **weapon 的 `Tex0` 允许是 `_a`**，即源容器给的结果；`_b_m` 的"经验性"标注需要
  **回到 c159 槽位 + RDEF 重新裁**，而不是继续用渲染观感支撑。

> **待办**：用 c159 的 weapon 材质块（`001265.c159` block0/block4）与 RDEF 资源绑定，
> 把 weapon `Tex0` 的最终归属定下来 —— 这是**可判定**的事，不应再挂着 EMPIRICAL。

## 3. 渲染侧验收（本轮补做）

v1 声称"three.js 侧已基本没问题"。按用户要求补做硬验收，结果如下：

| 验收项 | 结果 | 证据 |
|---|---|---|
| **原 BRDF 完整恢复？** | ✅ **是** | 全文件 `gl_FragColor.rgb =`（整体覆盖）**0 处**；`uAlbedoGain` / `q_envF`（旧的整体替换系数）**0 处** |
| **环境只替换 radiance 输入？** | ⚠️ **生产路径是，但存在第二套违规实现** | 见 §3.1 |
| **crystal roughness 用源通道？** | 🔶 **部分** | 派生贴图 `rough_repack` 的 G ≡ 源 `_a.alpha`（Δ=0，已验证）；晶体公式的 `d` 目前是 `q_mm`（**DetailMap 缺失时的降级分支**，非源公式） |
| **A/B/C 不再出现异常条纹？** | ❓ **未复验** | 本轮未重跑 A/B/C 的三态对照与条纹检查 |
| **7 个 primitive 运行态参数正确？** | ✅ **是** | `__brdfState()` 实测 7/7：`transparent=false / opacity=1 / alphaTest=0 / blending=0`；weapon F0=baseColor(metal)、crystal F0=0.04(dielectric)；真实 lod：weapon 0.26 / crystal 4.22 |

### 3.1 ⚠️ 新发现：仍存在一套 `outgoingLight` 叠加实现

```
行 1553:  'outgoingLight += _env * uIblScale * uIblStrength;'
行 1706:  applySourceEnvBright(mat, idx, callOpts.sourceIblMode);   // 仅当 callOpts.sourceIblEnabled
```

- 这是**旧口径**的实现，**正是用户明令禁止的"对 outgoingLight 额外叠加"**
- 它**没有**被删除，只是靠 `applyMaterialLayers` 的**早退**（`state.neoxReport.applied > 0` 即 return）在生产路径上被绕过
- **风险**：一旦链未能生效（`applied=0` → 走无光照回退预览），这条路径就会激活，
  **环境被计算两次**；且 `__reapplyMaterialLayers` / lab 路径可显式开启它

**结论**：口径的遵守**依赖一个控制流早退，而非代码层面的唯一实现** —— 这**不构成"渲染实现已验收"**。

## 4. 已验证**正确**的部分（请勿从这里查）

这些是程序化实测过的，不是推断：

1. **通道映射闭环**：`param_repack` 的 `G ≡ 源_m.R`、`B ≡ 源_m.G`（1024² 逐像素 `max|Δ|=0`）；
   `rough_repack` 的 `G ≡ 源_a.alpha`（Δ=0）。与源约定「Metallic=ParamMap.y / Roughness=ParamMap.x」

## 6. 参考图问题（比较口径）

- 参考图是游戏**整帧截图**（含 bloom、toneMapping、UI、背景）
- 我们的指标是**纯武器区**（`__primOnly(0) ∪ __primOnly(4)` 与背景帧作差）
- **两者不可比 → 此前所有偏亮/偏暗结论作废**
- **重测要求**：同一武器遮罩、同一裁剪、同一颜色空间、同一显示变换
- 另注：指标对**布局高度敏感**（参数面板行数变化会改变画布尺寸 → 像素类指标整体平移），
  重测时必须**固定画布尺寸**
