## 二、缺陷 15：`u_crystal_metallic` 被误映射到 Three 的 metalness（**我上一轮自己引入的回归**）

**用户反馈**：「把紫色、蓝色也染回去」——晶体呈暗navy，发闷，没有参考图里的亮紫亮蓝。

**根因**：第五轮我把 `u_crystal_metallic`（0.75–1.0）写进了 `m.metalness`。
metalness=1 时 albedo 退出漫反射、外观几乎全由环境反射决定，而环境项被压得很小 → 晶体变暗。

**而这条结论本文件早就写过**（L1295-1301 原文）：

```
// ★ 源结构（pbr_crystal 反汇编 L381-389）：基底色 = t_basecolor 原色参与漫反射着色，
//   u_crystal_metallic(cb0[10].y) 属"晶体层"参数，不等于基底 albedo 的金属度 →
//   不得映射到 Three 的 metalness（映射后 albedo 不参与着色，金色丢失 ✗）。
```

**修复**：晶体 `metalness: 1.0 → 0.0`（按介电处理）；撤销注入里的 `m.metalness = cp.u_crystal_metallic`，
源值改用 `userData.crystal_metallic_source` 记录，语义标 unresolved、不参与渲染。

> 教训：这条坑文档里写着，我还是踩了。**该项目的注释不只是注释，是已验证结论** —— 动手前应先全文检索相关结论。

## 三、缺陷 16：prim6 因 REQUIRED 无条件要求 `t_basecolor` 而整块隐藏

运行时实测（`window.__chainMats()`）显示 prim6：`matVisible=false`、`hasMap=false`、`hasEnv=false`、
无任何注入 —— **材质从未被编译**（不可见 → 不渲染 → `onBeforeCompile` 不触发）。

**根因**：prim6 属 `forward_crystal_roughness_24da` 族，manifest 的 `required_slots`
**没有 `t_basecolor`**；而代码对晶体一律 `REQUIRED=['Tex0','t_basecolor','NormalMap']`
→ `chainOk=false` → `m.visible=false`。

**修复**：REQUIRED 按「该族是否声明 t_basecolor」自适应：
有 → `['Tex0','t_basecolor','NormalMap']`；无 → `['Tex0','NormalMap']`。

## 四、缺陷 17：颜色槽对无 `t_basecolor` 族不适用

```js
const albedoSlot = isWeapon ? (g.Tex0||{}) : (g.t_basecolor||{});   // ← prim6 得到 {}
```
→ `srcA=null` → `albedoOk=false` → fail-closed 占位材质。

**修复**：晶体颜色槽回退 `t_basecolor || Tex0`，并在链上记录实际所用槽位
（`Tex0(fallback: 该族无 t_basecolor)`）。

## 五、⚠️ 我自己的探针 bug（如实披露）

本轮一度得出「晶体注入未生效」的错误结论，原因是 `__chainMats` 检查的字符串是 `q_CrystalMask`，
而注入的 uniform 实际名为 **`uCrystalMask`** —— **查了一个从不存在的名字**，
连续三轮显示 `crystalInj: false`。

期间还误判过一次「字段被遮蔽」（`ud.__frag || ud.__fragCrystal`，`__frag` 恒先命中）。
**两次都是我自己的观测工具错，不是渲染链错。** 修正后确认：注入自第五轮起一直正常工作是。

> 教训：诊断工具本身必须可自证。`__chainMats()` 已加入 `crystalFragSet` / `crystalFragLen` /
> `crystalHasMapAnchor` / `crystalHasDitherAnchor` / `__crystalOBC` 计数器等自证字段。
