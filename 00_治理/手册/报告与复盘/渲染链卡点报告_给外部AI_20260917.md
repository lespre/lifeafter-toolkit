> 禁止调整曝光/灯光/颜色/金属度去凑参考图，缺失数据必须标 `unresolved` 而不能用猜测值填补。

## 2. 渲染链现状（已实现）

| 环节 | 实现 |
|---|---|
| 基色 | `prim0/4` → `src_tex/012_b_m.png`（**经验判定，见 §4.1**）；晶体 → `t_basecolor`=`012_a.png` |
| 粗糙度 | 晶体：`t_basecolor.a`（源公式 `Roughness = t_basecolor.a`）→ 重排为 `rough_repack_*.png` 的 **G 通道**（three 读 `roughnessMap.g`） |
| 金属度 | weapon：`ParamMap` → 重排为 `param_repack_*.png`（three 读 `metalnessMap.b`） |
| 法线 | `NormalMap`；**GLB 无 TANGENT → 运行时用逐三角累加 + Gram-Schmidt 补出顶点切线** |
| 环境 | **覆写 three 的 `getIBLRadiance`**，只产 radiance：<br>`lod = 5.0 + 1.2*log2(max(rough,0.0019))`；<br>方向旋转 → `textureLod(cube)` → RGBM 解码 `L = pow(sm.rgb*sm.a*16, 2)` → `L + uIblMix*(min(L,1.5)*0.299805 - L)` → `* uIblScale` |
| 晶体颜色 | 注入源公式：`mm = saturate(Tex0.r)`；`A = mix(T, T*uc, mm)`；`B = mix(ub, T*uc, d)`；`C = mix(A,B,mm)`，其中 `d = mm`（DetailMap 缺失时的降级） |
| 不透明 | 全部 7 个 prim：`transparent=false; opacity=1; alphaTest=0; blending=NoBlending`，片元强制 `gl_FragColor.a=1.0` |
| 面剔除 | **DoubleSide**（源资产是薄壳；FrontSide 下正对枪管看会"中空透明"） |
| 其它 | `texture.anisotropy = maxAnisotropy`；`renderer.setPixelRatio(min(dpr,2))`；ACESFilmic toneMapping |

**结果**：`__neox()` = `{applied:7, failed:[], missing:[]}`，无 JS 异常、无 shader 编译错误。

## 3. 已验证**正确**的部分（请勿建议从这里查）

这些是**程序化实测**过的，不是推断：

1. **通道映射闭环、无错**
   - `param_repack` 实测：`G ≡ 源 _m.R`、`B ≡ 源 _m.G`（1024² 逐像素 `max|Δ| = 0`）
   - `rough_repack` 实测：`G ≡ 源 _a.alpha`（Δ=0）
   - 与源约定「Metallic = ParamMap.y / Roughness = ParamMap.x」及 three r180 读 `.g/.b` **完全闭环**
2. **`GLSL 保留标识符`（含 `__`）与 `pow` 类型不匹配均已清零**（曾因此导致 9 条 shader error + 252 条 `useProgram: program not valid`，武器完全不绘制；改名后修复）
3. **cube 六面 `flipY`** 由 three 的 `CubeTexture` 构造器强制 false，与 2D 贴图一致
4. **顶点切线实现有效**（GLB 无 TANGENT，补切线后法线细节能量 +4.3%）
5. **manifest 哈希锁全通过**：`neox_material` 31/31、`src_tex_shas` 10/10、`cube_faces` 12/12
6. **死引用 0**：`window.__*` 19 定义 / 8 使用全部有定义

## 4. 卡点（按影响排序）

### 4.1 【数据层】weapon 基色 `_b_m` 在两个源容器里都**没有依据**

- 自解 `001265.c159`：block0/block4 的路径只有 `001a / 001m / 001s_m / 001n / qiangpi.cube`，**没有 `_b_m`**
- `dual.glb` 的 `MAT_w012.baseColorTexture = w012_a`，且 `w012_a` 逐像素等于 `012_a.png`
- **但受控 A/B 实验**（同一套 Three BRDF，只换 weapon 基色贴图）：
  - `_a` 方案：gold **0.0%** / violet **37.02%**
  - `_b_m` 方案：gold **21.47%** / violet **10.53%**
  - 游戏参考图为**金色主体** → `_b_m` 更接近
- **现状**：保留 `_b_m`，但在 manifest 里标 `binding_basis: "EMPIRICAL"`，明确「非 source-derived」

> **待解**：源容器说 `_a`，实验说 `_b_m`。是否说明 `001a` 是**细节/掩码层**而非 albedo？
> 还是 c159 的路径块与 GLB 的材质导出有 one-of 错误？

### 4.2 【数据层】4 个晶体槽位在项目内**完全没有源资源** ★ 最大卡点

| 槽位 | 源 c159 里给的逻辑路径 | 项目内 glob 结果 |
|---|---|---|
| `DetailMap` | `common\textures\crystal_bump_n_uvva.tga` | **0 命中** |
| `t_caustic_tex` | `common\textures\crystal_caustic_uvva.tga` | **0 命中** |
| `t_refraction_tex` | `common\textures\refraction_envmap_3.tga` | **0 命中** |
| `t_reflection_tex` | `common\textures\crystal_reflection_uvva.tga` | **0 命中** |

- 6 个晶体 primitive × 4 槽 = **24 条未绑定记录**（另有 1 条 `<unresolved>`）
- **两份独立审查报告（T1、T4）分别得出同一结论** ✓
- 附带问题：`prim6` 的 `t_caustic_tex` 被绑到了**角色妆容路径** `character\players2021\...\new_tattoo\textures\crystal_caustic.tga`，
  而同文件 block1/2/5 的该位是 `common\textures\crystal_caustic_uvva.tga`，且后者被降格成伪槽位 `<unresolved>`

**替代品实测**（从 GPK 里找到的候选，已重解并保留 alpha）：

| 文件 | 槽位候选 | 真实 alpha std | 能否承担 |
|---|---|---|---|
| `gpk_1229.png` | DetailMap | **0.5**（几乎恒定 255） | ❌ 源公式要 `d = m × DetailMap.a`，alpha 不承载调制 |
| `gpk_1230.png` | t_refraction_tex | **75.0**（有内容） | ✅ 资产合格，但**层公式缺常数**（见 4.4） |
| `gpk_1276.png` | t_caustic_tex | **0.3**（几乎恒定） | ❌ 同 1229 |

### 4.3 【数据层】源 c159 赋值 17 个 uniform，渲染链只复现 **5** 个

未复现的 12 项（`001265.c159` / `001223.c159` 实测）：

```
u_refraction_brightness / _color / _contrast / _rotation   （折射层，4）
u_caustic_brightness / _depth / _tilling                   （焦散层，3）
u_subsurface_color                                          （次表面，1）
u_crystal_specular / u_crystal_metallic                     （2）
u_base_metallic / u_base_specular                           （2，本皮肤未用）
```

其中 **4 项因缺贴图客观不可复现**（对应 §4.2），其余属「公式未恢复」。

### 4.4 【常数层】折射层的两个关键常数**静态不可得**

折射链公式**已从反汇编逐指令复原**：

```asm
480  mad   r6.xz, r8.xxyx, l(0.159155, 0, 0.318310, 0), l(0.5, 0, 0.5, 0)   // 球面等距柱状 UV: 1/(2π), 1/π
481  sample_l(texture2d) r8.xyz, r6.xzxx, t5, s5, cb0[191].z                 // t5=折射图, LOD=u_refraction_mipmap
482  mul   r8.xyw, r8.xyxz, r8.xyxz
483  add   r4.z, r8.z, r8.z
484  mul   r8.xyz, r4.zzzz, r8.xywx                                           // (2z·x², 2z·y², 2x·z²)
485  add   r4.z, cb0[191].y, l(1.0)                                           // contrast
486  add   r4.z, r4.z, cb0[191].y
487  mad_sat r4.z, r8.x, r4.z, -cb0[191].y                                    // sat(x·(2c+1) − c)
488  mul   r4.z, r4.z, cb0[191].w                                             // × brightness
489  mul   r9.xyz, r4.zzzz, cb0[184].xyzx                                     // × u_refraction_color
490  mul   r8.xyz, r8.xyzx, r9.xyzx
491  mul   r8.xyz, r3.wwww, r8.xyzx
492  div   r9.xyz, r8.xyzx, cb1[266].xxxx                                     // ÷ 场景曝光
```

**寄存器映射已交叉验证**（4 条独立对上）：`cb0[191].z`=`u_refraction_mipmap`、`.y`=`u_refraction_contrast`、
`.w`=`u_refraction_brightness`、`cb0[184].xyz`=`u_refraction_color`；`cb0[188].x`=`u_cube_brightness` ✓、
`cb0[187].w`=`u_rotate_angle` ✓（后两条与原报告一致，证明映射可信）。

**卡住的两个量**：
- `u_refraction_mipmap` 的**取值**：7 个 c159 文件全无（该皮肤不覆盖 → 引擎默认值），
  `dxbc_buffer_definitions.json` 135 个条目**全部无 value 字段**
- `cb1[266].x`（场景曝光）：运行时量

> ⚠️ **重要更正**：我此前认为「折射结果进 `o0.w`（alpha）」—— **这是错的**。
> 全量复核：`L492` 除曝光的结果写进 **`r9`**，而 `r9` 在 **`L990/991` 汇入 `o0.xyz`（颜色）**；
> `L992` 的 `dp3_sat luma, r8.xyz` 读的是**未除曝光的 r8**，且我漏了 `L993 × cb0[192].x` 与 `L994 mad_sat(..., r1.w, r6.w)`。
> 即：**折射链影响颜色**，另有一条独立的 alpha 路径。

### 4.5 【朝向层】cube 六面的 D3D↔GL 朝向未知，且与 IBL 旋转耦合

- 六面是 `B8G8R8A8_UNORM 128×128 mips=8` 的 DDS cube，已重解为 `faces/<name>_f{0..5}_m0.png`
- **导出脚本在已知目录树内 0 命中** → 无法核对面索引与 D3D `+X,-X,+Y,-Y,+Z,-Z` 的对应关系
- 项目里有一份 `l3_coord_facemap.json`，但实测**自相矛盾**（blue≠42·i、+X 不在面中心）→ **不得引用**
- **耦合现象**：把 IBL 旋转矩阵从 `x'=Rx·sin+Rz·cos` 改成源式 `x'=cos·Rx+sin·Rz`
  （`rot=0` 时**数学上为单位变换**，已验算）后，画面**变暗**了（p50 0.159→0.122，p95 0.511→0.352）
  → 说明**面序可能一直需要补偿**，或源式的 sincos 目标操作数次序另有解释
- 旁证：`qiangpi` 的 **f3 面 RGBM 解码亮度仅 0.137，而 f1/f2 峰值 226+** → 面朝向对结果影响极大

**未解**：SM4 `sincos` 的目标操作数次序到底哪个是 sin、哪个是 cos？

### 4.6 【显示链】bloom 不可用，且**参考图口径本身没校准**

- 按 `viewer.json` 里项目**自己标定**的 `bloom {strength 0.55, radius 0.55, threshold 0.8}` 启用 `UnrealBloomPass` 后：
  **画面被整体打成全黑**（`canvas.toDataURL` 100% 像素亮度<0.02；CDP 截图 93.7%）
- 隔离实验：`OutputPass.enabled=false` 仍黑；全部 mesh 隐藏则正常；**把 7 个材质的 `onBeforeCompile` 置空仍黑**
  → 责任在 `UnrealBloomPass` 本身，**不是**注入的 IBL 块
- 机制未取证（**推测**：HDR 极值经 bloom mip 链产生 NaN，`0×NaN=NaN`）
- **更关键**：在**固定布局**下测得的武器区 p95 = **0.820**，而参考图（整帧）p95 = **0.579**
  → **「当前高光偏低、需要 bloom 补」这个前提在武器区口径下不成立**

**参考图比较的根本问题**：参考图是游戏**整帧截图**（含 bloom、toneMapping、UI、背景），
而我们的指标是**纯武器区**；两者口径不同，**此前所有「偏暗/金色不够」的判断都建立在这个不可比之上**。

### 4.7 【语义层】`t_surfacemap` 的语义未赋名

- 它在 manifest 里是 verified 绑定（`012_s_m.png` / `010_s_m.png`），但**渲染链零消费**
- 文件名规则表把它定为 `t_surfacemap`（按 `001s_m.tga` 命名规则，**非着色器证据**）
- 项目自身的 DXBC 实验渲染器记录：**「武器端 `SV_Target3.y` = `t_surfacemap.x`」**
  —— 它写进延迟管线 GBuffer 的一个材质数据通道，**不是能直接乘到 albedo/specular/AO 的常规贴图**
- 实测 `_s_m` 的 **R 通道 99.76% 恒为 255**（几乎无调制信息）

## 5. 我想问外部 AI 的问题

1. **`_a` vs `_b_m` 的冲突怎么判？** 源 c159 与 GLB 都指向 `_a`，但 A/B 实验下 `_a` 渲染出 0% 金色（参考图是金色主体）。
   有没有系统性的方法（而不是再猜一次）来判定「c159 的 001a 到底是 albedo 还是细节层」？

2. **缺失的 4 张源贴图（crystal_bump / crystal_caustic / refraction_envmap_3 / crystal_reflection）** 在 NeoX 里通常承担什么角色？
   它们的**通道约定**（哪个通道是 alpha 调制、哪个是颜色）是什么？有没有公开的 NeoX/同类 PBR 管线命名惯例可参照？

3. **`u_refraction_mipmap` 的默认值**：当材质表不覆盖它时，NeoX 引擎会用什么默认 LOD？
   有没有办法从 shader 的静态信息（cbuffer 声明、默认常量表）反推？

4. **SM4 `sincos dst0, dst1, src`** 的语义到底是 `dst0=sin, dst1=cos` 还是相反？
   （这决定我 IBL 旋转矩阵的写法，目前两版画面差异很大）

5. **D3D 的 DDS cube 六面顺序**（`+X,-X,+Y,-Y,+Z,-Z`）在 three.js `CubeTextureLoader`（`px,nx,py,ny,pz,nz`）里是否**直接对应**？
   若 D3D 是左手系而 GL 右手系，**哪些面需要翻转**（水平/垂直）？

6. **`UnrealBloomPass` 在全黑这件事**：three r180 + SwiftShader 下，什么条件下 bloom 会把整个画面打成黑？
   是否已知与 HDR 输入中的 NaN/Inf 有关？有没有标准的防御写法？

7. **晶体「通透/辉光」感**到底该由哪一环产生？
   已排除：`u_emissive_*`（本皮肤 c159 里**根本没有这些参数**）、折射链（它影响**颜色**）、
   `t_caustic`/`DetailMap` 候选（alpha 恒定）。**剩下最可能是显示链的 bloom** —— 但这个方向被 §4.6 的全黑问题挡住了。
