## 2. 已完全解出的四种容器格式（含精确偏移）

### 2.1 GPK（HPGF 族 = `res\*.gpk`；gres 族 = `Documents\gres\*.gpk`）
- 文件头 16 B：`[0]=0 / [4]=block_count ^ 0x46475049 / [8]=2 / [12]=block_count`（**AES-ECB 加密**）。
- 块 base `B`：`B+4 = entry_count+1`（**真实条目数 = 该值 − 1**）、`B+8 = block_size`（下一块 = `B+block_size`）、**`B+48` 起为 `entry_count × 32 B` 的 AES 表**。
- 行 = `<8I> = (off, comp, dec, c1, c2, flag, hash_lo, hash_hi)`；**载荷 = 块 base + off + 20**（`+20` 处是 20 B 明文头 `(comp, dec, c1, c2, flag)`；`flag=12` 为 zstd）。
- **条目键（"fid"）= `(murmur3_x86_32(path, 0x77777777) << 32) | murmur3_x86_32(path, 0x66666666)`**，`path` 用**反斜杠原样、latin1、大小写敏感**。
- ✅ 该 fid 对 `.gim / .mesh / .mtg / .sfx / .spr / .bin` **按名 100% 命中**（所以名字轴本身是对的）。
- ❌ 对**贴图 `.tga` 名**：在 **4,579,785 行（91 个 GPK）** 里，34 个声明名 **0 命中**。

### 2.2 FPK（NXPK）
- 前 48 B **AES-ECB 解密**后：`[8:12]=='NXPK'`、`u32@12=version(=3)`、`u32@16 = entry_off`、`u32@20 = entry_n`、`u32@24 = n16`。
- **另有 16 B/条的哈希表，位置 = 文件偏移 32 起，共 `entry_n` 条**（本文称之为 **H16**）。
- **条目表在 `entry_off`，整体 AES 加密，每 48 B**：`off=u32@8 / clen=u32@12 / olen=u32@16`；载荷 = `file[off:off+clen]`（`clen!=olen` ⇒ zstd）。
- ❌ H16 **不是** `md5(path)`、**不是** GPK 那套双 murmur3 fid、**不是** `murmur3_x64_128(path)`：用**清单里 2 万个真实路径** ×（原样/小写/反斜杠/去扩展名/3 种编码）标定，**对 2,113,641 个 H16 全 0 命中**。
- ❌ H16 也**不包含**清单的 400,070 个 checksum，也**不包含** 12,987 个已物化资产的 checksum（0/0）。
- ✅ 但**条目载荷**解出来算 md5，**能命中清单 checksum**（见 §3），说明内容确实在里面、只是键对不上。

### 2.3 NPK
- 前 16 B AES；头里 `magic='NXPK'`、`entry_off=u32@16`、`entry_n=u32@20`；条目 48 B 同样 AES 加密。
- ❌ 条目 fid（u64）**不是** `path_id = 双 murmur3`：拿 `script.npk` 里 **65,995 条能还原逻辑路径的条目**做正控 → **0/65,995**；8 组真值 × 9 变换 × 4 编码 × 16,560 候选哈希 → 仍 0。（真值 fid 高 32 位随序号单调增长 ⇒ 更像"全局 ID + 未知哈希"。）
- ❌ NPK 条目载荷 md5 **对 weffect 声明名 0 命中**（817,281 条全解压）。

### 2.4 `.idx` + `.wpk`（转码贴图库；`effect.idx`/`ui.idx`/`model.idx`…）
- `.idx` = `magic 'SKPW' | u32 data_size | u32 ver=1 | u32 count | 16 B 填充` = **32 B 头** + `count × 36 B` 条目 + **4 B 尾**。
  - 条目 = **16 B 键在条目起始** + `u32@20`（低 8 位 = `pkg`）+ `(off, psz, hf)@24/28/32`（`header_size = hf & 0xffff`）。
- **键 = `md5(解码后的载荷)`**（已 875/875、1,031/1,031、1,487/1,487 三次独立自证）。
- `.wpk` = `magic 'FKPW'`，**载荷按 8192 B 块分帧**：每块 = **16 B 键 + 16 B 块头 + 数据**。
- 载荷 = `1DPW` 头 + 加密体；**算符已解**：`tag 0x4341('AC')/0x4350('PC')/0x4358('XC')` + `derive_key(len,t)` 的 **AES-ECB** 解前 `plen` 字节 + 逐字节 XOR 尾 + 前 64 B 反序 XOR `0x5a` + `ENON`/`DTSZ`(zstd) 层 → 明文（DDS/PNG/JPG/TGA）。
- `pkg` 决定文件名：`<family><pkg>.wpk`。**本机只有 `effect3.wpk`**（即本机只物化了 `pkg=3` 的条目）。
- ⚠ **一个关键量级差**：清单里 `effect/` 名字有 **7,506** 条，而本机 `effect.idx` 只有 **1,032（mrzh）/ 1,489（LifeAfter）** 条 ⇒ **绝大多数 effect 贴图在本机根本没有对应条目**（其余在未下载的 `effect<N>.wpk` 里）。

## 5. ★★ 现在可用的**标定数据集**（我认为这是破局关键，也是我最想请 GPT 一起设计实验的地方）

上一轮的扫描产生了一个**前所未有的数据集**：**52,934 个 FPK 命中**里，每一条都同时具备

1. **逻辑路径名**（来自清单，如 `ui/item_icon/icon_366387_1_s.png`）
2. **载荷原始字节的 md5**（= 清单 checksum，已逐条重算断言）
3. **所在容器**、**条目序号 `i`**、**条目表偏移 `entry_off + i*48` 的 48 字节明文**（AES 已解）
4. **同序号在 H16 表里的 16 字节值**：`file[32 + i*16 : 32 + i*16 + 16]`

⇒ **这等于给了 5 万组 `(路径, 16B 键)` 真值对**，而在此之前我们只有哈希猜测。

**可做的实验（请 GPT 给出优先级与数学思路）：**
- **E1｜判定 H16 依赖什么**：H16 是否与"路径"相关？（用同一路径在**不同容器**里的 H16 是否相同；用**不同路径、相同内容**的两条是否 H16 相同。）
- **E2｜若是路径哈希，反推算法**：5 万组真值下，逐字节验证常见 128 位/64 位哈希（xxHash64/xxh3-128、CityHash、SpookyHash、FarmHash、MurmurHash3 各变体、CRC64、SipHash、FNV、以及"两次不同 seed 的 32 位哈希拼接"）以及**带 salt / 带规范化（小写、反斜杠、去扩展名、前缀 `res/`、UTF-16）**的组合。给出可判别的特征（例如 5 万组中**碰撞数**、值域分布、是否随条目序号单调 ⇒ 更像 ID 而非哈希）。
- **E3｜若是内容哈希**：H16 是否等于**载荷字节**的某种哈希（我们已知它不是 md5；试 xxh3-128 / md5(AES(...)) / 双 xxh64 等）。
- **E4｜是否与"容器内偏移/索引"有关**：H16 与 `i`、`off`、`clen` 是否有确定性关系（回归/模运算/线性同余）。
- **E5｜若 H16 是加密产物**：是否存在 `H16 = AES_ECB_K(md5(path))` 或 `AES_ECB_K(索引)` 之类的构造（同一容器的 H16 表整体是 AES 解出来的，注意区分"表加密"与"键本身加密"）。用 5 万真值做**已知明文攻击可行性判断**（AES 密钥未知，但若 H16 = E_K(known)，则可用真值对构造 64 位/128 位码本，反查我们的 28 个名字）。
- **E6｜反向**：既然 `名字 → 内容 md5` 已知、`内容(md5) → 条目` 已知（扫描得到），那么 **`名字 → 条目` 是已知的**。请判断：**H16 表里是否存在"由条目序号 i 与内容 md5 共同决定"的键**（我们已经能把 5 万组 `(i, md5(载荷), H16[i])` 全部列出来）。
- **E7｜另一条完全不同的路**：本机 `effect.idx`/`effect3.wpk` 只有 1,487 条，而清单 `effect/` 有 7,506 条。请判断是否存在"**转码表**"（源 `名字.tga` → 转码后 DDS 键）——我们已确认 idx 键 = `md5(DDS 载荷) ≠ md5(源 tga)`。若存在这种表，它**最可能长什么样、藏在哪**（是否可能就在 `res.npk` 的其它条目/其它 `.npk` 的载荷里；我们已按"载荷内容包含 checksum 字符串"的思路未做全量，因为载荷共 250 GB 级）。

## 7. 纪律与边界（必须遵守）

- **不许顶替**：不能因为"看起来像"就把某张匿名 DDS 当成某个名字的贴图；证据不足就保持 `unresolved`。
