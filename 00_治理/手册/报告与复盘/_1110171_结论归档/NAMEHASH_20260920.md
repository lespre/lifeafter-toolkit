# NAMEHASH 调查报告 —— `file_hash_pack.bin`（FHPK v2）与「名字哈希」机制

- 日期：2026-09-20
- 作用域：只读游戏数据与既有产物；写入仅限本目录
- 验证黄金集合：`03拆包产物/_target_1110171/h16/truth_pairs.json`（51,893 条）
- 结论一句话：**`file_hash_pack.bin` 的「名字哈希」是一个 32 位内容摘要（每文件，与路径/文件名无关），而 H16 是 128 位且无零填充；两者零交集 ⇒ 这套机制不能把 `effect\textures\**\*.tga` 映射到包内条目。**

---

## 0. 结论速览（TL;DR）

| 问题 | 结论 | 证据 |
|---|---|---|
| `file_hash_pack.bin` 是什么 | **FHPK v2 明文清单**（启动器自更新清单），条目 = `bin/**` 客户端二进制 + `res/**.npk` 容器名 | 见 §1 |
| 里面有没有 `effect\textures\**\*.tga` | **没有**。`.tga` 出现 **0** 次、`.dds` **0** 次；只有 4~7 处 `effect`，且全是容器名 `res/effect.layers.*.npk`、`res/effect_cache.layers.*.npk` | 见 §2 |

| 能不能用来映射特效贴图 | **不能**（本机现有数据下）。唯一剩下的路见 §5 | 见 §4 |

## 1. `file_hash_pack.bin` 格式判定

### 1.1 头部（两个版本同构）

```
offset  len  field
0x00    4    magic   = 46 48 50 4B  "FHPK"
0x04    4    version = 02 00 00 00  (LE) = 2
0x08    4    count   = 1,528 (LifeAfter) / 1,555 (mrzh)   ← 条目数
0x0C    4    recLen  = 28 00 00 00 (LE) = 40              ← 记录固定字段长度
0x10    ...  记录区开始
```

### 1.2 记录结构（已逐字节验证，跨文件一致）

```
[16 B 摘要][u8 标志][u8 名字长度 L][L B 路径(ASCII, 反斜杠/正斜杠混合)][0x00][pad 到 4B][40 B 尾部]
                                                                    ^ 名字长度字节位于 名字起始-2
```

- `u8 名字长度` 恰等于 路径字节数（不含结尾 NUL）。样本：
  - `L=33` → `bin/x64-2/CCGameCaptureHook64.dll`
  - `L=26` → `bin/x64-2/CCMsgSdk.x64.dll`
  - `L=29` → `bin/x64-2/CrashHunter_PC3.dll`
- 40 B 尾部 = 两段各 20 B 的 `(offset, _, size, _, _)` + MD5：
  - 段 A：`u32 offset`，`u32 0`，`u32 size`，`u32 ?`，`u32 0`
  - 段 B：`u32 0`，**16 B 内容 MD5**
- 记录总长 = `2 + L + 1 + pad4 + 40`，实测 delta 与 `L+58` 一致（943 个名字样本，众数 delta = L + 58）。

### 1.4 两版本差异

- 文件大小：`E:\mrzh` = **109,490,519 B**；`E:\LifeAfter` = **109,029,717 B**（差 460,802 B）
- 条目数：**1,555 vs 1,528**（差 27 条）
- md5：`e9d4c12c180644084c3016ab33a99d1b` vs `1362488133ee8e2595c6bdbfa35ca1c3`
- **差异高度局部化**：第一条记录的 16 B 摘要不同（`c1c3 17fc 8ae3 ce9a 53d2 a251 a347 f911 67d4 a7c8` vs `c5 38fc687e69b32fd814c74af01314fb6af757bb`），其后 **路径与尾部 MD5 完全相同**（逐字节 `==`）。即两版本共用同一清单骨架，仅少量条目增删 + 摘要变化。
- 两版本条目集：`bin/` 各 **1,052**（完全相同），`res/` **458 → 480**。

### 1.5 不是压缩/加密

- 无 zstd 魔数 `28 B5 2F FD`、无 lz4 帧魔数；路径与 MD5 明文可读；
- 用既有 `AES_KEY = 606308d8a32c782013d26c2f226f686d` 试解 0x10 起 16 B：未得到 ASCII/结构（不是 NXPK 头）。
- 判定：**FHPK v2 明文自有格式**，非 NPK/FPK。

## 3. 候选算法验证（命中率，分子/分母）

### 3.1 FHPK 摘要 = 32 位值（关键结构事实）

- 1,510 条中 **1,509 条**的 16 B 摘要满足 `bytes[4:] == 0x00 * 12`，即真正的值是 **低 4 B 的 u32**，高 12 B 是零填充。
- **H16 侧：51,637 个 H16 中，高 12 B 为零的 = 0 个**；低 12 B 为零的 = 0 个。
  ⇒ 结构上就不是同一种东西。零填充的 32 位值 × 命中全随机 128 位 H16 的概率 ≈ 0。

### 3.2 对 FHPK (路径, 32 位摘要) 的穷举（分母 = 1,510 条 × 多形式）

算法：`md5 / sha1 / sha256 / mm3_x86_32 / murmur2_32 / xxh32 / xxh64 / fnv1a32 / fnv1_32 / fnv1a64 / fnv1_64 / djb2 / djb2x / sdbm / elf / loselose / java31 / one_at_a_time / crc32 / adler32`

路径形式（每种都试）：`原名 / 反斜杠 / 小写 / 反斜杠小写 / 大写 / 仅 basename / basename 小写 / 去扩展名 / 末尾加 NUL`，编码 `utf-8 / gbk / utf-16le`。

种子：`0, 1, 0x66666666, 0x77777777, 0xFFFFFFFF, 0x9E3779B1, 0x5BD1E995`，以及 0…2^20 全枚举（4 个样本要求 ≥2 命中）。

**结果：0 命中（无任何 ≥2/5 或全量 >5 的组合）。**

### 3.3 摘要到底是什么 —— 已定位为「内容摘要」，不是名字哈希

同一 basename 在不同目录出现时，摘要**随该文件的尾部 MD5 一起变**：

| 路径 | 摘要 | 尾部内容 MD5 |
|---|---|---|
| `bin/x64/CCGameCaptureHook64.dll` | `f44d3636` | `7838e8b51170952f` |
| `bin/x64-3/CCGameCaptureHook64.dll` | `f44d3636` | `4810cf59e77c2612`（≠）|
| `bin/x64-2/CCGameCaptureHook64.dll` | `fc17c3c1` | `543413b8acc047ab` |
| `bin/x64-2/grecord/CCGameCaptureHook64.dll` | `3bf6b488` | `1e7ea66cf5e91552` |

- 134 个 basename 存在 **>1 个摘要**；早期「摘要只取决于 basename」的印象来自**这些同名文件内容恰好相同**的样本。
- 结论：**摘要 ≈ 该文件内容的 32 位摘要/索引**，与名字无因果关系 ⇒ 命名为「名字哈希」是误导，它是**内容轴**。
- `unresolved`：32 位摘要与尾部 MD5 的精确换算（是 MD5 的哪 4 字节 / 哪种折叠，或另一 32 位内容 CRC）未确定；已排除 md5/sha/crc32/adler/fnv/xxh/murmur2/3 的直接取段。

### 3.4 NPK 条目 ID（引擎真实名字哈希）= 64 位，与 H16 无关

公开实现（`Ekey/LA.NPK.Tool` 的 `NpkHash.cs` + `NpkHashList.cs`）给出**引擎真正的名字哈希定义**：

- `MurmurHash3_x86_32(ASCII(path), seed)`；
- NPK 条目 64 位 ID = `mm3(path, 0x77777777) << 32 | mm3(path, 0x66666666)`（`path` 用反斜杠）。

用**真实 NPK 条目表 + 解出的真实逻辑路径**做验证（分母 = 531 条，来源 `E:\LifeAfter\script.npk`，路径从解密条目内 `tI + u32 len + path` 精确取出）：

| 候选 | 命中 / 531 |
|---|---|
| mm3_32 seed∈{0,1,0x66666666,0x77777777,0xFFFFFFFF,0x9E3779B1,0x5BD1E995} × 6 种路径形式 → 高/低 32 位 | **0** |
| mm3pair（含换序、含 4 种字节序）| **0** |
| murmur64A / murmur64B / xxHash64 / CRC64(ECMA/ISO/XZ/WE/Jones) / md5[0:8] / md5[8:16] / sha1[0:8] / mm3_x64_128 | **0** |
| NPK 条目 ID（真实）∩ H16 的任一 8 B 半段（4 种字节序）| **0 / 51,637×4** |
| `path_id(51,893 真值路径)` ∩ 真实 NPK 条目 ID | **0** |

补充事实：`res.npk`(3,114 条)、`ui.npk`(35 条)、`script.npk`(531 条) 的条目 ID **全部严格升序**（`ids == sorted(ids)`），符合「按哈希键排序的表」；`npk_reader.py` 内注释声称 `path_id` 已验证（脚本路径与资源路径均匹配），但**本次用其自身的 531 条 ground truth 复算为 0/531**——该实现或其路径形式与当前游戏版本不符。

### 3.5 H16 相关（复核既有事实，未推翻）

- 对 51,893 真值：`H16 == payload_md5` = **0/51,893**；
- `H16 == md5(path)` / `md5(反斜杠 path)` / `md5(lower)` / `md5(basename)` / `sha1[0:16]` / `sha256[0:16]` / `fnv1a32` 补零 = **全部 0/51,893**；
- 与 §3.4 一致：**H16 既不是路径哈希，也不是内容 MD5**（保持既有结论）。

## 4. 可执行性结论

**不能。** 本机现有数据下，「名字哈希」机制**无法**把 `effect\textures\**\*.tga` 映射到包内条目。

排除依据（逐条可核）：

1. **载体不对**：`file_hash_pack.bin` 只登记 `bin/**`（1,052 条）与 `res/**.npk`（458/480 条容器名），`.tga`/`.dds` 出现 **0** 次；`.npk` 出现 458 次但都是**容器本身**，不是容器内条目。它管的是「启动器自更新完整性」，与包内条目映射无关。
2. **命名空间不相交**：真值路径顶层为 `l10n/ ui/ effect/ model/ …`，FHPK 顶层只有 `bin/ res/`；交集 **0/49,848**。
3. **位宽不对**：FHPK 摘要是 **32 位零填充**（1,509/1,510），H16 是 **128 位无零填充**（51,637 个中 0 个零填充）⇒ 结构上不可能相等。
4. **算法穷举失败**：20 种哈希 × 9 种路径形式 × 3 种编码 × 多种种子（含 2^20 枚举）对 1,510 条 FHPK 对 **0 命中**；12 种 32/64/128 位哈希 × 6 种形式对 531 条真实 NPK 对 **0 命中**。
5. **引擎名字哈希（NPK 64 位 ID）与 H16 无交集**：真实 NPK 条目 ID 与 H16 半段（4 字节序）交集 **0**。

## 5. 唯一的下一步（可执行）

**`enable_namehash_check` 保护的是 NPK 容器的条目名，不是 FPK 的 H16。** 因此正确路线只有一条：

> **拿到装特效贴图的 NPK 容器本体，直接用「真实 64 位条目 ID ↔ 路径」配对反解哈希。**

具体动作：

1. **先确认容器落点**。FHPK 已给出容器名清单：`res/effect.layers.*.npk`、`res/effect_cache.layers.*.npk`（另见 `res/scene_bw/*.npk`、`res/model/*.npk`）。**本机未找到这些 effect NPK**（`E:\LifeAfter` 下只有 `res.npk`、`res\ui.npk`、`script.npk` 存在）。需要从完整客户端或下载源取回这些 NPK。
2. **用 NPK 自带 ground truth 反解**：`script.npk` 已证明可从解密条目内的 `tI + u32len + path` **精确取出真实逻辑路径**（531 条，路径 100% 可读）。对 effect NPK 同样取出 路径 + 64 位 ID 对，即为**真实 (名字 → ID) 表**。
3. **表一旦建立，映射即闭环**：查表得 ID → 在 NPK 条目表中定位 → 拿到载荷；`truth_pairs` 的 H16 轴仍用于 FPK，不需要它来解 NPK 条目。
4. 若目标贴图确实只在 **FPK**（而非 NPK）里，则 §3.5 的穷举已把「H16 由路径决定」这条彻底排除，**不存在**用名字哈希解 FPK 条目的路径——只能继续沿用「载荷 md5 == 构建清单 checksum」这条直证通道。
