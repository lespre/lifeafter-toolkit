## 一、诊断：烂在哪

**现状规模**
```
顶层            10 项（+ 2 个散落文件：08lifeafter wiki构建.txt、09wiki构建.md）
03拆包产物        42 个目录 + 152 个根散落文件（csv/json/md/sh/py 混堆）
08Lifeafter wiki  20 个目录 + 14,923 个文件（含 40+ 个 _ 前缀实验页）
```

**三个根因（不是"文件多"，是"分类维度错了"）**

1. **按主题堆，没按生命周期分** → 可重建的东西（提取产物）和不可重建的东西（交付物、源快照）平级摆着，导致"哪些能删"永远要重新判断。
   - 证据：`indexes/`（基础设施）与 `斩神联动_3D浏览/`（交付物）同级；`_target_1110171/`（证据链）与 `jobs/`（空壳）同级。

2. **没有临时区** → 实验产物就地固化，靠 `_` 前缀自我标记，但从不清理。
   - 证据：`_freeze_v1.2` `_gim_out` `_gpk_extract` `_known_loop` `_sfx_029` `_target_*` 六个；wiki 里 `_3d_open` `_cmp3715*` `_hy_*` `_parts13_*` 等 40+ 个。

3. **没有交付区** → 6 个定版交付物埋在产物堆里，清理时随时可能被误删（本次已人工救回 6 项）。

**附：4 个空壳目录是代码造的，不是人放的**
```
jobs(0) previews(0) logs(9) skin_assets_preview(1)
← 来源：01拆包器本体/工具库/10_应用核心/toolkit_core/paths.py:34
```

## 二、目标架构：按「可重建性」分层

**唯一分层依据 = 删掉之后能不能重建。** 这是能一劳永逸回答"这个能删吗"的唯一稳定标准。

```
E:\la拆包项目\
├── 00_治理/        人的入口：纲要、目标、agent 日志、规范、决策记录
├── 01_工具/        工具本体（对 mrzh 只读）        ← 现 01拆包器本体
├── 02_文档/        方法论/容器格式/异常/能力矩阵/案例复盘 ← 现 02文档索引
├── 03_索引/      ★ 可重建  统一索引 sqlite + 派生索引（mesh/名字库）
├── 04_源快照/    ★★ 不可重建  每次热更一份，只读
├── 05_提取/      ★ 可重建  按需解包产物
├── 06_分析/      ★ 可重建  专题分析产物
├── 07_交付/      ★★ 不可重建 定版交付物
├── 08_wiki/        站点（纯消费者）              ← 现 08Lifeafter wiki
└── 09_临时/      ★ 可随时清空  实验/日志/预览/试跑
```

**三类性质，处理方式完全不同**

| 类 | 目录 | 能删吗 | 清理策略 |
|---|---|---|---|
| 可重建 | 03_索引 / 05_提取 / 06_分析 | 能删（重跑即可） | 按需清；索引可从源重建 |
| **不可重建** | **04_源快照 / 07_交付** | **绝不能删** | 只增不改；纳入备份 |
| 知识 | 00_治理 / 01_工具 / 02_文档 / 08_wiki | 不建议删 | 版本管理 |

**⊘ 被废弃的旧维度**：不再按"皮肤/武器/音频/地图"这类主题分顶层。主题只作为**目录内部的子目录名**。

## 八、为什么这次能一劳永逸

**本次调研的结论（三路独立调研一致）**：成熟项目的目录不是按"装了什么"分的，是按**"删了能不能重来"**分的。
- AssetRipper：`Source/` 下 `IO.Files / Import / Processing / Export.*` —— 阶段即目录
- `arknights-data-pipeline`：`src/`（可重建）+ `SOURCE_STRATEGY.md`（不可重建的源定义）+ `docs/`（知识）
- Ark-Unpacker：`src/`（代码）+ `test/res/`（样本）+ `test/_summary/*.std`（黄金快照）

**落到我们**：`03_索引/05_提取/06_分析` 随便删，`04_源快照/07_交付` 锁死不动，`00/01/02/08` 是知识层。**以后"这个能删吗"这个问题不需要再讨论。**
