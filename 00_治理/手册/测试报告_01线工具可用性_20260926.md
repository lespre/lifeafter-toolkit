## 二、发现的 2 个真 bug（都已修）

### bug 1 ★ `find` / `extract` / `export` 实际不接受 fid

- **现象**：`export <16位hex fid> --out x.csv` → `[export] 既不是存在的文件，索引里也查不到：DA4F8D9D7ED0B47F`
  但该 fid **确实在索引里**（直接从 `entries` 表查得到）。
- **根因**：`unified_index.UnifiedFileIndex.find()` 把输入**一律当逻辑路径**做 path→fid 哈希：
  ```python
  candidates = path_candidates(logical_path, ...)
  for candidate in candidates:
      by_fid.setdefault(f"{path_fid(candidate):016X}", []).append(candidate)
  ```
  传 16 位 hex 会被当成一个**字面路径**哈希成一个毫不相干的 fid ⇒ 永远命中 0。
  而 `--help` 与 docstring 一直承诺「`.bin` 条目载荷，或**逻辑路径 / fid**（经索引提取）」。
- **修法**（严格增量）：`find()` 开头加 fid 直达分支 —— 输入形如 16 位十六进制**且库里确实有这条**才走新分支；否则仍按路径处理。
  ```python
  _FID_RE = re.compile(r"[0-9A-F]{16}")
  raw = (logical_path or "").strip().upper()
  if _FID_RE.fullmatch(raw):
      rows = self.conn.execute("SELECT * FROM entries WHERE fid_hex = ? ...", (raw,)).fetchall()
      if rows:
          return FindResult(logical_path, (raw,), hits)
  ```
- **验证**：`extract <fid>` → exit 0 · 产出 **40,075,316 B**；`export <fid>` → 找到条目、提出表体 **33,894,879 B**；
  路径输入回归 ✓；**84 passed** ✓。

### bug 2 ★ 3D预览器 自 2026-09-21 起就是坏的（缺一个 vendor 文件）

- **现象**：无头 Chrome 实测 `3D预览器/index.html` → `canvas` **不存在**（`canvas-container` 在，但 three.js 没初始化）。
- **根因**：`vendor/three/addons/curves/NURBSUtils.js` **缺失** ⇒ 404。
  依赖链 `index.html → FBXLoader.js → NURBSCurve.js → NURBSUtils.js(缺)` 断 ⇒ 整个 ES module 图加载失败。
  全项目搜 `NURBSUtils.js` **零命中**；两份「搬移前快照」（`95_待清理/待裁决_3D预览器实验资产_A/B`）**也都是 0 个**
  ⇒ **不是搬移丢的，是建 vendor 那天就漏了。**
- **修法**：从官方 `three@0.160.0` 取回该文件（7,861 B），装进两个 addons 目录：
  `vendor/three/addons/curves/` 与 `poster/assets/vendor/three/addons/curves/`。
- **验证**：HTTP 服务日志 `NURBSUtils.js` **404 → 200**；CDP 实测 `canvas=True · canvases=['1118x746']`；
  缺失依赖再扫 **0 处**。

### 载荷解码级补测（`03_执行/90_临时/line1_payload_sweep_20260926/payload_sweep.json`）

**改了什么**：之前只覆盖「最小的 10 个容器」（373,425 条）—— **有偏抽样**，
最大的 `scene_bw_01`(147,402 条)、`effect_01`(214,133 条) 和 `res.gpk` 一条都没摸过。
现在 **60 个容器每个抽 40 条**，取法是容器内按 `row_index` **均匀铺开**（不是随机 ⇒ 可复现、首中尾都摸到）。

**★★ 过程中发现判据本身有洞（已修）**：第一版只对 `flag == 2` 校验长度，
而

```
flag 12 = zstd     1,989,569 条（86.5%）  ← 大头
flag 0  = 原始        274,295 条（11.9%）  decoded == packed，无变换
flag 2  = lz4 block    36,979 条（1.6%）
```

⇒ 只查 flag 2 等于**漏掉 86.5% 的条目**。已改为：**凡 `decoded != packed`（即有变换）就必须长度吻合**。

**结果**：

```
容器覆盖   60 / 60（100.0%）
抽样       2,400 条 → 通过 2,400（100.00%）
全通过容器 60 / 60
零异常 · 零空产出 · 零长度不符
用时 1.3s

抽样 flag 分布 vs 全库占比（证明抽样无偏）：
  flag 12 (zstd)   2,148 条 89.5%   全库 86.5%
  flag 0  (原始)     215 条  9.0%   全库 11.9%
  flag 2  (lz4)       37 条  1.5%   全库  1.6%
```

### 仍未覆盖的（如实标注）

- **仍是抽样**：2,400 / 2,300,843 = **0.10%**。100% 的是**容器覆盖**，不是逐条。
- **`res.gpk` 没做全量 fid 对账** —— 它在 60 容器里被抽到 40 条（✓），
  但「索引里 res.gpk 的每一条 fid 都能在容器哈希表里找到对应」这件事没做过。
  三条 ground truth（`qiangpi.cube` / `car_studio01.cube` / `fashion_qiangpi.cube`）全在它里面。
- ⇒ **「① 线无 bug」的表述应该是**：**入口层、库层、以及 60 容器全覆盖的载荷解码抽样，均已实测可用**；
  逐条全量（2,300,843 条）与 `res.gpk` fid 全对账未做。
