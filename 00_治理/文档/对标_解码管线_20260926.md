### 1. CUE4Parse（Unreal，C#）

- 仓库：<https://github.com/FabianFG/CUE4Parse>（Apache-2.0，593★，master）
- 关键文件：<https://github.com/FabianFG/CUE4Parse/blob/master/CUE4Parse/UE4/Pak/PakFileReader.cs>、<https://github.com/FabianFG/CUE4Parse/blob/master/CUE4Parse/UE4/Pak/Objects/FPakEntry.cs>

**① 索引层**：内存表，非 SQLite。`Mount()` 按版本走三条路：`ReadIndexUpdated`（v10+，PathHashIndex + FullDirectoryIndex）、`ReadFrozenIndex`（v9 frozen）、`ReadIndexLegacy`（v1-9）。产物统一为 `Dictionary<string, GameFile> Files`（`new Dictionary<string, GameFile>(fileCount, pathComparer)`），v10+ 还支持 `FDirectoryIndex` 与 `FlatDirectoryIndex`（magic `0x50464451` = `'PFDQ'`）两种目录索引形态。它**只在挂载时构建一次内存表，不落盘**。（PakFileReader.cs `Mount` / `ReadIndexLegacy` / `ReadIndexUpdated` / `ReadFlatDirectoryIndex`）

**② 定位层**：路径字符串 → 字典查键。v10+ 的 `FDirectoryIndex` 给出 `目录名 → (文件名 → offset)`，其中 offset 可为负：`-offset-1` 索引到「未编码条目表」`NonEncodedEntries`，负索引越界时 `Log.Warning(...); continue;`（跳单条）。**对无名资源：目录索引是强制的** —— 缺 PathHashIndex 直接 `throw new ParserException(primaryIndex, "No path hash index")`，缺目录索引 `throw new ParserException(primaryIndex, "No directory index")`。也就是说它**不支持「只有哈希没有名字」的降级模式**。（PakFileReader.cs）

**③ 解码层**：`CompressionMethod` 枚举（`None/Zlib/Gzip/LZ4/Oodle/... /Unknown`），条目内的压缩方式索引指向 footer 里的 FName 名字表：`CompressionMethod = reader.Info.CompressionMethods[(int)((bitfield >> 23) & 0x3f)]`（`Info.CompressionMethods` 来自 v8+ footer 的 5×32 字符表）。未知方式被**显式建模**为 `CompressionMethod.Unknown`（`compressionMethodIndex == -1 ? CompressionMethod.Unknown : ...`）。解码分发是一个 `switch`（`Decompress(compressed, 0, blockSize, uncompressed, ...)`），无插件机制。加密：`ReadAndDecryptEntryAt(...)`，AES-ECB + `Aes.ALIGN`(16) 对齐。（FPakEntry.cs / PakFileReader.cs）

**④ 校验层**：**不做条目 SHA1 比对**。`FPakEntry` 读到 hash 字段时直接跳过：`Ar.Position += 20; // Hash`。索引侧同样只读不解。→ 明确记录为「未查到校验实现」，这对我们是个反向参照（我们的 `verify` 已经比它强）。

**⑤ 错误处理**：**混合策略，且分层清晰**。
- 结构级错误 → 硬抛：`throw new ParserException(index, "No path hash index")`、`throw new InvalidAesKeyException($"Given aes key '{AesKey?.KeyString}' is not working with '{Name}'")`、`throw new ParserException("Corrupt pak PrimaryIndex detected")`。
- 条目级异常 → `Log.Warning` + `continue`（跳过该条，保留其余）：`Log.Warning("Invalid nonencoded pak entry with index {Index}, path {Path}", ...); continue;`。
- 版本不认识 → `Log.Warning("Pak file \"{Name}\" has unsupported version {Version}")` 后**继续**（有 `UsingCustomPakVersion()` 白名单豁免一批游戏的自定义版本号）。
- 一致性告警：`if (!IsEncrypted && EncryptedFileCount > 0) Log.Warning("Pak file ... is not encrypted but contains encrypted files")`。

**⑥ 测试做法**：**未查到**。仓库语言统计为 C / C# / C++ / CMake，页面未列出测试工程或金标准样本说明。

**对我们的直接意义**：FPakEntry 的位域解码里有一处教科书级的「同一字段在不同情况下语义不同」处理 ——
```csharp
CompressionBlockSize = compressionBlocksCount switch
{
    1 => (uint) UncompressedSize,   // 块数=1 时，这个字段的含义就是「整个解压后大小」
    > 0 => compressionBlockSize,    // 块数>1 才是真正的块大小
    _ => 0
};
```
以及无压缩时 `CompressedSize = UncompressedSize;`（注释：*The Size is the same thing as the UncompressedSize when CompressionMethod == CompressionMethod.None*）。这与我们的 P1 是**同一个问题的两种做法**：它把「字段语义」写进条件分支，我们写成了一个通用 `declared_size` 校验。

### 2. repak（Rust，UE .pak）

- 仓库：<https://github.com/trumank/repak>（Apache-2.0 / MIT 双许可，master）
- 关键文件：<https://github.com/trumank/repak/blob/master/repak/src/entry.rs>、<https://github.com/trumank/repak/blob/master/repak/src/error.rs>、<https://github.com/trumank/repak/blob/master/repak_cli/src/main.rs>

**① 索引层**：内存。README 明确：*"Only parses index initially and reads file data upon request"*，且 *"Can rewrite index in place to perform append or delete operations without rewriting entire pak"*。索引解析后是 `Vec<Entry>`，条目结构见 `repak/src/entry.rs`：
```rust
pub(crate) struct Entry {
    pub offset: u64,
    pub compressed: u64,
    pub uncompressed: u64,
    pub compression_slot: Option<u32>,
    pub timestamp: Option<u64>,
    pub hash: Option<Hash>,
    pub blocks: Option<Vec<Block>>,
    pub flags: u8,
    pub compression_block_size: u32,
}
```
注意：**`compressed` 与 `uncompressed` 是两个独立字段，不存在一个笼统的「declared size」**。

**② 定位层**：路径字符串 → 按名查。CLI `list` / `hash-list` / `get` / `unpack` 都以 `pak.files()` 的路径为基础，miss 时返回 typed error：`#[error("No entry found at {0}")] MissingEntry(String)`。`--strip-prefix` 默认 `../../../`（mount point 规范化）。**对无名资源**：未查到 repak 有 hash-only 的降级路径。
- CLI 子命令划分（`repak --help`）：`info` / `list` / `hash-list` / `unpack` / `pack` / `get`，全局选项 `-a, --aes-key`。注意它**专门有一条 `hash-list`**：*"List .pak files and the SHA256 of their contents. Useful for finding differences between paks"*（main.rs `ActionHashList` + `action_hash_list` 用 rayon 并行算 SHA256 打印 `{hex} {file}`）。

**③ 解码层**：`compression_slot: Option<u32>` 是 footer 压缩名表的索引；`Entry::read_encoded` 从 u32 位域还原：
```rust
let compression = match (bits >> 23) & 0x3f { 0 => None, n => Some(n - 1) };
let mut compression_block_size = bits & 0x3f;
if compression_block_size == 0x3f { compression_block_size = reader.read_u32()?; }
else { compression_block_size <<= 11; }
let compressed = match compression { None => uncompressed, _ => var_int(29)? };
```
→ **两处「同一槽位语义随条件变」都被显式分支处理**：① 6-bit 块大小槽 `==0x3f` 表示「再去读一个 u32」，否则是「内联值 × 2048」；② 无压缩时 `compressed` 不读字段，直接等于 `uncompressed`。

未知方式：`Compression` 枚举 + feature gate 错误（`Error::Compression` / `Error::Encryption` / `Error::Oodle`），解压失败有专门变体 `#[error("{0} decompression failed")] DecompressionFailed(Compression)`。不是静默跳过。

**④ 校验层**：**只做「差异比对」，不做「正确性校验」**。`hash-list` 输出内容 SHA256 供两包对比；`unpack`/`get` 解压后直接写出，**未查到**与索引里 20 字节 SHA1 的比对代码（`Entry::read` 里 `let hash = Some(Hash(reader.read_guid()?))`，读了存着，读取路径 `read_file` 不比对）。也没有「重压回对」。

**⑤ 错误处理**：单一定义 `repak::Error`（thiserror），CLI `main() -> Result<(), repak::Error>`，出错即非零退出。枚举（error.rs 全文）包含：
`Strum` / `Aes` / `Compression` / `Encryption` / `Oodle` / `Io` / `Fmt` / `Utf8` / `Utf16` / `IntoInner` / `Bool(u8)` / `Magic(u32)` / `OodleFailed` / `MissingEntry(String)` / `PrefixMismatch{prefix,path}` / `WriteOutsideOutput(String)` / `OutputNotEmpty(String)` / `InputNotADirectory(String)` / `DecompressionFailed(Compression)` / `Version{used,version}` / `Encrypted` / `OsString` / `UnsupportedOrEncrypted(String)` / `Other(String)`。
注意 `#[error("{0}version unsupported or is encrypted (possibly missing --aes-key?)")]` —— **把「版本不支持」和「加密了没给 key」合并成一条可操作的提示**。安全侧：解包路径穿越是硬错误 `WriteOutsideOutput`（README: *"Unpacking is guarded against malicious pak that attempt to write to parent directories"*）。

**⑥ 测试做法**：
- 单元测试：`repak/src/entry.rs` 文件末尾有 `mod test { #[test] fn test_entry() { ... } }`，做法是**读一条 V5 条目 → 写回 → `assert_eq!(&data, &out)`**（round-trip 字节级相等）。
- 金标准样本：README 提到 *"repak uses `BTreeMap` in place of `HashMap` to deterministically write the index and happens to rewrite the test paks in the same order"* —— 说明存在 test paks 作为可重写比对样本；更细的 fixture 说明**未查到**。
- CI：仓库有 `.github/workflows`。

### 3. rust-u4pak（Rust，UE .pak，含 check 子命令）

- 仓库：<https://github.com/panzi/rust-u4pak>（MPL-2.0，161★，main）
- 关键文件：<https://github.com/panzi/rust-u4pak/blob/main/src/check.rs>、<https://github.com/panzi/rust-u4pak/blob/main/src/index.rs>、<https://github.com/panzi/rust-u4pak/blob/main/src/pak.rs>、<https://github.com/panzi/rust-u4pak/blob/main/src/decode.rs>

**这是本次对标里「校验层」最值得抄的一个。**

**① 索引层**：内存 `Index { mount_point: Option<String>, records: Vec<Record> }`。定位链路：读 footer → 读 index records → 每条 record 带文件 offset。v10+ 分主索引 + 二级索引（`read_secondary_index_records`）。（index.rs）

**② 定位层**：路径字符串 + `Filter`（通配）。**关键在「拿不到名字」时的降级**：
```rust
warn!("Hash index is used as no full directory index was found. Filenames and paths can not be restored using this index!");
...
for _ in 0..file_count {
    decode!(&mut index_buff, hash: u64, entry: u32);
    encoded_record_info.seek(SeekFrom::Start(entry as u64))?;
    if let Ok(record) = Record::decode_entry(&mut encoded_record_info, format!("{:x}", hash)) {
        records.push(record);
    } else {
        warn!("Failed to read record for file {:x}. Skipping.", hash);
    }
}
```
→ **用 hex 哈希当占位名，并明确 warn 告知「名字不可还原」**。另有单条失败降级 `warn!("Failed to read record for file {}. Skipping.", p)`、`warn!("Failed to resolve name for file {} in folder {}. Skipping.", ...)`。（index.rs `read_secondary_index_records`）

**③ 解码层**：每记录一个 `compression_method: u32`，白名单 `pub const COMPR_METHODS: [u32; 4] = [COMPR_NONE, COMPR_ZLIB, COMPR_BIAS_MEMORY, COMPR_BIAS_SPEED];`，名字映射未知 → `"unknown"`（`compression_method_name`）。压缩块结构在 record 里。
**「同一字段不同语义」的两个真实处理**：
1. `pub fn header_size(version: u32, variant: Variant, record: &Record) -> u64` —— 内联记录头长度按 **version × variant × 是否有压缩块** 分支计算（`V3_RECORD_HEADER_SIZE = 53` / `V1 = 56` / `V2 = 48` / `CONAN_EXILE = 57`，有块再加 `blocks.len() * 16`，v3+ 再 +4）。
2. `decode!` 宏（decode.rs 全文）内建条件字段支持：`decode!(reader, a: u32, if cond { b: u64 }, ...)`，不满足条件的字段声明为 `Option<T>` 并置 `None` —— 一种**内嵌的声明式格式 DSL**。（pak.rs / decode.rs）

**④ 校验层**（`check` 子命令，check.rs 全文）—— 七类检查：
1. 索引区域 SHA1：`check_data(&mut BufReader::new(in_file), " ", index_offset, pak.index_size(), pak.index_sha1(), ignore_null_checksums, ...)`。
2. 每条记录 SHA1：对压缩块逐块 `hasher.update(&buffer)`，末尾 `let actual_digest = hasher.finish(); if &actual_digest != checksum { Err("checksum missmatch:\n\texpected: ...\n\tactual: ...") }`。
3. 越界：`if offset + record.size() > index_offset { "data bleeds into index" }`。
4. 内联记录 vs 索引记录元数据一致：`if !record.same_metadata(&other_record) { "metadata missmatch" }` + `"data record offset field is not 0 but {}"`。
5. 压缩块连续性：`"compression block start offset is bigger than end offset"`、`"compression block with index {} start offset differes from expected value"`、`"actual record end offset differes from expected value"`。
6. **无压缩时的字段语义检查**：`if record.compression_method() == COMPR_NONE && record.size() != record.uncompressed_size() { "file is not compressed but compressed size ({}) differes from uncompressed size ({})" }` —— **这正是我们 P1 该走的路：把「两字段在无压缩时必须相等」写成条件断言，而不是拿一个字段当通用预期值。**
7. 文件名唯一性：`"filename not unique in archive"`。
另有 `ignore_null_checksums`（哈希槽全 0 时放行，**显式开关**，不是默认吞）与 `NET 校验失败会单独提示`：`"Paths not found in pak:\n* ..."` 也计入 error_count。（check.rs）

**⑤ 错误处理**：`Error::new(String).with_path(filename)` 携带路径；多线程收集（crossbeam channel），`abort_on_error` 默认 **false** → 逐条错误写到 stderr 并累加 `error_count`，`check()` 返回错误**计数**；`--null-separated` 便于脚本消费。即：**默认不中断、但每条错误都可见且可计数**。

**⑥ 测试做法**：**未查到**。仓库语言为 Rust / Shell，README 无测试章节。

### 4. paksmith（Rust，UE pak，分阶段工程）

- 仓库：<https://github.com/r6e/paksmith>（MIT，2026-05 创建，main）
- 关键文件：<https://github.com/r6e/paksmith/blob/main/README.md>、<https://github.com/r6e/paksmith/blob/main/docs/plans/ROADMAP.md>、<https://github.com/r6e/paksmith/blob/main/crates/paksmith-core/src/error.rs>

**① 索引层**：内存 + trait 抽象。crate 划分：`paksmith-core`（库）/ `paksmith-cli` / `paksmith-gui`，另四个非默认成员 `paksmith-fixture-gen` / `paksmith-core-tests` / `paksmith-bench` / `paksmith-doc-lint`。Phase 1 定义 `ContainerReader` trait + `PakReader`，Phase 8 计划 IoStore（.utoc/.ucas）。索引在 `container::pak::index`。

**② 定位层**：`list` / `search` 查询条目。`search` 谓词：`--type`（可重复，OR）、`--name`（basename）、`--regex`（全路径）、`--min-size/--max-size`（人类单位）。未命中 → `EntryNotFound { path }`。**对无名资源**：未查到（iostore Phase 8 未实现）。
（Phase 划分一句话：`ROADMAP.md` 的 Phase Overview 表 1→9；Phase 1 pak 读取、2 UAsset 解析、3 导出、4 CLI、5 game profile、6 GUI、7 资产查看器、8 IoStore、9 wgpu 3D。）

**③ 解码层**：`CompressionMethod` 枚举，**未知是显式变体且分两种**：`Unknown(_)` 与 `UnknownByName(_)`。未支持的方式由 typed fault 明确拒绝：
```rust
pub enum DecompressionFault {
    UnsupportedMethod { method: CompressionMethod },
    DecompressionBomb { block_index, actual, claimed_uncompressed },
    ...   // 后文截断处还有 NonFinalBlockSizeMismatch / SizeUnderrun
}
```
error.rs 注释明说设计意图：*"Both `read_entry` ... and `verify_entry` reject the unsupported methods uniformly rather than silently returning ciphertext / unhashed bytes."* —— **拒绝静默返回密文/未校验字节**，这正对着我们的「解出来了但不知道对不对」。

**④ 校验层**（本项目最强项）：
- SHA-1 验证是 **opt-in**：Phase 1 描述 *"opt-in SHA-1 verification (entry payloads + main-index, FDI, and PHI regions on v10+)"*。
- 校验对象用类型区分：`HashTarget::{Index, Entry, Fdi, Phi}`（注释：*"Splitting `target` into a typed enum prevents the previous (kind=\"index\", path=Some(...)) nonsensical combination at the type level"*）。
- 不匹配：`HashMismatch { target, expected, actual }`，错误信息 `"SHA1 mismatch: {target} expected={expected} actual={actual}"`（hex，40 字符）。
- **「哈希槽被抹掉」是一种独立报警状态**：`IntegrityStripped { target }`，注释：*"An entry's stored SHA1 slot is zeroed but the archive's index hash is non-zero ... it is why this is an error rather than a skip"* 且 *"random corruption almost never zeroes 20 contiguous bytes"*。
- 解压炸弹：`DecompressionBomb` 注释：*"The decoder is bounded to `uncompressed_size + 1` bytes per block, so this fires the moment the lie is detectable."*

**⑤ 错误处理**：`#[non_exhaustive] enum PaksmithError`，结构化 fault（`InvalidFooterFault` / `IndexParseFault` / `DecompressionFault` / `AssetParseFault` / `MappingsParseFault` / `LocresParseFault` / `ProfileFault`）。三条纪律值得直接抄：
1. **「合法但还没实现」≠「不该发生」**：`UnsupportedFeature { context }` 的 Display 是 `unsupported feature: …`，注释明说 *"a deliberate not-yet-implemented limitation, NOT a bug or malformed input. Distinct from `Self::Internal`"*；`Internal { context }` 留给契约违反，并注明 *"per paksmith's no-panics-in-core invariant"*。
2. **字符串兜底要起摩擦名**：未提升为 typed variant 的兜底叫 `OtherUnpromoted`，注释：*"Named `OtherUnpromoted` (rather than `Other`) as a friction signal: the explicit \"Unpromoted\" suffix makes contributors reaching for a fallback at construction sites pause to ask \"should this be its own typed variant?\" before defaulting to the string-bag."*
3. **线路稳定的 Display**：*"preserves the wire-stable operator-facing token shapes ... so log greps + monitoring rules keep working"*，且**逐变体单测钉住精确字符串**。
其余：`MappingsParse`（.usmap）、`Decryption { path }`（`path` 为 `Option`，区分内存源与文件源）。

**⑥ 测试做法**（本项目第二强项）：

### 6. UnityPy（Python，Unity）

- 仓库：<https://github.com/K0lb3/UnityPy>（main）
- 关键文件：<https://github.com/K0lb3/UnityPy/blob/master/UnityPy/helpers/TypeTreeHelper.py>、<https://github.com/K0lb3/UnityPy/blob/master/UnityPy/files/SerializedFile.py>

**① 索引层**：内存。`SerializedFile.objects: Dict[int, ObjectReader]`（键 path_id）+ `types: List[SerializedType]`（每个带 `TypeTreeNode`）+ `script_types` / `externals` / `ref_types`；`_enable_type_tree` 由容器头部标志控制，也受配置 `config.SERIALIZED_FILE_PARSE_TYPETREE` 影响（可直接关掉类型树只做原始切分）。另有 `_cache` 加速资产互引。

**② 定位层**：path_id 字典 + `container`（从 `AssetBundle` 的 `ContainerHelper` 拿 container 名 → 资产）。**对无名/未知类型：`UnknownObject` 是一等公民**（见 ③④）。

**③ 解码层**：`TypeTree` 驱动 —— 每个字段的类型/长度/对齐完全由节点决定（`FUNCTION_READ_MAP` 把节点类型名映射到具体 reader；`metaflag_is_aligned` 判断 `kAlignBytes = 0x4000`；`node.m_Children[0].m_Type == "Array"` 判断变长数组）。**未知类型 → 兜底类**：
```python
clz = getattr(classes, node.m_Type, UnknownObject)
try:
    value = clz(**value)
except TypeError:
    ...
    if clz is UnknownObject or missing_keys:
        value = UnknownObject(node, **value)     # 连 typetree 节点本身一起带上
```
`getattr(classes, node.m_Type, UnknownObject)` 就是「按名查实现，查不到用显式 Unknown 类」。引用类型查不到时：`raise ValueError(f"Referenced type not found: {cls} {ns} {asm}")`。（TypeTreeHelper.py `read_value` / `get_ref_type_node`）

**④ 校验层（本次最直接的答案）**：
```python
def read_typetree(root_node, reader, as_dict=True, byte_size=None,
                  check_read=True, assetsfile=None):
    ...
    if check_read and bytes_read != byte_size:
        raise ValueError(f"Expected to read {byte_size} bytes, but only read {bytes_read} bytes")
```
- `byte_size` 来自容器里的 `objectInfo.byteSize`；`bytes_read = reader.Position - pos`。
- **关键语义**：这里校验的是「**反序列化消费掉的字节数** == 声明的对象字节数」，**不是「解压后大小」也不是「压缩后大小」**。
- 还有一个负长度防御：`if size < 0: raise ValueError("Negative length read from TypeTree")`。

→ 这一条直接解释了我们的 P1：**校验必须盯住一个"语义唯一"的量**。UnityPy 挑的是「对象序列化字节数」，我们在 flag 0 上挑的却是「压缩后长度」，语义错配 → 误报。

**⑤ 错误处理**：**raise，不静默**。`ValueError("Negative length read from TypeTree")`、`ValueError("Expected to read ... but only read ...")`、`ValueError(f"Referenced type not found: ...")`。降级只发生在「类是未知的」这一种情况，且降级产物是带节点的 `UnknownObject`（信息不丢）。

### 7. QuickBMS / MexScript（多格式，脚本 DSL）

- 文档：<https://aluigi.altervista.org/papers/quickbms.txt>（GPL-2.0；作者 Luigi Auriemma）
- 脚本语言谱系：MexScript → QuickBMS 扩展；见 <https://wiki.xentax.com/index.php/MexScript>（我抓取该页返回空内容，故仅按 quickbms.txt 正文与官方描述记录）

- `-M F` *"experimental compare and merge feature that allows to compare the extracted files with those located in the folder F"*（明确标注为**实验性**，且 *"currently this experimental option will create files of 0 bytes if they are not different, so it's not simple to identify what files were written"*）；
- `-# in reimport mode checks if the archived files and those to reimport are the same (hash)`；
- `-L F` dump offset/size/name；`-v`/`-V` 详细调试；`-X`/`-H` hex 查看。

**⑤ 错误处理（本项目最有对比价值的一点）**：默认是**失败即停**，宽容要显式开：
- `-.` *"don't terminate QuickBMS if there is an error while parsing multiple files (like wrong compression or small file), just continue with the other files"* —— **续跑是显式开关**。
- `-e` *"ignore the compression errors and dump the (wrong) output data anyway"* —— **「照样导出错误数据」是一个明确标注为实验性的开关，不是默认**。
- 其他：`-o` 覆盖、`-k` 跳过已存在、`-K` 自动重命名、`-0` *"no extraction of files, useful for testing a script without using space"*（干跑）、`-I` 变量名大小写敏感开关、`-P CP` 指定 code page。

**⑥ 测试做法**：**未查到**（无测试框架；社区靠 zenhax 论坛共享脚本互相参照；有 `-0` 干跑与 `-v`/`-V` 调试作为验证手段）。

**对我们的意义**：QuickBMS 是「**格式描述 DSL**」路线的极端案例 —— 用 100 行文本描述 100 种容器，代价是「格式知识散在脚本里、没有类型系统、没有内建校验」。它的 `-e`/`-.` 默认关闭也印证了一条纪律：**宽容行为必须是显式开关**。

### 8. Kaitai Struct / 010 Editor Binary Templates（格式声明 DSL）

#### 8.1 Kaitai Struct（`.ksy`）

- 入口：<https://kaitai.io/>；用户手册：<https://doc.kaitai.io/user_guide.html>；伞仓库：<https://github.com/kaitai-io/kaitai_struct>（编译器与可视化器 GPLv3+，各语言 runtime MIT/Apache-2.0；0.11 发布于 2025-09-07）

**① 索引层 / ② 定位层**：不适用 —— 它是**解析器生成器**，不管理容器与条目定位。
**③ 解码层**：**声明式 YAML（`.ksy`）→ 编译成 12 种语言的解析器**（C++/C#/Go/Java/JS/Lua/Nim/Perl/PHP/Python/Ruby/Rust）。核心键：`meta`（`id`/`endian`/`file-extension`）、`seq`（有序字段）、`types`（子类型）、`enums`、`instances`（惰性计算字段）、表达式语言（`size: my_len * 2`、`size: header.body_len`、`size-eos: true`、`terminator: 0`/`strz`）。
**④ 校验层（声明式断言）**：
- `contents: [0xca, 0xfe, 0xba, 0xbe]` —— 读并比对 magic，不匹配即错误。
- `valid:` 支持 `eq`（或缩写 `valid: 0x42`）/ `min` / `max` / `any-of` / `expr`。手册原话：*"When a value does not meet the specified criteria, Kaitai Struct raises a validation error, halting further parsing. This preemptive measure ensures the data being parsed is within the expected domain, providing a first layer of error handling."*
- 注意：手册同时声明 *"The actual implementation of validation checks is language-dependent and may vary in behavior and supported features across different target languages."*
**⑤ 错误处理**：验证失败 → 抛错中止解析（= 硬失败，无「跳过继续」内建机制）。

**「同一字段在不同条件下语义不同」的官方答案（本次重点）**：
Kaitai 用三种机制表达，官方 issue 里给出了与 010 Editor 模板的完整对照（<https://github.com/kaitai-io/kaitai_struct/issues/849>）：
1. **`if:` 条件字段** —— `seq` / `instances` 的属性可开关：
```ksy
seq:
  - id: t_count
    type: u1
  - id: cell_info
    type: inter_mr_cell
    repeat: expr
    repeat-expr: t_count
  - id: shape_id
    type: u1
    if: location_id == 1
```
2. **`type/switch-on` + `cases`** —— 同一位置按前面字段的值换类型：
```ksy
  - id: shape
    type:
      switch-on: shape_id
      cases:
        0: undefined_info
        1: point_info1
    if: location_id == 1
```
3. **`params` / `value` 实例** —— 把 `_parent.shape_id` 这类长引用收成一个局部名（维护者原话：*"if you don't like these long `_parent.shape_id` references in every `if`, you can make a shortcut of it"*）。
另有 issue #584 展示「用三元表达式切换 `type`」（`type: '_parent.osu_ver < 20140609 ? u1 : f4'`）。

#### 11.1 Ekey/LA.NPK.Tool（C#，LifeAfter NPK 解包器）

- 仓库：<https://github.com/Ekey/LA.NPK.Tool>（**已 ARCHIVED**，15★，2021-09 创建，main）
- 关键文件：<https://github.com/Ekey/LA.NPK.Tool/blob/main/LA.Unpacker/LA.Unpacker/FileSystem/Package/NpkUnpack.cs>、<https://github.com/Ekey/LA.NPK.Tool/blob/main/LA.Unpacker/LA.Unpacker/FileSystem/Package/NpkEntry.cs>、<https://github.com/Ekey/LA.NPK.Tool/blob/main/LA.Unpacker/LA.Unpacker/FileSystem/Package/NpkHash.cs>

**① 索引层**：**无持久索引**。每次运行：读头 32 字节 → `NpkCipher.iDecryptData` 解密 → `NpkHeader{ dwHash(8), dwMagic(4), dwVersion(4), dwTableOffset(4), dwTotalFiles(4) }`；`dwTableSize = dwTotalFiles * 48`；`Seek(dwTableOffset)` 读整表再解密，解析进 `List<NpkEntry> m_EntryTable`。

**② 定位层**：**名 → 哈希字典**。`String m_FileName = NpkHashList.iGetNameFromHashList(m_Entry.dwHash.ToString("X16"));`；哈希算法是 **murmur3-32（带 seed）over ASCII 名**（`NpkHash.iGetHash(String, UInt32 dwSeed)`，`MurMur3Core` 完整实现，含尾块 1/2/3 字节处理）。
**最值得抄的一点：命中率是被度量并公开的。** README 有一整张「NPK ProjectList Information」表，逐包给出百分比，例如：
```
| res.npk                    | 53041 of 64427 (82%) |
| script.npk                 |   530 of   531 (99%) |
| Documents\script.npk       | 30642 of 30642 (100%)|
| res\scene.npk              |     0 of   420  (0%) |
| res\textures.npk           |     4 of   383  (1%) |
| res\scene_bw\bigworld\...  |     0 of  3936  (0%) |
```
→ **「拿不到名字的比例」是一等指标，不是靠感觉**。这正是我们 P2（贴图名 0 命中）该有的呈现方式。

**③ 解码层（与我们 flag 问题直接同族）**：条目 48 字节，字段布局：
```csharp
m_Entry.dwHash             = TEntryReader.ReadUInt64();   // 8
m_Entry.dwOffset           = TEntryReader.ReadUInt32();   // 4
m_Entry.dwCompressedSize   = TEntryReader.ReadInt32();    // 4
m_Entry.dwDecompressedSize = TEntryReader.ReadInt32();    // 4
m_Entry.dwCompressedCRC    = TEntryReader.ReadUInt32();   // 4
m_Entry.dwDecompressedCRC  = TEntryReader.ReadUInt32();   // 4
m_Entry.dwCompressionFlag  = TEntryReader.ReadInt32();    // 4   // 注释：2 > lz4
TEntryReader.Position += 16; //reserved data
```
→ **两个大小字段、两个 CRC 字段是分开命名的**（`dwCompressedSize` / `dwDecompressedSize`、`dwCompressedCRC` / `dwDecompressedCRC`）。这是 P1 的结构性答案。
分支处理（`NpkUnpack.cs`）：
- `flag == 0` → 按 `dwCompressedSize` 读原样；**但 `script.npk` 有内嵌子格式**：先读 `UInt16` magic，`!= 0x4974` 则整体解密，再看开头 `Int64` 是否 `== 1`（表示 zlib），是则 `ZLIB.iDecompress(lpSrcBuffer, 18)`（**从偏移 18 开始，即 8 字节标记 + 8 字节压缩大小 + 2 字节**），否则原样写出。
- `flag == 2` → `LZ4.iDecompress(lpSrcBuffer, m_Entry.dwDecompressedSize)`。
- **其他 flag → 原样 `File.WriteAllBytes`，无警告无报错**。

**④ 校验层**：**结构上有两个 CRC 字段，代码里一个都没用**（读了就丢，`NpkUnpack` 全文无 CRC 比对）。→ 与我们现状同类：字段存在、校验缺位。

**⑤ 错误处理**：
- magic 不符 → `Utils.iSetError("[ERROR]: Invalid magic of NPK archive file"); return;`（**整体退出**）。
- version 不符 → `Utils.iSetError("[ERROR]: Invalid version of NPK archive file"); return;`（**整体退出**，且硬编码 `dwVersion != 3`）。
- 未知 flag → **静默原样落盘**。
- 参数错误 → 打印 `[Usage]` 并 return。

#### 11.2 ZhangFengze/NeoXResearch（Python，NeoX 引擎逆向笔记）

- 仓库：<https://github.com/ZhangFengze/NeoXResearch>（66★，Python 97.1% + C 2.9%）
- 性质：**README 即逆向方法论文档**，不是工具。

**NPC/NPK 格式（README 原文）**：
```
[0:4]   magic head 必须为 'NXPK'
[4:8]   包含文件数量
[20:24] 元信息表 相对文件头的偏移
中间是裸数据，之后是元信息表，然后文件结束
元信息表每项 28 字节：
[0:4]   文件ID（文件路径的哈希）
[4:8]   文件数据 相对文件头的偏移
[8:12]  文件数据大小
[12:16] 文件数据解压后大小
[24:26] 压缩方式（0：未压缩 1：zlib 2：lz4，一般为2）
[26:27] 加密方式（0：未加密 1：rc4 2：simple，一般为0）
注意 lz4 采用 block 压缩方式
```
**两个直接印证我们问题的点**：
1. **「大小」是两个字段**（`文件数据大小` vs `文件数据解压后大小`），且**「压缩方式」与「加密方式」是两个独立字节** —— 不是打包进一个 flag。LifeAfter 的 NPK 把两者塞进一个 flag（见 11.1），说明**同族引擎不同版本/不同游戏的字段语义确实会变，必须按容器识别，不能跨容器套用**。
2. **「解出来但识别不了」= 漏了一层解密**，README 明写：
> FileLoader 读出文件后，如果 this+44 字节处存储了 `neox::game::NXEncodeHook` 实例地址，则调用其成员函数对文件内容进行解密。参考链接里的 npk 解包没有处理这一步解密，**导致解出的文件无法识别**。

→ 我们 P2「贴图名 0 命中」、以及解出来的数据「看着像但用不了」的类问题，在别人的项目里往往就是**少了一层变换**，而不是哈希算法错了。

其余方法论（值得作为我们排查路线的模板）：先用 IDA Strings 里的 CPython 调试串定位版本号 → 用官方源码字符串反查函数 → 沿调用关系找 `NXNpkLoaderCreator` / `NXFileLoaderCreatorManager` 的注册点 → 动态调试 dump `redirect.nxs`。作者还记录了三条**失败的**替代路线（"修复 pyc 的其他尝试"），属于**显式记录「此路不通」**的好习惯。

## 三、对我们的启发

> 每条格式：**做法** —— 来源（项目 · 文件 · 代码位置）→ 对我们的具体动作。

### A. 把「条目大小」拆成两个字段，而不是一个 `declared_size`（直击 P1）

- 来源 1：**repak** `repak/src/entry.rs`，`struct Entry { pub compressed: u64, pub uncompressed: u64, ... }` —— <https://github.com/trumank/repak/blob/master/repak/src/entry.rs>
- 来源 2：**CUE4Parse** `CUE4Parse/UE4/Pak/Objects/FPakEntry.cs`，`public readonly long CompressedSize; public readonly long UncompressedSize;` 且 `public bool IsCompressed => UncompressedSize != CompressedSize && CompressionBlockSize > 0;`
- 来源 3：**Ekey/LA.NPK.Tool** `NpkEntry.cs`：`dwCompressedSize` / `dwDecompressedSize` / `dwCompressedCRC` / `dwDecompressedCRC` 四个字段分开命名 —— <https://github.com/Ekey/LA.NPK.Tool/blob/main/LA.Unpacker/LA.Unpacker/FileSystem/Package/NpkEntry.cs>
- 动作：NPK 条目统一按 `packed_size` + `unpacked_size` 两字段建模；校验规则按 flag 分流，**不要**再有一个笼统的「预期大小」。

### B. 「无压缩时 size 字段等于另一个字段」要写成条件分支（P1 的第二种表现）

- 来源 1：**repak** `Entry::read_encoded`：`let compressed = match compression { None => uncompressed, _ => var_int(29)? };`（无压缩时**不读**该字段）
- 来源 2：**CUE4Parse** `FPakEntry.cs`：`else { // The Size is the same thing as the UncompressedSize when CompressionMethod == CompressionMethod.None. CompressedSize = UncompressedSize; }`
- 来源 3：**rust-u4pak** `src/check.rs`：`if record.compression_method() == COMPR_NONE && record.size() != record.uncompressed_size() { "file is not compressed but compressed size … differes from uncompressed size …" }` —— 语义约束被写成**显式断言**
- 动作：把「flag ↔ 大小字段语义」写成一张表 + 对应断言；flag 0 的断言应是「`len(packed) == packed_size`」，而不是「`len(unpacked) == declared_size`」。

### C. 校验对象要按类型分开，错误信息要能机读

- 来源：**paksmith** `crates/paksmith-core/src/error.rs`：`enum HashTarget { Index, Entry, Fdi, Phi }`、`HashMismatch { target, expected, actual }`（`"SHA1 mismatch: {target} expected={expected} actual={actual}"`）；注释原话：*"Splitting `target` into a typed enum prevents the previous (kind=\"index\", path=Some(...)) nonsensical combination at the type level."* —— <https://github.com/r6e/paksmith/blob/main/crates/paksmith-core/src/error.rs>
- 动作：我们把「校验对象」也做成枚举（容器头 / 容器索引 / 条目 / 子区域），错误带 `expected`/`actual`，让 `verify` 的输出可被脚本消费而不是靠人读日志。

### D. 「完整性被抹掉」要是一种独立报警状态，而不是「没哈希所以跳过」（直击 P4）

- 来源：**paksmith** `error.rs` 的 `IntegrityStripped { target }`，注释原话：*"An entry's stored SHA1 slot is zeroed but the archive's index hash is non-zero ... it is why this is an error rather than a skip"* 且 *"random corruption almost never zeroes 20 contiguous bytes"*，并注明「Monitoring rules can alert on this variant separately」。
- 来源 2（两级哈希做增量失效）：**akdp** README：*"用 AB 包 hash 先筛出变化包，再以 Sprite SHA-256 决定真正的发布 delta"*
- 动作：索引里为每个容器存 **容器级 sha256**（不只清单指纹），并为条目建立「有哈希 / 零值 / 无声明」三态；`stale` 判定升级为「单文件 sha256 变了 → stale」，直接解决 P4。

### E. 「我还不支持」与「数据不对」必须分成两类错误（间接解决 P1 的误报噪声）

- 来源：**paksmith** `error.rs`：`UnsupportedFeature { context }`（Display `unsupported feature: …`，注释 *"a deliberate not-yet-implemented limitation, NOT a bug or malformed input"*）vs `Internal { context }`（契约违反）；`OtherUnpromoted` 的「摩擦命名」注释。
- 动作：`decoded_size_mismatch` 拆成 `UnsupportedFlag` / `SemanticMismatch` / `SizeMismatch{expected_field, actual}`；能力缺口不能被算进「数据质量问题」的统计里，否则 94.88% 这种数字会掩盖真问题。

### F. 解压正确性可以就地用「实读字节数 == 声明反序列化字节数」来验，不必重压回对

- 来源：**UnityPy** `UnityPy/helpers/TypeTreeHelper.py` 的 `read_typetree(...)`：
  ```python
  if check_read and bytes_read != byte_size:
      raise ValueError(f"Expected to read {byte_size} bytes, but only read {bytes_read} bytes")
  ```
  配合 **AssetStudio** `SerializedFile.cs` 的 `objectInfo.byteSize = reader.ReadUInt32();` —— <https://github.com/K0lb3/UnityPy/blob/master/UnityPy/helpers/TypeTreeHelper.py>
- **关键洞察**：它校验的量是「消费掉的字节数」，语义唯一；我们在 flag 0 上校验「压缩后长度」也语义唯一 —— 问题不在于「用 size 校验」，而在于**用错了那个 size**。这说明修法很小：换字段即可。
- 动作：`unpacked_size` 校验只对「解压后」产物做；`packed_size` 校验只对「容器切片长度」做；把两者的对应关系按 flag 表声明（见 A/B）。

### G. 拿不到名字时：显式降级 + 明确告知 + 用 hex 名占位（直击 P2）

- 来源 1：**rust-u4pak** `src/index.rs` `read_secondary_index_records`：`warn!("Hash index is used as no full directory index was found. Filenames and paths can not be restored using this index!")` 后 `Record::decode_entry(&mut encoded_record_info, format!("{:x}", hash))` —— **用 hex hash 当占位名，条目照样可导出**
- 来源 2：**Ekey/LA.NPK.Tool** README 的逐包命中率表（`res\textures.npk 4 of 383 (1%)`）
- 来源 3：**UnityPy** `get_ref_type_node` → `raise ValueError(f"Referenced type not found: {cls} {ns} {asm}")`（连 cls/ns/asm 一起报，便于回查）
- 动作：`find`/`restore` 在名字不可还原时，输出「hex fid 占位条目」+「本容器不可还原比例」；把 P2（贴图名 0/4,579,785）从「0 命中」升级为「N 条中 M 条不可还原，键形态 X，样本 fid 前缀 …」，从而可追。

### H. 「同名不同义」的字段，用外部 schema 决定语义，而不是散落硬编码

- 来源 1：**Unity `TypeTree`** —— 内嵌（AssetStudio `m_EnableTypeTree` / `TypeTreeBlobRead`）或外置（**AssetsTools.NET** `manager.LoadClassPackage("classdata.tpk"); manager.LoadClassDatabaseFromPackage(afile.Metadata.UnityVersion);`，wiki 原话 *"the tpk file contains information about how to deserialize assets for various engine versions"*）—— <https://github.com/nesrak1/AssetsTools.NET/wiki/Getting-Started:-Assets-file-reading>
- 来源 2：**Kaitai Struct** `.ksy` 的 `if:` / `type: switch-on … cases:` / `params`（<https://github.com/kaitai-io/kaitai_struct/issues/849>）
- 来源 3：**FlatBuffers schema**（torappu 用 `ResourceManifest.fbs` + `OpenArknightsFBS`；akdp manifest 记录 *"ASTR/flatc 等转换器来源"*）
- 动作：把我们的「flag → {size 字段语义, 解码器, 校验规则}」外置成一份**声明式映射表**（YAML/JSON 都行，甚至就是我们索引里的一张表），代码只做查表执行。好处：新增 flag 不动代码；出现「同 flag 不同容器」时（Ekey 的 script.npk 就是例子）能按容器覆盖。

### I. 路径哈希索引要能「按 hash 列条目」，让 fid 成为一等键

- 来源：**rust-u4pak** `src/index.rs` 的 hash-index 分支遍历 `(hash: u64, entry: u32)` 并对每条 `Record::decode_entry(..., format!("{:x}", hash))`
- 动作：我们的双 murmur3 fid 已经能算，应该**存进索引**（`fid → 容器/偏移`），使「无路径也能列出/导出」成为默认能力，而不是必须走 `--variants`。

### J. 未知类型/格式要有「兜底对象」，而不是丢弃

- 来源 1：**UnityPy** `clz = getattr(classes, node.m_Type, UnknownObject)` → `UnknownObject(node, **value)`（**连 typetree 节点一起带上**）
- 来源 2：**AssetStudio** `AssetsManager.ReadAssets()` 的 `default: obj = new Object(objectReader);`
- 动作：解不出的条目落盘为「带原始元数据的占位条目」（容器/偏移/长度/fid/flag/原始头部 hex），使 0 命中的那部分仍可统计、可回查，而不是消失。

### K. 索引/发布要带 manifest，且校验门 fail-closed

- 来源：**akdp** README —— manifest 记 *"契约版本、源版本、校验指标和三个包的大小/SHA-256"*，Release 保持 **draft 直到校验完成**，*"校验门不过则不发布（fail-closed）"*
- 动作：`index build` 除了产索引，再产一份 manifest（容器清单 + 每包 sha256 + 每包条目数 + 未解析比例 + 工具版本）；把 `verify` 明确作为「索引可用/不可用」的门。

### L. 回归样本要显式命名、可复跑（探针）

- 来源：**akdp** `config/probes.json`：`{"operators": ["嘉辛塔", "时隙", "珊比"], "events": ["act53side"]}` + *"记录数回归"* —— <https://github.com/3aKHP/arknights-data-pipeline/blob/main/config/probes.json>
- 动作：为 60 容器/2,300,843 行建一份类似探针（每容器固定 N 条已知条目 + 期望 flag/大小/首字节 magic），跑 `index build` 后逐条核对 + 比对总行数，防「改一处坏另一处」。

### M. 用独立实现当交叉验证 oracle

- 来源：**paksmith** README：*"The fixture-generation crate in particular depends on a git-sourced parser used as a cross-validation oracle."*
- 动作：NPK 侧可用 **Ekey/LA.NPK.Tool** 或 NeoXtractor（<https://github.com/MarcosVLl2/NeoXtractor/issues/50> 有 LifeAfter 支持诉求）当对拍对象；UE 侧用 repak / rust-u4pak / CUE4Parse 三方互校 `index`/`list` 结果。

### N. 缓存与增量要能自愈

- 来源：**torappu** `assets.py`：下载失败 `dest.unlink(missing_ok=True)`（注释 *"下载失败时清理 dest"*）、解压中断 `hashed_ab_path.unlink(missing_ok=True)`（注释 *"解压中断会留下损坏的缓存文件，必须清掉"*）；缓存键用本地算的 crc64 而非响应头（*"这样缓存键不再依赖响应头"*）
- 动作：重扫时若某容器读取失败/哈希不符，**删除该容器在索引中的全部行并标记**，而不是保留旧行 —— 这是 P4 的另一半（旧行残留会让「单个包换了」检不出来）。

### O. 覆盖率要作为一等指标公开

- 来源：**Ekey/LA.NPK.Tool** README 的「NPK ProjectList Information」逐包百分比表（既有 100% 也有 0%）
- 动作：`index status` / `overview` 输出「命名覆盖率」「解码成功率」「校验通过率」三张按容器的百分比表；0% 要显式出现，不能因为难看而省略。

### P. 「少一层变换」是「解出来但识别不了」的常见真因

- 来源：**ZhangFengze/NeoXResearch** README：*"FileLoader 读出文件后，如果 this+44 字节处存储了 `neox::game::NXEncodeHook` 实例地址，则调用其成员函数对文件内容进行解密。参考链接里的 npk 解包没有处理这一步解密，导致解出的文件无法识别。"* —— <https://github.com/ZhangFengze/NeoXResearch>
- 动作：P2（贴图名 0 命中）排查时，优先怀疑「贴图相关容器多一层变换/另一套哈希输入（含扩展名/大小写/目录前缀）」，而不是先怀疑 murmur3 实现错。

### Q. 对「本次无事可做」与「失败」要分开表达

- 来源：**torappu** `core/tasks/base.py`：`class SkipTask(Exception)` —— *"Raised by a dependency (or a task body) when there is nothing to do. The scheduler logs it as \"Skipping task\" instead of counting a failure."*；以及 `di.py` 的**注册期**依赖校验（*"fails when the task is registered (at import time), not when the pipeline reaches it"*）
- 动作：`index build` 在「无变化」时应输出 `skipped`（并附指纹证据），与 `failed` 区分开；配置错误尽量在启动时暴露。

## 四、明确不建议照搬的

### 1. 不要用 QuickBMS 式的「关掉校验/忽略错误」来解决误报

- 相关做法：`-e` *"ignore the compression errors and dump the (wrong) output data anyway"*；`-.` *"don't terminate QuickBMS if there is an error … just continue"*（<https://aluigi.altervista.org/papers/quickbms.txt> §2）
- **为什么不建议**：我们 P1 的 94.88% 是**误报**，用「关校验」能立刻变绿，但会同时关掉真问题的信号；而且 QuickBMS 自己把 `-e` 标注为实验性、默认关闭 —— 连它的作者都不把它当默认路径。
- 正确做法：按 A/B/F 修字段语义，让断言变精确。

### 2. 不要把 AssetStudio 式的「catch + 日志 + 继续」当默认策略

- 相关做法：`AssetsManager.cs` 每个加载器都 `catch (Exception e) { Logger.Error(...) }` 后继续；`ReadAssets()` 失败对象只进日志。
- **为什么不建议**：`AssetRipper#1168` 的诉求本身说明了痛点 —— *"99.9% 的资源可以解密，但正是那 0.01% 让整个解密无法进行"*（<https://github.com/AssetRipper/AssetRipper/issues/1168>）。也就是说，「整体失败」太脆、「逐条吞掉」太静，两端都不被接受。日志不是数据：不可机读、不可聚合、不可发布。
- 正确做法：走 paksmith 路线（C/E/J）—— 结构化 fault + 显式 unknown 条目 + 可聚合的指标。

### 3. 不要照搬 repak / CUE4Parse 的「不校验」

- 相关做法：repak 读取路径 `Entry::read_file` 不比对 `hash`；CUE4Parse `FPakEntry` `Ar.Position += 20; // Hash` 直接跳过；两者都无「重压回对」。
- **为什么不建议**：它们不需要校验（用途是 `pack`/`unpack` mod 场景），而我们的项目基石就是「索引地基 + verify」。我们已有的 `verify` 是**领先项**，不应为了「像成熟项目」而降级；反过来，`hash-list`（repak）这种「输出内容 SHA256 供对比」的思路值得吸收到 P4 的 stale 判定里。

### 4. 不要照搬 Ekey 的 NPK 条目字段定义（只学习惯）

- 相关做法：48 字节条目、`dwVersion != 3` 硬编码、flag 0/2 两分支、未知 flag 静默原样落盘。
- **为什么不建议**：它只覆盖 2021 年的 LifeAfter，且 README 自己显示命中率差异极大（`res\scene.npk 0 of 420 (0%)`、`res\textures.npk 4 of 383 (1%)`）；NeoXResearch 的 28 字节条目与「压缩方式/加密方式分列」证明**同族引擎布局随版本变**。把它的字段定义当契约会被 2026 年的包直接打脸。
- 正确做法：学它的**两个 size / 两个 CRC 分开命名**（A）和**命中率公开**（O）这两个习惯，字段定义以我们自己的实测为准。

### 5. 不要把 akdp 的 LLM 摘要步骤搬到我们链上

- 相关做法：`summarize` *"增量 LLM 双级别摘要（summaries.json + event_summaries.json）"*，依赖 `LLM_BASE_URL/LLM_API_KEY/LLM_MODEL`。
- **为什么不建议**：引入外部 LLM 端点会带来成本、速率限制、**不可复现**与隐私面；我们的链是只读拆包/知识项目，摘要不是发布契约的一部分。akdp 把它放在 `validate` 之前且只对缺失条目调用（*"典型更新 ~15-20 章 + 1-2 活动 ≈ 20 次调用"*），说明它自己也把它当可选项。
- 可迁移的是 **validate 门 + manifest + probes**（K/L），不是 summarize。

### 6. 不要为 3 个子命令族引入 torappu 式 DI 容器

- 相关做法：`torappu/core/di.py` 自研 FastAPI 式注解注入 + `analyze()` 注册期校验 + `SkipTask`。
- **为什么不建议**：torappu 有几十个 task（`tasks/` 下逐个资产类型一个文件），DI 摊销得过来；我们只有 `①-0/①-1/①-2` 三个族，引入 Resolver/Depends/Param/Dependant 的抽象成本高于收益，还会让 `01_工具/run_all.py` 的入口变绕。
- 可迁移的是两条纪律：**注册期/启动期暴露配置错误**、**`skipped` 与 `failed` 分开**（Q）。

### 7. 不要把整条链重写成 Kaitai Struct DSL

- 相关做法：`.ksy` 一份声明 → 编译成 12 种语言的解析器（<https://kaitai.io/>）。
- **为什么不建议**：需要引入 `ksc` 编译步骤 + 对应语言 runtime，且我们的「格式」目前只有容器头 + 条目表两个小结构，手写 Python 更快更可控；Kaitai 的 `valid` 实现还**因目标语言而异**（手册明说），会给校验语义引入不确定性。
- 可迁移的是**表达习惯**：`if:` / `switch-on` / `valid:` 三种写法（H）。若将来 FPK/WPK 的未知键形态需要穷举探索，再单独评估局部使用。

### 8. 不要把 010 Editor 模板当「主格式文档」

- 相关做法：C 风格模板 + Template Results 变量树（<https://www.sweetscape.com/010editor/templates.html>）。
- **为什么不建议**：GUI 工具、模板不可编译执行、进不了 CI，也没有内建断言/回归（本卡片 ④⑥ 均未查到）。它适合**人工单文件探索**，不适合作为我们 60 容器、230 万行规模的权威格式来源。
- 可迁移的：用它的 Template Results 视图做**人工抽查**（例如核对某个 flag 的头几字节），产出结论后再落到我们的声明式映射表（H）。

### 9. 不要保留 `declared_size` 这个单字段抽象（这是我们自己的既有设计）

- 相关做法：拿一个随 flag 变语义的字段当通用「预期大小」校验。
- **为什么不建议**：本次对标的 **11 个项目里，凡是处理「两个大小」的都显式分成两个字段**（repak `compressed`/`uncompressed`、CUE4Parse `CompressedSize`/`UncompressedSize`、Ekey `dwCompressedSize`/`dwDecompressedSize`、NeoXResearch「文件数据大小」/「文件数据解压后大小」），**没有一个**用单字段 + 语义词重载去校验。
- 正确做法：A + B + F。
